# 求职 AI 伙伴：早期产品假设（历史）

>
> 产品不做个人签证或工作资格判断，相关问题交给学校 DSO 或雇主核实。

更新：2026-10-05。本文记录用户已经表达的需求和讨论中的假设；不把假设当作已验证的市场结论。

## 我们为谁做

第一个用户是创始人自己，代表一群在美国求职的 F1 学生。他们可能缺少 networking 资源，不敢联系陌生人，也不知道如何表达自己的经历；对岗位、职业路径、实际工作和学校知识如何转成工作能力缺少认识。同时，重复填写申请表、改材料占用了探索和学习的时间。

用户最直接的表达是：**“我不知道该怎样开始，也没有时间找到适合自己去问的导师。”**

所以产品不能只要求用户先给一个目标岗位，也不能在第一次使用时就让用户确定长期职业方向。自动填表是已有的资产，将作为产品的一项能力继续保留。

## 正在讨论的第一段体验

入口：“我不知道怎么开始，带我开始。”

1. 用短对话了解经历、学过的内容、感兴趣或排斥的事情、时间与现实限制。允许“还不知道”，先提出可供纠正的理解。
2. 给出两到三个可探索的方向，以真实岗位和实际工作为例，解释学校经历可以如何形成证据，以及仍有哪些未知。
3. 选一个小问题和少量合适的交流对象，例如校友或有相似背景的从业者；解释为什么值得问、应该问什么。
4. 在产品里演练一次开场和追问，再准备用户愿意使用的消息。帮用户完成真实的小行动，复盘实际发生的事。
5. 根据反馈更新下一步，而不是把第一次判断永久当作用户的职业定位。

这里的“导师”未必是一开始就建立长期关系的人。先得到一次有帮助的交流，可能更符合用户当下的时间和胆量。

## 代办和学习怎样共存

| 场景 | 助手承担什么 | 用户逐步掌握什么 |
| --- | --- | --- |
| 了解职业 | 整理真实岗位、工作内容和能力证据，注明来源与时间 | 判断一个方向是否值得探索 |
| Networking | 筛选对象、拟消息、模拟对话、提示跟进 | 开场、提问、表达和建立关系 |
| 项目与能力 | 把课程经历映射到工作任务，提出可完成的小项目 | 做出可展示、能解释的真实成果 |
| 投递申请 | 从已确认资料准备材料，插件辅助填表并显示缺口 | 检查事实、理解为什么修改、决定是否提交 |

重复劳动可以多代办；沟通技能通过演练、提示和逐步减少帮助来形成。发送消息和提交申请应展示实际对象、材料与动作；不能替用户编造工作经历、工作授权或交流结果。

## 产品形态

电脑和手机共用一个响应式聊天产品、求职档案和任务记录。用户能看见并修正助手记住的事实、偏好和推断。职业探索、交流练习、材料准备和投递是同一段求职过程的不同能力。

插件是电脑浏览器中的执行端，不承载整个产品；未来可以添加官方 API 或云浏览器。手机可聊天、演练和审阅，现有 Chrome 插件不直接成为手机执行能力。见[自动化调研](automation-options-research.md)。

## 还需要一起决定

第一次15分钟体验已确定为：**比较两个职业方向，并确定一个验证行动**。课程项目与已有经历是比较的输入；方向先作为假设，由实际岗位任务和试做反馈逐步修正。详见[求职基础架构](career/architecture.md)。
- 当用户紧张时，助手如何帮助，才能既完成行动又留下可迁移的能力？
- 哪个真实经历最适合作为创始人自己的第一次完整试用？
- 如何区分“有用的职业认知”与看起来很丰富但没有帮助的建议？

先观察用户是否真的完成了一步、是否更理解下一步、是否愿意回来继续；消息数量和聊天时长不能替代这些结果。正式名称、公开仓库名、模型供应商和许可证尚未确定。
