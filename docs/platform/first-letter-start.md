# 初见选择与首封信后台请求的连接

按产品 02 §5.4、05 C1/C7 和 09 后台生成规则，FirstLetterStart.choose 将「直接写信吧」的实际选择、准备资料、执行请求和 outbox 放入同一个数据库事务。任何一步失败或迟到取消都保留原来的 C1；不会先进入 C7 再丢失后台请求。「好」仍进入 C2，不要求首封信配置，也不生成任务。

## 服务端配置与日期

新增可选的 PLATFORM_EXPERT_ROSTER_JSON，封闭 JSON 形状为 schemaVersion、revision、enabledExperts。例如：

```json
{"schemaVersion":1,"revision":1,"enabledExperts":[]}
```

未配置表示没有发布声明，不能接受首封信执行。显式空名单表示不介绍任何已上线队员。列表只能包含规范专家键，不允许重复、未知项或遗漏；不会默认启用 P0 的三个专家。配置只声明运营者实际开放的名单，不授予工具、模型、组织内容或对外执行权限。名单变更须更新 revision，并一致更新 API / worker 配置；名单内容本身也参加准备资料比对。

FirstLetterSettings 从本人已保存的每日偏好取得 IANA 时区，使用 PostgreSQL 的实际时钟计算当地日期。没有时区就返回 DAILY_SETTINGS_REQUIRED，不采用浏览器猜测、测试日期或其他用户设置。初次准备、执行 claim、实际 started 回调、最终发送检查和续租都在真实用户锁下检查当前设置。保留历史草稿和进度的读取不要求今天的日期仍与信稿相同。

## 重复点击和恢复

真实 welcome 操作 ID 同时标识首封信请求。并发重复点击只保存一次。客户端响应丢失后的再次观察验证原始选择、请求、准备资料和 outbox，然后返回原选择；不会重新检查今天的模型配置而误报首次提交失败，也不会借新登录替换原请求的执行会话。

旧实现已单独保存的 direct_letter 选择若没有配套执行请求，不会在重复观察时补造新授权。它需要明确的恢复设计。已经接受的准备若跨日、时区/名单变更或会话失效，同样不会自动改写原始权限和资料。

## worker 与应用接入

API 和 worker-main 现在组装同一套真实设置读取器。显式配置队员名单时，API 可启动通知生产者，worker-main 可启动首封信生产者及 worker；关闭时等待它们退出。options.enableQueue=false 仍可关闭测试应用的队列。商业模型调用仍由现有路由、服务器开关、用户协议、费用和租约共同限制。

worker 不再要求调用者传入固定日期/名单回调：从原始请求还原用户后，读取本人当前偏好及服务端名单。没有增加 Redis 消息字段、数据库表或账户数据项。内部 FirstLetterStart 已由 app 返回，原来的 HTTP /companion/welcome/choice 路由暂未切换。

## 尚需产品衔接

05 初见 O0–C1 没有收集时区，但偏好页在完成初见后才能进入。已向产品负责人提出：在「直接写信吧」之后补一个简短时区确认，浏览器仅提供候选，用户明确保存。尚未得到回复，当前不改产品流程，也不将缺时区的新用户导入无法继续的等待页。

时区入口确认并实现后，再把现有 HTTP 选择路由切到原子服务。唯一 post 发布、C7 完成、C2–C6 及超时触发、跨日/失效任务恢复、真实模型质量评测和完整学生流程验收仍待完成。这些不能由“队列已跑通”代替。

## 验证范围

使用虚构学生、真实出生及初见记录、已保存的偏好、隔离 PostgreSQL schema 和实际 Redis。仅模型传输注入测试响应，没有外部模型 HTTP 请求。测试包括原子回滚、并发重复、丢失响应的观察、原会话撤销、配置未设、午夜前后的真实时区换算、执行前时区变更、历史进度读取、独立 worker 和旧孤立选择拒绝。每个用例独立 schema，测试队列只清理自身 UUID 命名空间。

本轮未设置主应用环境变量、读取评测密钥、重启预览、迁移主库或部署。生产 worker-main 的接线经类型检查；完整生产进程启停和真实模型质量不由组件测试代证。

2026-10-09 验证结果：新增原子启动/设置/队列集 9/9、名单配置 3/3、初见及进度 HTTP 10/10、生成与真实进程恢复 33/33、既有队列及任务准备 15/15、生产/安全配置 13/13 均通过；API 类型检查及 diff 空白检查通过。修复后的测试合计 83 个不同用例。没有数据库结构变化，不需要新增 schema 审阅基线。
