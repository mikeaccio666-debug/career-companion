# Worker 总退出期限

对应产品 09 第 8B 步的部署准备，以及运行健康检查中原先尚未覆盖的整个 worker 关闭期限。

## 行为

实际 `worker-main.ts` 在启动完成后处理 SIGTERM 和 SIGINT。收到第一个信号时停止新增维护循环，并同时要求 heartbeat、任务消费者、各类生产队列、邮件 worker 和第一封信 worker 收尾；已有维护也纳入等待。所有组件结算之后才关闭数据库。重复信号共用同一次关闭，不会重置期限、重复清理或立即绕过收尾。

`PLATFORM_WORKER_SHUTDOWN_TIMEOUT_MS` 默认 25000，允许 1000–120000 毫秒。期限从第一个信号开始，覆盖 heartbeat、维护、队列、任务、邮件与数据库，不只是最后的 BullMQ close。该计时器保持引用，避免仅剩未完成 Promise 时被误当作正常退出。

- 所有关闭成功：退出码 0。
- 关闭失败：固定错误提示，退出码 1。
- 总期限届满：固定超时提示，退出码 1；不写任务完成、取消、退款或发送成功回执。
- 异常内容、数据库地址、模型提示词和账号信息不进入新增日志。

正常收尾允许当前已承接任务结束。超时结束进程后，已经发生的外部请求结果仍可能未知；原有真实任务/调用/费用租约与恢复规则继续负责核对，不能据退出码推断“没有调用供应商”或直接重试。该实现没有改写业务恢复策略。

## 部署边界

把应用退出期限设得短于目标托管平台的终止窗口，保留进程和容器收尾余量。25000 是应用默认值，不是对任何托管服务窗口的测量或承诺。

Node 定时器无法在事件循环被同步代码卡住时执行；宿主仍需独立的终止和进程树管理。此功能不证明所有外部 CLI 子进程、远端 API 调用都已停止，也不覆盖 worker 初始化尚未完成时的关闭。正式实例的 SIGTERM、数据库/Redis 故障和恢复验收仍待部署环境执行。

## 验证（2026-10-09）

18 项相关检查通过，API 类型检查通过：

- 4 项关闭处理器检查：同步停止入口、重复信号、正常收尾、期限届满、迟到结果、失败脱敏与一次退出。
- 11 项配置/入口检查：默认值与边界、无效配置、生产入口在不合法配置下连接前拒绝。
- 3 项真实 worker-main 子进程检查，使用隔离 PostgreSQL、独立 Redis 队列和受限制的回环模型响应：禁用→重启处理→再重启不重复处理；SIGTERM 等待实际在途第一封信并完成校验；模拟响应一直等待时以测试设置的 2 秒期限退出 1，重复 SIGTERM 不提前退出，数据库连接实际消失，调用及费用仍为 admitted、原阶段仍 running、没有完成正文或终态回执。

测试模型只走本地回环，未调用商业模型服务。真实子进程、独立队列、临时目录及 schema 已清理。没有修改主预览、主数据库、实际部署配置或启动部署。
