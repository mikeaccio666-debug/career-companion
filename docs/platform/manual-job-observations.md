# 本人收藏的岗位与原文证据

依据 03 §2.6、05 §2.16、07 P0-9 和 09 §3A。落实首版本人粘贴 JD 的收藏、核对、去重与移除路径；不代表完整旅程看板、投递阶段、材料包或学生 Agent 已接通。

## 用户路径

认证入口 `/journey/jobs` 从诞生后的学生入口与设置页进入。本人填写公司、岗位、岗位家族、地点、可选链接与截止时间、JD 原文和私人备注，点击「确认收藏」后保存。页面不生成未经核对的岗位事实。截止输入使用岗位原文的当地日期、时间和本人明确填写的时区，不默认采用设备时区。网页换算后仍通过现有接口保存明确 UTC 时刻与原 IANA 时区；两者同时提供或同时为空。

手贴记录始终显示「你贴的 JD · 没核实是否还开放」，`source=manual`、`state=unknown`。链接只保存；用户主动点击才打开，使用 HTTPS、noopener、noreferrer 和 no-referrer。LinkedIn、Indeed 同样只存不抓。没有抓岗任务、后台请求、关闭检测、匹配概率或市场岗位总量。

同一规范链接，或 NFKC、大小写与空白规范化后的公司加岗位名相同，先提示已经收藏。可以打开已有记录，或点击「还是新建」再提交明确的新收藏。服务端在实际账号锁内检查去重，不能靠并发绕过；分页之外的旧记录也通过本人查询找到。移除会删除原文与备注，更正时重新收藏形成一份新的观察；旧观察不能被悄悄改写成最新网页事实。

## 原文规则与信息边界

`career-core/manual-job-evidence` 只定位英文 sponsorship、工作授权、公民、U.S. person、ITAR 与 clearance 相关原句。引用带 JD 的真实字符区间，保存与读取均检查原文子串；保留原标点、CRLF 位置与 U.S. 缩写。明确措辞按规则记录 `explicit_yes` / `explicit_no`，条件、含糊措辞、正反冲突和展示溢出保持 `unknown`。规则不是雇主政策调查或个人资格判断。

网页只展示原句和检查时间，不把分类标签改写成「这家会 sponsor 你」。检查时间来自数据库实际保存/检查时刻，明确指出检查的是本人粘贴的文字；没有匹配原句时使用规格指定的「没找到相关原句……提交前请自己扫一眼」。原句最多展示 50 条，超过时明确提示并保持未知，完整 JD 仍可展开核对。

本文路径没有输入模型、L0 分级、消息来源、安全租约、工具授权或模型使用回执。正文及备注不进入任何主理人/队员上下文。后续真实 Agent 接入仍要补来源分级、当前权限、租约和模型使用持久化，不能把岗位元数据或保存成功当成执行许可。

## 持久化、权限与重试

迁移 056 建立 `platform_career_job_observations` 及不可变操作凭证表。公司、岗位、链接、截止、地点、原文、原句、备注和完整记录一起加密，仅归属、固定 manual/unknown、版本和实际时间作查询投影。密文认证 owner、记录和版本；读取核对全部投影、真实最新操作和确定性原句结果。有效旧密文不能撤销已经生效的移除。

本人真实学生会话、账号窗口、CSRF 和请求限额保护所有 HTTP 路径。新收藏要求当前协议及邮箱准入；本人读取、去重查询和删除在当前准入撤回后仍可使用。账号重置或请求中途失效使事务回滚，不产生孤立记录或伪成功凭证。账号删除级联清理密文与凭证。

操作凭证只保存加密的请求摘要、归属、坐标、版本与时间，不含 JD 或备注。原操作重试返回当前真实记录或已移除状态，不能复活被移除内容；不同请求复用操作 ID 被拒绝。一次最多保存 500 个岗位；列表每页 50 条、支持继续读取，列表不携带原文、原句或私人备注。独立详情按需读取。浏览器不持久缓存私人数据；切换账号、离开页面取消读取并清除组件内存。未知写入结果保留原操作进行重试。

通用角色目录和严格对象/ID 解析放在共享契约 `career-record-values`，方向契约保留原导出兼容；模型与数据库逻辑不进入页面。

## 接口与验证范围

- `GET /career/job-observations`：本人摘要页，可使用归属校验后的 `after` 游标。
- `GET /career/job-observations/:id`：本人完整原文及定位证据。
- `POST /career/job-observations`：本人确认收藏，原操作 ID，expectedRevision=0；客户端不能设置来源、开放状态、sponsorship、检查时间或归属。
- `POST /career/job-observations/duplicates`：按本人拟收藏字段只读查询实际重复记录，不写入。
- `DELETE /career/job-observations/:id`：本人明确移除，带真实版本和稳定操作 ID。

响应均为 private, no-store。真实 PostgreSQL 与真实密码登录 HTTP 检查跨用户、准入撤回、CSRF、账号窗口、并发去重、分页、加密、原句、删除、真实会话重置、已删除旧密文回滚、操作不可变、账号级联删除与重复执行迁移。契约与请求协议测试使用虚构数据，校验来源、字段、版本和归属；不替代真实存储测试。所有付费模型和外部供应商请求为 0。

类型检查、完整 Web 回归、构建和相关 API 回归结果以 PR 的确切提交及私人检查回执为准。本次没有浏览器视觉验收，没有更新主预览、主数据库或部署。投递阶段、岗位与方向比较、岗位准备上下文、主线收藏及投递官调用仍待后续真实链路实现。


## 截止时间与时区输入

产品 05 §2.16 要求截止带时区，08 的外部事件显示同样需要时区。岗位页现在可以按原文填写当地时间和时区，例如 America/Los_Angeles；输入后显示待保存的日期、时区名和 UTC 偏移量，列表按保存的原时区显示。既有 UTC 记录继续原样换算显示，不改写其时间或时区，也不添加提醒、抓取或岗位仍开放的声明。

换算与面试日程共享 zoned-date-time 纯函数。面试的既有接口和专用文案由适配器保留；岗位编辑状态与命令转换独立在 manual-job-deadline，页面只组装现有接口请求。

- 时间与时区都留空才表示未填写；只填一项、无效日期、无效时区不能保存。
- 夏令时前跳造成的不存在时刻拒绝保存，不自动顺延。
- 夏令时后退造成同一当地时间出现两次时，展示两种 UTC 偏移量，不预选；本人明确选择后才允许保存。改日期或时区清空原选择，提交时再次核对。
- 保存结果未知时，日期、时区及选择跟其他字段一同锁定；用原操作重试保留原 UTC 时刻、时区和 operationId，不重新换算或创建另一份记录。
- 编辑用的当地时间与选择字段不进入 HTTP 契约，服务端仍校验既有 deadlineAt / deadlineTimeZone 字段。

验证：全部 867 项网页检查通过（新增 5 项边界检查），网页类型检查与生产构建通过。独立 Chromium 环境使用实际 React 页面、全局样式和虚构账号客户端，确认缺失时刻阻止保存、重复时刻需选择、改时刻清空选择、第二次纽约 01:30 正确提交为 06:30 UTC、丢失回执后原请求重试只有一份记录，以及保存后显示原时区。390×844 浅色/深色与 1440×900 页面无横向溢出，截图已查看；私有 fixture 的 favicon 404 不影响页面功能。
