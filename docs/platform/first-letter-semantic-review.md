# 第一封信的语义复核与一次重写

依据 02 §3.4、§5.4，接续共用规则检查。first-letter-review.ts 提供内部 runFirstLetterReviewCycle：在真实后台 runtime 协议上执行语义复核及至多一次整封重写。没有开启商业调用或新增 HTTP 接口；测试用实际来源准备和注入的虚构供应商传输。

## 流程

1. 重新解析候选稿并进入同一个共用输出检查器。格式/硬规则不符合的初稿直接进入一次重写，不花一次复核调用为明确违规背书。
2. 其他初稿进入单独复核请求，逐项判断身份、记忆、对外执行、全部用户事实、队员、三件事、语言/人格、禁用内容，以及每个引用的完整含义。每项只能是 supported / contradicted / uncertain；缺项、额外字段和未给定的引用均拒绝。
3. 全部 supported 返回 reviewed_draft；任意 contradicted/uncertain 用固定规则编号请求重写。重写保留原资料、人设、语言和执行规则，随后再次运行共用检查及语义复核。
4. 一次重写后仍不符合，返回产品规定的普通失败提示「这条我没组织好，先不发了。换个说法再问我一次？」。该提示不是第一封信，也不完成 C7。真实正常终态且记账回调完成的 rewrite invalid_format 同样到此结束。
5. 拒绝、取消、断流、复核协议错误或记账回调失败立即停止，不自动重试或换模型。供应商错误不能被当作“复核不通过且未花费”。

每次函数调用最多两次复核加一次重写；初次写信调用不在这里。这里的计数仅在当前进程有效。后续持久化任务必须记录阶段与重写次数、核对上次调用及检查点后再恢复，不能重启此函数来清零重写限制。

## 来源与模型边界

- 复核 system 策略由代码持有；信稿、名字、人格、初见资料和引用都在 user 数据消息中。重写指令也由固定 system 文本给出。旧稿和复核结果不能注入平台指令。
- 发送的是原写信上下文的最小资料投影、正文与短引用；内部 owner/companion/conversation/source/preparation ID 不进入模型消息。完整结果仍含私人候选内容，只能在服务端处理，禁止记录日志。
- 复核请求使用现有 first_letter_generation 单次后台用途及同一个明确选择的服务端路线，没有普通聊天、其他供应商或更贵模型回退。每次请求 tools=none、store=false，沿用 1536 输出 token 和 15 秒适配器界限。
- 每阶段必须另行提供 requestAdmission 与 onModelCall。函数核对实际 started → admission/launch → finished 回调，等最终记账回调成功之后才接受结果；正文自报“完成”不能替代回调。
- 结果绑定 preparationId、正文/签名/引用摘要、rubricRevision、实际调用 ID 与 provider/model，并冻结。unknown/missing usage 的真实成本仍应由持久化 CostGuard 处理，不在此处声称免费。

## 明确的剩余工作

reviewed_draft 的 assurance 为 non_durable_model_judgment。它证明收到本次绑定信稿的模型判断，**不证明判断必然正确，也不是持久化回执、发送许可或学生入口完成**。原共用检查结果不会被伪造成 passed_rules，不能只看到模型 supported 就写入主线。

本模块需要由真实任务服务提供身份、当前资料/名单/协议、安全状态、后台租约与 heartbeat、每阶段 CostGuard 预留/发送意图/结算、加密检查点和崩溃恢复；这些尚未为第一封信接通。所有这些都完成并通过真实模型质量评测后，才能接 post 唯一发布/送达。当前没有任务自动启动，没有修改主应用开关、价格表、预算或部署。

复核模型可能漏判否定、事实和提示注入，规则也可能误判有效同义句。还需要真实样例与人工审查评测复核质量；注入传输返回 supported 的工程测试不算这项质量证据。原 PR3 顺序门槛不变。
