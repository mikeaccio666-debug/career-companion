# 主理人后台通知的初始读取恢复

依据 02 §15.3：生成意图、真实固定会话与来源在 PostgreSQL 中受理，Redis 只保存请求和任务引用。关闭页面、观察请求取消或通知重发不授予新代次、新会话、模型准入或诞生权限。

## 修复范围

实际 worker 在进入 generate / recover 之前，先在原来的两秒有限时事务内只读核对原受理请求、真实账号会话、当前协议、来源和任务状态。此前该事务的操作期限或 PostgreSQL 查询取消也会被归入 storage hold，停止后续通知恢复，尽管此次通知尚未进入模型生成阶段。

现在只在这段初始核对里，将真实 DatabaseOperationTimeout 或 PostgreSQL 57014 标成内部读取暂不可用。worker 拒绝本次通知并保持原数据库 outbox 可恢复；下一次分发仍沿用真实请求 ID 与任务 ID，重新运行完整身份、来源与核心生成状态检查。没有新增 HTTP 执行接口，不修改已受理请求、不合成授权，也不延长事务、租约或通知重新检查间隔。

进入 generate / recover 之后的超时不使用这个标记。已有数据库争用、授权撤销、损坏来源、配置不可用与未知供应商结果继续由原有规则处理；已发请求且没有可靠结果的任务仍 uncertain，不能因此重发或伪造 fallback。初始读取阶段超时不是此前供应商结果已知的证据。费用结算与原生成核心保持不变。

## 验证方法

虚构本人实际登录、真实 PostgreSQL、Redis、BullMQ worker 与本机 SSE 模型协议服务贯通。故障测试在真正的初始来源 SQL 前执行数据库 pg_sleep，分别触发真实两秒操作期限或 PostgreSQL 查询取消；没有直接抛出虚构超时。首次通知之后任务仍 pending / generation 0，没有模型请求、模型调用行或预览；原 outbox 未永久隔离。只调整已有通知的 dispatch 时间，以验证真实重新分发路径，不创建第二个意图。恢复后模型请求、调用行与预览各一份，原受理密文和摘要不变。

另一个场景在真实读取超时后递增账号认证版本、删除旧会话并建立新会话；重发仍使用原受理会话，收到 authorization hold，模型调用保持零。新会话不自动替代旧执行权限。

测试的等待器也修复了独立的观测竞争：BullMQ getState 是较晚的一次 Redis 读取，可能已经看到终态，而之前读取的 Job 对象还没有 finishedOn / failedReason。现在要求 Job 对象包含实际终态时间，才解释失败原因，不增加等待期限或改变生产执行行为。

## CI 证据与剩余条件

上传批次 #60 的 CI 曾出现通知恢复断言失败，但旧日志只有调用数断言，不能确定它发生在哪个阶段。#61 的完整 CI 仍因 PDF 抽取失败而失败，该轮通知恢复检查通过；不能把一次通过当作已定位之前的竞争。原通知丢失测试保留原通过条件，并在失败时补充经过限定的任务状态、通知终态、隔离原因和计数，不输出用户内容、凭据、原始异常或模型请求。

PDF 服务错误分类已在 #62 修复；CI 显式安装 PDF 依赖仍需要此前请求的 GitHub workflow scope。此文件不宣称 GitHub 完整 CI、生产负载、真实模型质量或用户浏览器验收已经完成。未修改主预览、部署服务、调用付费模型或处理真实申请。

本批远端验证：63 项真实 PostgreSQL / Redis、后台生成与实际进程恢复检查全部通过，0 失败、0 跳过；平台类型检查通过。额外对照使用 #62 的未修复服务源码和同一组新增测试，三项均观察到真实通知 completed、任务 pending / generation 0、held_reason=storage、模型请求为零；恢复已检查的修复源码后，三项全部通过。检查日志和具体源文件摘要只保存在忽略目录。此证据证明初始读取超时的恢复缺口，不证明旧 CI 那一次失败就是同一原因。
