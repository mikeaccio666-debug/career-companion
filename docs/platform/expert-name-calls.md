# 专家名字识别

依据产品 03 §4.4，`packages/career-core/src/team/members.ts` 保存规范名字，`name-call.ts` 提供不调用模型的候选识别。默认 P0 名单为前辈、投递官、面试官；真实接入方仍须从服务端配置构造当前可用名单，默认名单不证明对应服务已经上线。

`detectNameCall` 识别句首完整称呼、请/找/让/叫的请求和句末问句。单字称呼只在首行行首加标点时有效。多个名字按原文顺序返回，同一队员去重；每项只含名字、专家 key、原文 UTF-16 位置、句式与可用状态，不复制任务正文。不在启用名单的规范队员返回 unavailable，以便主理人采用产品规定的未上线文案，不能作为可调用队员执行。

引用、代码和改前改后标签不触发叫人。未闭合引用和代码按数据保守处理。普通多行输入仍可包含请求；具有对话标签的多行记录排除，已知多行转写也排除。转写类型必须由真实输入来源确定，不能以客户端自报类型代替来源校验。无标记的粘贴文本与本人输入无法仅靠字符串可靠区分，这个规则函数不声称能识别所有转写。

MentionPicker 和 Discord /ask 的结构化选择通过 `resolveExplicitExpertCall` 检查规范 key 与可用状态。调用方先核真实身份及渠道来源；普通聊天里的 @ 文本、邮件地址或字面 /ask 不冒充结构化选择。

## 接入边界

此改动没有创建房间、轮次、专家运行或转发卡。未来真实服务仍需按 03 §4.1 的顺序处理：专家单聊、回复转发卡、叫名字、卡片按钮、主理人。单聊里叫别人不换人；是否为插话、输入分级、房间所有权、租约和费用检查由服务端完成，不能靠候选结果跳过。

叫名字不等于存在具体任务，也不授予执行权限。没有任务时的只读答问、prepare、工具权限和多队员结果落库仍需真实轮次接入。当前 09 的付费实测前置与禁止付费调用之间的实施顺序仍待负责人确认，本改动只补纯规则，不改变产品路线或启动学生轮次服务。

## 验证

14 项专项测试覆盖完整/单字称呼、多人顺序、普通提及、引用与嵌套引用、围栏与行内代码、转写、改前改后、未上线队员、结构化选择、原文位置、名单校验及输入边界。包含这些测试的 career-core 全套 208 项通过，无跳过；career-core 和 platform-api 类型检查通过。这些结果不是真实聊天端到端或模型路由准确率评测。没有 UI、数据库迁移、付费模型调用、部署或主预览改动。
