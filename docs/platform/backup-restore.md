# 备份与恢复演练

本页服务于 07 §3.14 的上线底座。2026-10-09 已验证虚构数据的本地逻辑备份恢复；还没有配置生产备份、跨区域副本、对象存储版本保留或 PITR，也没有生产 RPO/RTO 承诺。

## 可重复的隔离演练

在仓库根目录运行：

```sh
./scripts/project.sh --filter @companion/platform-api recovery:drill
```

前提是当前用户可运行 Docker，且本机已有 PostgreSQL 17 的 `postgres:17-alpine` 镜像。脚本不拉取镜像，先解析本机 image ID 再按该不可变 ID 建容器。它不接受现有数据库 URL、容器名、备份路径或生产数据；不读取后端 env。不要为运行演练填入生产凭据。

实现位于 `services/platform-api/test/recovery/backup-restore.drill.ts`。它按需创建一个 UUID 命名的 PostgreSQL 容器（512 MiB、1 CPU、256 PID），端口只绑定 loopback；source 和 target 是该新容器里的独立数据库。随机测试密码和数据密钥在内存里生成，命令行不包含它们。文件在权限 0700 的临时目录，dump/manifest 为 0600；成功或普通异常退出都会关闭连接并移除本次容器、匿名卷及临时文件。Docker/PG 子命令失败只输出固定错误，不打印原始 stderr。

演练不是自动备份工具，也不接入常规测试里的共享数据库。默认 `test/*.test.ts` 不运行 Docker 演练；须显式执行上述命令。主机或测试进程被强制终止时 finally 无法保证执行，应只检查并清理本次 `companion-recovery-<UUID>` 且带匹配 label 的资源，不能使用 prune 清理其他任务。

流程：

1. 新 source 数据库执行当前全部迁移，使用真实注册/协议/上传/简历接口创建两个虚构账号、一份附件、两版正文及一条本人确认。
2. 对全部 public 下的 platform 表采集行数与有序行摘要，对实际附件采集 SHA-256 清单。关闭 API 与写入器，保持数据库和附件快照配对。
3. 使用该容器内的 `pg_dump --format=custom --no-owner --no-privileges` 生成逻辑备份，另存附件。校验和保存在私有清单。
4. 删除 source 数据库和原附件目录，确保后续验证不能误读原实例。
5. 先验证截断归档无法成功恢复，再使用完整归档执行 `pg_restore --single-transaction --exit-on-error` 到空 target。目标不重新执行迁移；表、迁移账本、外键和触发器必须来自备份。
6. 比较全部表的实际行、列定义、约束、索引、触发器、函数、枚举及附件字节；用真实 API 读取已确认正文和附件，核对旧正文历史，重放原确认仍只有一条决定。验证匿名与另一账号不能读取本人文件/简历，恢复后的不可改写触发器仍生效。
7. 同一密文和坐标用原密钥能解密、错密钥失败；等长附件损坏被清单发现，丢失附件的 HTTP 读取返回缺失。清单校验必须在开放站点前完成，HTTP 仅检查文件大小并不能替代内容校验。
8. 在隔离 target 撤销已恢复的会话、提高账号认证版本，验证旧 cookie 失效、重新登录后可读。全程不开 worker/Redis、不调用模型、不发邮件、不联系第三方。

## 上线前必须落实的恢复集合

| 数据/配置 | 必须保留的内容 | 当前证据与缺口 |
| --- | --- | --- |
| PostgreSQL | 完整数据库、迁移账本、约束/触发器；生产角色和权限单独记录 | 本地逻辑恢复通过；云实例、角色权限与 PITR 待验证 |
| 私有对象 | 与数据库时间点配对的对象 key、版本、长度、内容校验和及删除状态 | 本地附件复制已演练；S3/R2 实际版本与权限恢复待验证 |
| 加密配置 | 能解密相应历史数据的密钥及版本引用，独立受控保管 | 随机测试密钥已验证；生产密钥备份、取回权限及轮换尚未配置 |
| 发布配置 | 源码 commit/image digest、PG 版本、配置版本、已审核法律/安全/身份资产 | 不能只备份数据库而丢失配套配置；实际部署需形成 release 清单 |
| 删除与撤销 | 备份时间点以后发生的账号删除、凭据撤销、文件清理的可信记录 | 完整账号删除仍未开放；恢复后避免复活已删除数据的流程待实现 |
| 队列与外部结果 | PostgreSQL outbox/操作证明，以及供应商结果不明的恢复规则 | 本演练不启动执行队列；不证明真实任务、邮件或供应商恢复无重复 |

数据库逻辑备份自身是一致快照，但不会同步外部对象存储；本演练通过关闭所有写入器得到配对集合。生产需要停写窗口或经验证的版本化对象方案。单库 `pg_dump` 也不含集群角色/表空间，不能将本演练的 `--no-owner --no-privileges` 直接当作生产权限恢复方案。[PostgreSQL 17 SQL dump 文档](https://www.postgresql.org/docs/17/backup-dump.html)

逻辑 dump 不是连续归档/PITR。后者需要基础备份与对应 WAL；托管服务启用开关后还须实际验证可恢复时间点及失败告警。[PostgreSQL 17 PITR 文档](https://www.postgresql.org/docs/17/continuous-archiving.html)

## 正式环境恢复顺序

以下是上线准备的操作顺序，当前未执行生产恢复，也不是可直接替换域名后运行的脚本。

1. 隔离原写入入口，停止 API 写入、worker、调度器和邮件 outbox。明确事故时间、要恢复的时间点、已发生但结果不明的外部动作；保留现场供核对。
2. 在独立数据库和私有 bucket/prefix 恢复。使用受控备份清单核对来源、完整性、时间点、发布版本和所需密钥；不向公共日志输出连接串、密钥、正文或原始备份。
3. 从干净数据库恢复匹配版本的数据及角色/权限。恢复失败即停止；不以自动迁移掩盖缺表、缺历史或损坏。单事务恢复语义见 [pg_restore 文档](https://www.postgresql.org/docs/17/app-pgrestore.html)。
4. 对齐对象版本并检查清理/暂存日志；缺失对象、未知写入和历史删除不能被当作已完成。清单摘要须来自可信保存位置，摘要本身不证明备份来源可信。
5. 离线重放备份之后的删除/撤销记录。只给隔离验证实例加载解密配置，调用和邮件开关保持关闭；先核对 schema、解密、本人读取、跨账号拒绝与操作幂等。
6. 撤销恢复出来的登录会话并核对所有外部/插件授权。测试里的会话清理仅验证网页登录，不代表其他令牌和未完成任务已失效；这些需要各自恢复策略。
7. 先开放受控验证，再由发布负责人决定流量切换。逐项核对真实租约、权限、原始输入和外部回执后才恢复 worker/邮件；不清空费用或执行证明后重跑结果未知的调用。
8. 记录实际丢失区间、恢复用时、未恢复项目、责任人与回退点。没有验收结论时保持新实例隔离。

## 本次验证与剩余门槛

本次在 edaix-dev 的全新临时容器中演练，PG 17 镜像 ID 为 `sha256:b0f9560a2de083e2cc7382e75f808c7381a32852a7ec49117deedb300e552b24`。恢复 180 张表、112 行虚构数据和 1 份附件；所有表行摘要及上述数据库结构匹配，实际内容/API/权限/历史检查通过，外部调用为 0。测试使用 Fastify 实际路由的 inject 传输，不等于真实 TLS、代理或公网访问验收；未覆盖的业务表为空，其结构恢复不能证明所有领域流程都恢复正确。

少量虚构数据的执行时间只用于发现演练退化，不能外推生产 RTO 或备份频率。RPO（可接受的数据丢失窗口）、RTO（恢复服务目标）、备份保留期、跨账户/区域副本、密钥保管责任及恢复演练周期，须在选择生产数据库和对象存储后明确并验收。本地演练不改变未部署、完整账号删除/导出未完成及主对话质量门槛未通过的状态。
