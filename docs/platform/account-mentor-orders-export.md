# 本人导师订单、预留与财务历史归档

依据产品 04 §4.11、06 §11.3 和 09 §11，接续 [导师服务历史与会后反馈](mentor-completion-ratings.md)。这是账户内部快照的一部分；不是完整下载接口，也不执行收款、退款、取消或保留期清理。

## 导出内容

- `mentorOrders`：原报价、当时展示的完整公开服务条款、币种、付款引用、付款时间、已退款金额、状态、归属、原操作与修订时间。保留展示价与实际报价的区别，不根据现价重算。
- `mentorOrderOperations`：按订单修订保留 quote、void、pay、refund；收退款保留原金额、外部交易引用、发生时间和操作 ID。quote/void 标签由验证过的原证明位置与状态确定，不伪造原系统没有保存的命令。取消预约不推导出退款。
- `mentorSlotReservations` 与 `mentorReservationOperations`：实际预留的完整时间窗和 held/released 历史。容量时间窗可能长于用户购买的服务时长，分别保留，不改写成相同时间。内部导师账号、档案和时段 ID 不带出。
- `mentorFinancialRecords`：通过当前本人订单关联的最小财务保留记录，包含原金额、退款总额、状态、付款引用和已保存的 retentionUntil。
- `mentorFinancialOperations`：原财务证明的修订与 pay/refund 动作，并关联已验证订单回执的 operationId。财务证明只保存摘要和动作，没有过去每一版金额及保留期快照；归档不假造这些旧快照，具体交易金额和日期来自原订单操作。

六个区段各对应一张表。当前 166 张表中，78 张已有投影、7 张明确排除、81 张仍待处理。`complete=false`、`filesIncluded=false` 保持；完整归档 worker、私有文件和下载入口尚未交付。

## 归属与保留边界

订单、预留和它们的证明按自身 `user_id` 分页枚举，逐项与已验证的本人预约和历史对应；额外证明、缺失记录或跨账号父记录不能被内连接静默过滤。财务保留表没有 user_id，明确通过存活的 `platform_mentor_orders.id` 加本人 user_id 关联。已删除账号留下的财务记录不属于当前账号归档范围，不通过交接码、付款引用或邮箱重新猜测归属，也不会借归档执行保留期清理。该规则不把财务表定义为全局非个人数据；删号后的保留和清理仍遵守 06 §11.3。

交接码及其摘要、员工账号、员工授权版本、确认与政策文件引用、文件内容、内部摘要和密文不序列化。公开条款及用户自身的交易引用属于归档内容；它们不进入源码、运行日志、公开链接或模型上下文。收退款原始文件目前仍是员工持有的证据，不在这次个人文件交付范围内，客户生命周期处理仍待完成。

## 历史校验

`MentorOrders.readHistoryInTransaction` 共用原订单完整性校验，返回原不可变操作链；原普通读取仍只返回订单。预留历史读取校验完整一到两条证明，并用原首次操作与时间验证 held 快照，阻止只读取最新证明时遗漏初次占用。两者均验证密文上下文、行绑定、父记录和历史摘要。

财务读取验证最新金额与原订单一致、修订连续、全部财务证明的认证密文、动作和外部交易摘要，以及它们与已验证订单收退款命令的一一对应。历史校验不依赖当前员工角色、导师资料或目录可售状态，不重新访问员工文件或调用外部服务。

仍在密码复核后的同一 5 秒 REPEATABLE READ 事务中捕获，提交后才交付结果。错误、取消、未知字段、超限或历史缺失使整次捕获失败，复核凭证随事务回滚；没有部分成功结果。超出当前 16 MiB 上限仍需要归档 worker，不截断列表。

## 验证

新增十项隔离 PostgreSQL 测试，覆盖报价和作废、原完整时间窗、付清与部分/全额退款、保留期原值、其他账号和实际删除账号的保留账隔离、损坏/未知字段/孤立证明、旧 held 回放和缺失初次证明、105 个真实匹配取消记录跨页、103 条收退款证明跨页、取消及复核凭证重试，以及实际并发退款在归档提交后完成。全部使用虚构资料和真实服务的本地持久化路径；没有真实资金、支付供应商、付费模型或第三方调用。

最终 26 份账户导出、覆盖、导师服务及组织知识测试共 329/329 项通过，无跳过，包含本轮新增 10 项；API 类型检查及 git diff --check 通过。数据库结构未改，主数据库、开发预览与部署均未更新。
