## 这份文档回答什么问题

第一批真实用户的产品放在哪里、分几套环境；代码怎样从 PR 走到生产、出问题怎样回退、怎样配合分批放量；用户数据存在哪、交给了谁、怎样加密、备份和删除；谁值班、出了事怎么处理、怎样告诉用户；每月花多少钱；从今天到 B1 还要做哪些部署准备。

**结论**
- 沿用 Codex 的首选「Render 同源」：一个 Web Service 同时提供网页和 API，加同一镜像的 Background Worker、付费 Postgres 与 Key Value、私有 Cloudflare R2；托管、文件和邮件都在美国，区域 W0 按 Oregon 拍板；首批不拆 Vercel。
- 三套环境：开发（现有远程开发机）、预发（只有虚构数据，兼作获批的评测环境）、生产（B0 起的真实用户都在这里，按邀请批次放量）。
- 发布走「PR → CI 构建一次、记下 digest → 同一 digest 先上预发 → 产品负责人批准 → 先迁移，再发 worker 和 API」；迁移只追加、兼容上一版本，回退只回代码。开关只放共享环境组，改完要对 API 和 worker 各手动部署一次才生效；下一批的功能先上线、开关关着，到批次再打开。
- 模型调用要等 OpenAI 批准美国数据驻留、项目改走 `us.api.openai.com` 之后，才算在美国处理，获批前隐私政策如实写。处理用户数据的第三方有托管、对象存储、OpenAI、邮件、错误追踪、招募问卷、蔓藤（真人意向与订单）、客服邮箱托管，B2 加 Discord。`restricted` 结构化字段做应用层加密，对话正文和简历靠托管方的 AES-256 静态加密；数据密钥放在团队密码保险箱，两名管理员都能取。库外备份每天一份，用非对称加密，bucket lock 锁 14 天；B0 前做第一次恢复演练。
- 网页和 API 只有一个实例，数据库也不开高可用，所以危机资源不能只靠服务端：PWA 外壳里预置一张静态危机资源卡，发消息失败时直接显示。Render 健康检查只查存活，worker 心跳和 L2 自检走不依赖我们应用的外部告警。
- 首批 60–100 人时，固定成本每月约 $115–240，模型每月约 $200–1,360（假设）；建议模型月度总预算 $1,500，按「顶到硬上限的人不超过 10 名」对账，请产品负责人批准（待确认 4）。

## 1. 结论：怎么部署，为什么

**推荐**：B0–B3 用 Codex 已推荐的「Render 同源」方案（docs/platform/cloud-managed-options.md「选择依据与下一步」；docs/platform/deployment-plan.md「组件怎么部署」），首批不先拆 Vercel；托管、文件和邮件在美国，模型调用在哪里处理取决于 OpenAI 是否批准美国数据驻留（§4.6）。

**一句话拓扑**：用户浏览器 → `app.<域名>`（Render 托管的 HTTPS）→ 一个 Docker Web Service 同时提供网页和 API（含 SSE、私有文件，B3 起含插件接口 `/ext/*`）→ 同一镜像的 Background Worker 跑任务队列、调度、晨报、邮件和保留期清理（B2 起另加一个 Discord 进程）→ 同区的付费 Postgres（唯一事实来源）和 Key Value（任务通知）→ 私有 Cloudflare R2（文件与库外备份）；模型与语音由服务端调用 OpenAI，邮件经 Resend。托管、文件和邮件在美国；模型调用只有在 OpenAI 批准美国数据驻留、项目绑定 `us.api.openai.com` 之后才算在美国处理。

| 决定 | 内容 | 理由 |
|---|---|---|
| 托管 | Render：Web Service、Background Worker、Postgres、Key Value；对象存储用 Cloudflare R2 | 现有 Fastify、BullMQ 和 API 里的常驻定时器原样运行，不用改成 serverless（docs/platform/cloud-managed-options.md）；生产镜像和 Render 示例已在 `infra/platform/production/`；小团队不用管操作系统、数据库补丁和证书 |
| 同源，不拆 Vercel | 网页和 API 在同一个 origin | Cookie、SSE、私有媒体、PWA 缓存头都已按同源实现并测过；只有一个发布面，没有前后端版本错配；少一个第三方处理方。前端需要独立预览时，在首批复盘（2027-02-15 那周）再评估 |
| 区域 | 美国。Render 用 Oregon，W0 拍板；R2 用美国辖区 | 用户和主要供应商都在美国（§4.6）；延迟主要来自模型，区域影响有限，所以不再做 W2 实测。换区要新建服务并迁库（附录 A-6），所以 W0 定死 |
| 工作区档位 | Render Pro，不用 Hobby | Hobby 只能一名成员、每个项目最多两个环境、PITR 只有 3 天；Pro 有 7 天 PITR、强制双因素和工作区审计日志（附录 A-3、A-11）；生产设为受保护环境（附录 A-12）。Pro 没有只读角色，席位规则见 §5.4 |
| 环境 | 开发、预发、生产三套（§2） | 真实用户上线后不能在生产上试；评测要求「单独环境、数据全部虚构」（09 第 8 步） |
| 不进生产 | 工作台（`/workbench`）、本地朗读与转写、本地模型、3090 声线 PoC、浏览器与 CLI 执行器、只给工作台用的图片和视频供应商、`services/application-service`、`imports/` | 没有完成 Linux 与隔离验收，或不属于首批产品（AGENTS.md；docs/platform/deployment-plan.md；12 §5.2；09 §16） |

**相对 Codex 方案的补充**（都由产品要求推出，不改 Codex 的组件选择）：

1. 加一套预发环境，兼作获批的评测环境（Codex 的 Render 示例只有生产）。
2. 工作区用 Pro；生产设为受保护环境，和预发之间阻断私网流量；Render 席位只给两名管理员（§5.4）。
3. R2 bucket 建桶时就选美国辖区（之后不能改），而不只用位置提示（位置提示是尽力而为，附录 A-20）。
4. 每天一份库外备份：Render 定时任务加专用备份镜像，非对称加密，R2 bucket lock 锁 14 天；B0 前做第一次恢复演练。docs/platform/deployment-plan.md 已要求「独立恢复演练和定期逻辑备份」，本文定频率、保留期和防删除（§4.4）。
5. 健康检查拆成两个接口：Render 用的存活接口，以及给外部探测和告警用的深度检查接口（§6.4）。
6. B2 起 Discord 机器人是单独的 Background Worker，只跑一个实例（09 第 9 步）。
7. 首批生产完全不开工作台，员工只在预发用虚构资料使用；首批复盘时再评估。

**什么时候换方案**：出现以下任一情况再评估 Vercel 前端、Postgres 高可用或迁到 AWS、GCP：首批复盘认为前端需要独立预览；可用性要求超过单实例能给的水平（例如 P1-C 开始收费后）；需要专用私网、GPU 或浏览器执行池（docs/platform/cloud-infrastructure-options.md「为什么先托管」）。只需要固定出口 IP 时，Render 专用出口 IP 就够（§3.3）。

## 2. 环境与发布

### 2.1 三套环境

| | 开发 | 预发（staging） | 生产（production） |
|---|---|---|---|
| 在哪 | 现有远程开发机 edaix-dev（docs/platform/remote-development.md） | Render 同一项目下的独立环境 | Render 受保护环境 |
| 用途 | 日常开发与 Codex 自测 | 发布前验收；真实 HTTPS 与手机实测；恢复、回退与止血演练；获批的评测和声线盲测；员工使用工作台；10 §10 的 Discord 验收 | B0–B3 真实用户 |
| 数据 | 只有虚构资料（AGENTS.md） | 只有虚构资料和内部测试账号；不导入任何生产数据 | 真实用户数据 |
| 谁能访问 | 开发者经 SSH；服务只监听 loopback | 团队成员；不对外发邀请 | 用户按邀请；员工按角色；Render 席位只给两名管理员（§5.4） |
| 商业模型调用 | 关；本地模型与本地语音只在这里 | 默认关；评测窗口经产品负责人批准后打开，用单独的供应商项目和较低的费用上限（与 07 §9 第 11 行的冲突见待确认 11） | 预算批准且 CostGuard 接上后打开（09 第 8 步） |
| 怎么部署 | 手动同步 | main 每次合并后按 digest 部署 | 管理员人工触发，产品负责人批准 |
| 规格 | 现有共享主机，不作生产可用性承诺 | 最小档（§9.1） | §3 |

**数据隔离**：预发和生产各有自己的数据库、Key Value、R2 bucket、队列名（`PLATFORM_QUEUE_NAME`）、数据密钥、供应商项目与密钥、发信子域，B2 起还各有自己的 Discord 应用、机器人令牌和 OAuth 回调地址；环境之间阻断私网流量（附录 A-12）。生产数据永远不复制到预发或开发；排查生产问题只看不含内容的日志，以及用户主动附上的片段（07 §6.4）。按 PR 生成的预览环境首批不开（Render 示例已关，省钱，也少一份密钥暴露）。

**为什么 B0 直接在生产上跑**：B0 的目的就是验证生产链路。B0 的 5–10 人用的是自己的真实资料：团队成员、蔓藤员工与导师（都有雇佣或合同关系）；自愿的往届学员只在危机模板审核和资源核实完成后加入（§7.1），否则推迟到 B1。B0 的账号和数据之后照常保留。B0 与 B1 的区别只在邀请码的 `batch`（09 第 8B 步）。

### 2.2 从 PR 到生产

1. **PR**：Codex 按 09 的步骤开 PR，`verify` 全绿、至少一位人工审批后合并（07 §11）。涉及迁移的 PR 在描述里写「本迁移与上一版本代码兼容」或说明为什么不兼容（不兼容的不合并）。
2. **构建**：CI 对每个合并到 main 的 commit 构建一次 `linux/amd64` 生产镜像，推到镜像仓库（建议 GHCR），记下 digest；预发和生产都**按 digest 部署**，不按 tag，也不重新构建（按 tag 回退会拉到这个 tag 当前指向的镜像，附录 A-9）。镜像仓库至少保留最近 10 个生产 digest（假设），因为回退要求目标 digest 还在仓库里；GHCR 私有包的存储和 Actions artifact 共用额度（附录 A-28），计入 09 待确认 2 的 GitHub 套餐。现在 `.github/workflows/ci.yml` 只跑 `verify`，不构建生产镜像，由 Codex 补；镜像只在本地 ARM64 验过，要补 AMD64（infra/platform/production/README.md）。
3. **预发**：按同一 digest 部署（预发开自动部署，或由 CI 触发，由 Codex 定），顺序是迁移 → worker → API；跑一遍冒烟检查（健康检查、用虚构邀请码注册、登录与退出、发一条消息、上传并读回一个私有文件、构造一条 L2 消息确认 2 秒内收到模板和资源卡、手机尺寸打开五个界面）。
4. **批准**：产品负责人在发布记录里写「批准发布 <commit>」。发布记录不含密钥，写明 commit、镜像 digest、迁移编号、改了哪些开关、谁批准、谁执行、结果。
5. **生产**：由管理员执行（Codex 不部署，07 §11）。迁移作为一次性任务先跑一次；成功后先让旧 worker 停止接新任务，再发同 digest 的 worker，最后发 API。每个服务的发布前命令只挡它自己的发布，跨服务不是原子发布，所以顺序靠发布手册保证（infra/platform/production/README.md）。发完检查健康与登录，再用内部测试账号跑一次 L2 自检（§6.4）；之后盯 30 分钟：错误率、首个可见反馈与第一句延迟（07 §7.4）、队列等待。
6. **时间窗**：周二到周四美西 10:00–16:00（假设；B0 两周后按实际低峰时段调整，前提是有人醒着盯）。周五晚和周末只发修复。冻结期：11-26 至 11-29（感恩节）、12-21 至 2027-01-03（节假日值班期）。冻结期内只允许两类发布，都要产品负责人批准：修复；带开关、开关关着的新代码（含只追加的迁移）（待确认 17）。

正在进行的轮次在发布时可能被打断：旧实例收到 SIGTERM 后最多等 120 秒（Render 示例的设置，附录 A-7）；重启后过期的轮次标 `failed`，网页经订阅流显示已校验的部分和「没说完 [重试]」，后台任务从检查点续跑（15 §10）；L2 轮次崩溃后由服务端自动重放（09 第 2 步）。改开关同样要重新部署（§2.4）。所以发布频率保持在每周一次常规发布加必要的修复，不在晨报集中生成的时段发布。

### 2.3 迁移与回退

- **迁移只追加**（09 §1.1 第 5 条）：加表、加列、加索引；删列、改名、改类型分两次发布，先发不再读写旧列的代码，下一次发布再删。这样任何一次发布都能单独回退代码。
- **回退代码**：用 Render 的回退把 API 和 worker 退到上一个发布，复用上一版的镜像 digest（附录 A-9）。数据库不随之回退。两个服务分开回退，不是原子操作：先 API、再 worker（与发布顺序相反），两边都兼容当前的数据库结构。判断规则：发布后 30 分钟内出现 S1 或 S2（§8.2），15 分钟内找不到明确的修复，就回退。
- **回退会改变量**：服务级环境变量会回到目标版本的值，环境组里的值不变（附录 A-9），所以开关只放环境组（§2.4）。回退后马上逐项核对开关值，和发布记录不一致时在环境组里重设，再对两个角色各部署一次，并记入发布记录。在控制台回退会关掉该服务的自动部署，预发演练回退之后要重新打开。
- **回退数据库**：只用于数据损坏，不用于普通坏版本。做法是 PITR 恢复成一个新库，立即清空它的 IP 白名单（默认 0.0.0.0/0，附录 A-34），核对后再切连接（附录 A-3）。这样会丢失恢复点之后的写入，对象存储也不会回到同一时刻（docs/platform/deployment-plan.md）。需要产品负责人批准。
- **前端兼容**：PWA 的旧窗口会一直跑旧前端，直到用户关掉全部窗口（docs/platform/mobile-web.md），所以 API 至少兼容上一版前端。
- **演练**：B0 前在预发做一次「发布 → 回退 → 核对开关 → 再发布」演练，记录用时。

### 2.4 功能开关与分批放量

09 的开关（`PLATFORM_FEATURE_*`、`PLATFORM_TEAM_ENABLED` 等）是全局的；批次之间的差别来自邀请时间。做法：**下一批要开的功能先上生产、开关关着，过了闸门再打开**。

**开关怎样生效**：`PLATFORM_FEATURE_*`、`PLATFORM_TEAM_ENABLED`、`PLATFORM_ALLOW_PROVIDER_CALLS`、`PLATFORM_REQUIRE_INVITE` 只放在 API 和 worker 共用的环境组里，不设同名的服务级变量（服务级变量会被回退改掉，§2.3）。API 和 worker 都关了自动部署（`render.example.yaml` 里 `autoDeployTrigger: off`；生产本来就人工发布），而环境组改动只会让开了自动部署的服务自动重新部署（附录 A-14）。所以改环境组之后，要对 API 和 worker 各手动部署一次（同一 digest，不重新构建），新实例过了健康检查才生效，需要几分钟；只改值、不部署，开关不生效。中期把止血开关改成数据库里的运行时配置，就不用重启，也不会打断正在输出的回复（交给 Codex，首批复盘时评估）。

| 批次（07 §6.3） | 邀请 `batch` | 生产上打开的 | 新增进程或接口 | 仍关闭 |
|---|---|---|---|---|
| B0，11-23 起 | `B0` | P0 全部（W7 完成的项 11-30 起打开）；商业调用（预算获批后）；队伍只开主理人、前、投、面 | Web Service、worker | Discord；`/ext/*`；身份时钟提醒；外部来源 |
| B1，12-07 起 | `B1` | 同 B0 | — | 同上 |
| B2，2027-01-04 起 | `B2` | Discord 私信；B2 补齐集（公开职位链接读取，只开 `system` 来源）；身份时钟提醒（移民专业人士审核后）；作战简报（面经到位后） | Discord 进程（12-18 前部署，不对用户开放；见待确认 17） | `/ext/*` |
| B3，2027-01-25 起 | `B3` | 插件后端，只对自愿者（待确认 12） | API 内的 `/ext/*` | — |

- 所有批次：生产 `PLATFORM_ENABLE_WORKBENCH=0`、`PLATFORM_REQUIRE_INVITE=1`、`PLATFORM_FEATURE_IDENTITY_REMINDERS=0`（审核前）；内推评估相关的表和开关都不存在（09 第 8B 步）。
- **暂停放量**（07 §7.4 的护栏触发时）：停发新邀请码，不下线服务；已入组的用户照常使用。
- **冻结期跨批次**：B2 所需功能在 12-18 前「开关关着」上生产，12-21 至 01-03 冻结期内只发修复和「开关关着」的代码，01-04 过闸门后打开。

## 3. 生产拓扑

### 3.1 进程

- **MCP 与外部数据**（03 §2.8；09 第 3D 步；docs/platform/mcp.md）：
  - B2 只开 `system` 来源，即第一方岗位源：API 和 worker 直接向 Greenhouse、Lever、Ashby 的公开读取域名发只读请求。

## 4. 数据与隐私

### 4.1 数据分类

敏感度以 03 §8.5 为准，本表只补「存在哪、怎样保护、交给谁」，按实际实现如实写。所有 Postgres 数据（含副本和备份）都有托管方的 AES-256 静态加密（附录 A-18），下表「保护」一列只写在此之上的措施。

| 类别 | 例子 | 存在哪 | 保护 | 谁能看 | 会不会离开我们的系统 |
|---|---|---|---|---|---|
| 账号与认证 | 邮箱、密码哈希、会话 | Postgres | 密码哈希；会话 cookie HttpOnly、Secure、SameSite=Lax | 本人 | 邮箱地址交给邮件服务 |
| `normal` | 目标、技能、偏好、公司名与阶段 | Postgres | 只有托管层 | 本人；发言者按 03 §8.5 | 模型；B2 起 Discord（10 §3.9） |
| `sensitive` | 简历全文、对外内容全文、联系人、薪资与 offer 条款、学籍日期 | Postgres；上传原件在 R2 | 待确认正文和学籍日期做应用层加密；**简历全文、联系人、offer 条款只有托管层保护** | 本人；专家只经工具读 | 模型（按需）；不进 Discord、邮件、推送 |
| `restricted` 结构化字段 | 身份与签证日期、待业天数、OPT 与 H-1B 状态 | Postgres | `data-crypto.ts` 应用层加密（09 第 2 步；同一机制也加密主理人自由文本和通知载荷） | 本人 | 只在用户自己提起时用于网页正文的生成；不送朗读（12 §6.4） |
| 对话消息正文 | 用户在对话里说出的心理、健康、危机和身份内容 | Postgres | **只有托管层保护**，不在应用层加密范围内；`platform_safety_events` 只存指向这些消息的引用（与 03 §8.5「一律加密」的出入见待确认 16） | 本人；安全复核人只看被标记的那一轮及前后各 5 条（07 §6.4） | 模型（作为上下文）；用户在 Discord 私信里自己打的字存在 Discord（§4.3） |
| 组织内容 | 题库、方法卡、面经 | Postgres | `license_id`、编辑与审核分离（04 §4.3） | 按 entitlement | 模型（`allowed_uses` 含 `model_context`） |
| 运营与审计 | 埋点、员工审计、成本账本、回执 | Postgres | 不含内容（07 §7.5） | 员工按角色 | 不离开 |
| 商业 | 真人意向（称呼、邮箱、用户写的需求）、订单引用、`payment_ref` | Postgres | 不存支付信息 | 运营 | 离开：蔓藤运营看到称呼、邮箱和用户写的需求（06 §6.3）；P0 由蔓藤线下收款，订单与付款记录在蔓藤 |
| 客服往来 | 用户发到 support@、privacy@ 的邮件和附件（可能含截图、简历、对话片段） | 邮箱托管商 | 托管商的措施 | 运营、产品负责人 | 邮箱托管商（§4.3） |

### 4.2 加密

- **传输**：全站 HTTPS，证书由 Render 自动续期；现在只有静态文件带 `nosniff`、私有文件带沙箱 CSP，B0 前补 HSTS、CSP、防嵌套等安全响应头（也要确认 Render 入口默认加了哪些）；数据库和 Key Value 不开公网访问，只走 Render 私网；R2 走 TLS（附录 A-21）。
- **静态**：Render Postgres 的主库、副本和全部备份都用 AES-256 静态加密，付费且开了持久化的 Key Value 也是（附录 A-18）；R2 对对象和元数据做 AES-256 静态加密（附录 A-21）。隐私政策可以写托管方静态加密。
- **应用层**：`src/data-crypto.ts` 用专用密钥 `PLATFORM_DATA_KEY` 加密 `restricted` 结构化字段、待确认正文、学籍日期、通知载荷和主理人自由文本，密文带密钥版本，粘贴到别的行无法解密（09 第 2 步）。对话消息正文和简历全文不在其中（§4.1）。预发和生产用不同的数据密钥。
- **数据密钥丢失等于数据永久不可读**，备份也救不回来。所以生成后立即放进团队的密码保险箱，两名管理员都能取出，每季度核对一次；不进聊天、邮件、源码和开发机。
- **库外备份用非对称加密**（例如 `age`）：备份任务里只放公钥；私钥离线保存两份，两名管理员各持一份（§5.3）。攻破 Render 只能拿到公钥，解不开备份。
- **只存哈希**：邀请码、Discord 绑定码、插件令牌（09）。

| 密钥 | 数据密钥在密码保险箱；备份私钥离线两份 | 长期 | — | 每季度核对能取出 |

- **验证 RPO 与 RTO**：B0 前在预发做一次完整恢复演练；W6 用生产的第一份备份再做一次；首批期间每月一次，较大的迁移之后加一次。每次记录实际用时和丢失的时间窗，写回本表。
- **怎样核对、又不读用户内容**：按表比对行数和校验和，再用内部测试账号的一行 `restricted` 数据做解密检查，不查看任何用户内容。生产备份的恢复只在受保护的生产环境里做，临时实例 24 小时内删除，记入发布记录；库外演练在新建的工作区里做，演练完立即删除这个工作区。恢复出的每个新库都先清空 IP 白名单（附录 A-34）。
- **恢复以后**：①核对数据库引用了但 R2 里已经没有的文件，标为「文件已删除」；②重放恢复点之后发生的账号删除（需要保留被删账号的 id 用于重放，待确认 9）；③在发布记录里写明恢复了什么。
- **库外备份是第二道防线**：它防的是托管账号被误删、被盗或托管方事故，不替代 PITR。Render 账号被攻破时，攻击者拿到的只有公钥和一个删不掉、改不了已有备份的令牌（bucket lock），仍可读出密文，但没有离线私钥解不开。

### 4.5 保留期、删除与导出

- **按表的保留期**以 09 第 6 步的表、03 §8.8、04 §4.11、06 §11.3 为准，由 worker 里每天一次的 `retention` 任务执行，**包括 R2 里的文件**。B0 开始后第 30 天（12-23）对话事件就会到期，所以 `retention` 在 B1 前必须上线。
- **账号删除**：`DELETE /account` 级联删除数据库记录、私有文件、外部身份和插件令牌（09 第 8B 步）。删除后数据还会留在：PITR 最长 7 天、库外备份约 15 天、OpenAI 滥用监控日志最长 30 天（零数据保留批下前）、Resend 日志 30 天、Render 控制台日志 14 天和错误追踪 30 或 90 天（都不含内容）。隐私政策据此写「备份滚动保留不超过 30 天」（假设，待确认 14）。
- **我们删不掉或要人工删的**，隐私政策也要写：用户在 Discord 私信里自己发的消息（存在 Discord，只能用户自己删，10 §3.13）；发到 support@、privacy@ 的来信（收到删除请求时人工删除，否则处理完 90 天后删，假设）；蔓藤的意向与订单记录（按数据处理条款删除）；团队频道的事故记录（只有内部 id）。
- **日志**：不含内容（§6.2），保留 Render 控制台 14 天（Pro）加错误追踪 30 或 90 天，写进隐私政策。
- **导出**：`GET /account/export` 自助完成；删除或导出出错，工程 7 天内人工处理（07 §6.4）。
- **预发和开发里没有真实数据**，所以删除范围只是生产、备份和上面列出的处理方。

### 4.6 数据在哪里处理

- 计算与数据库在 Render 美国区，R2 用美国辖区，Resend 的账户数据在美国。
- **OpenAI**：没开驻留时默认是全球处理。美国数据驻留要先找销售确认资格，开了以后按项目配置，要改走 `us.api.openai.com`，不覆盖 system data；2026-03-05 及之后发布的模型加价 10%（附录 A-25）。所以只有在 OpenAI 批准美国数据驻留、项目绑定 `us.api.openai.com`、代码改好（§3.3）之后，模型调用才算在美国处理。获批前隐私政策写「OpenAI（美国公司，处理位置以其政策为准）」，不写「数据只留在美国」。W0 向销售同时申请驻留和零数据保留，两项都可能不批。
- 不用任何中国境内的云或与受关注国家相关的实体处理用户数据；国产语音服务只接收虚构文本（12 §1.2、§6.4）。首批 100 人远低于 28 CFR 202.205 的批量门槛（例如个人健康数据是超过 1 万人，附录 A-29），但门槛按 12 个月累计、多类数据合并计算，律师确认前仍按保守做法执行。
- 身在中国大陆的员工，以及蔓藤运营与复核人员，能否从各自所在地访问含用户数据的界面（安全复核、运营台、意向与订单），由律师确认（待确认 10）；确认前身在中国大陆的人不允许访问。
- 寒假回国期间网页和邮件在大陆能否打开，是可达性问题，不是数据驻留问题：W5 实测，结果写进「回国期间」的帮助说明（10 §1.3）。

### 4.7 蔓藤数据的授权与访问控制

- 生产导入任何蔓藤内容前，要有书面授权，并且含「发送给第三方模型供应商处理」（07 §9 第 4 行；04 M0-2）；没有 `license_id` 不发布。
- 导入、发布、撤回脚本（04 §4.8）在生产上作为一次性任务运行，只有管理员能触发，每次写员工审计和发布记录；编辑与审核不是同一人。
- 蔓藤员工如果担任内容编辑或审核，用单独的员工账号，看不到任何用户的对话、记忆和资料库（04 §4.9）。招募问卷和真人意向只走产品方渠道，蔓藤销售看不到（07 §9 第 14 行）；蔓藤运营看到的意向数据（06 §6.3）不进销售 CRM，由数据处理与保密条款约束。
- **唯一例外是安全复核**：如果 07 待确认 5 指定的复核人来自蔓藤，限定为不参与销售、不担任该用户导师的人员，签保密协议，只看被标记的那一轮及前后各 5 条，不通知蔓藤的销售或导师（02 §10.3）；在隐私政策里写明复核人的身份和这些约束。
- 给蔓藤的报告只用不含 `user_id` 的聚合（n ≥ 3，04 §5.5）。
- 蔓藤 MCP 的服务凭据经密码保险箱的共享条目交付，不经聊天和邮件（04 §6.3）；授权撤回后按墓碑语义停止使用，旧结果不可读（04 §4.12）。

## 5. 安全

### 5.1 鉴权与账号上下文

沿用现有设计（09 §1.5；docs/platform/architecture.md「从本地走向多用户服务」）：会话 cookie 为 HttpOnly、SameSite=Lax、生产 Secure、14 天；学生路由要求 `x-companion-account`；写操作校验 Origin，生产的 `PLATFORM_ALLOWED_ORIGINS` 只有 `https://app.<域名>` 一项；员工路由 `staffOnly` 叠在 `secure` 上并写审计；生产强制邮箱验证。部署相关的要求：入口不剥掉账号头、不缓存私有响应（docs/platform/deployment-plan.md）；员工账号与学生账号分开，不共用账号。

**员工账号**：应用内员工账号目前只有密码，而 safety_reviewer 能看危机对话，ops 能看邮箱和意向。要求（交给 Codex，09 第 8B 步）：B1 前给 safety_reviewer、org_admin、ops 加 TOTP 二次验证，最晚在 B2 前（OPT 待业期用户进入时）完成（待确认 6）；员工会话缩短到 12 小时（假设）；复核人必须签保密协议。补上之前的补偿做法：员工角色只发给具名个人；每次查看写审计，每周复盘（§8.6）；离职 24 小时内收回。

### 5.2 限流与入口防护

- **B0 前修好可信代理**（docs/platform/deployment-plan.md「流式聊天与长任务」）：现在匿名限流按 socket 地址计数，放在 Render 的入口后面可能把所有人算成一个来源，B1 集中注册时会批量返回 429。要按 Cloudflare 加 Render 入口的转发头来验证配置。
- 已登录请求按账号计数；09 第 9、10 步新增 Discord 和插件的 scope；L1、L2 不受任何限流影响（02 §10.3）。被 429 拒绝的消息没有落库、服务端无从分级，所以客户端要显示危机资源卡兜底（§6.4）。
- Render 给所有服务自带 DDoS 防护（底层是 Cloudflare）；Web Service 的入站 IP 规则要 Scale 档，首批不用；不加额外的 WAF（附录 A-36）。

## 6. 可观测性与告警

### 6.1 错误追踪

后端接错误追踪（建议 Sentry，美国区）：关闭默认的个人信息采集，不发请求体、cookie、URL 参数，按发布版本打标签，新错误类型当天看。前端首批只接错误类型和堆栈，不采集页面文本和用户输入。错误追踪属于遥测，要在生产显式打开（AGENTS.md），并写进隐私政策。

### 6.2 日志

现在 API 的请求日志是关着的（`app.ts` 里 Fastify 的 logger 为 false），也没有错误追踪和请求关联 id（docs/platform/deployment-plan.md「监控与发布」）。B0 前打开结构化日志：每条只有请求或任务 id、路由模板、状态码、耗时、错误码、用户 id 的摘要；不记邮箱、正文、URL 参数、请求体、简历、页面内容、令牌（AGENTS.md；07 §7.5）。日志先留在 Render 控制台（Pro 14 天）；需要更长保留时再用日志流转发，转发目的地也要进 §4.3。Render 每个实例每分钟最多处理 6,000 行日志，超出的直接丢弃，也不进日志流（附录 A-15），所以要控制行数：每个请求一行，不打调试日志，SSE 不按事件记。

### 6.3 指标与埋点

- **产品埋点**：07 §7.5 的 `platform_product_events`，白名单事件、只有枚举和数字，在我们自己的数据库里。周一指标周报从这里出（07 §6.5）。
- **运行指标**（由 worker 里的运维自检每分钟算一次，只存数字）：丝滑四项的 P50 与 P95（07 §7.4、15 §1.2：首个可见反馈、主理人第一句、转发卡第一句、后台任务进度间隔）、供应商错误率、队列等待、outbox 最老一条的年龄、晨报准时率、数据库连接数、存储错误数。worker 或数据库出问题时这些会一起失声，所以兜底的告警不能依赖它们（§6.7）。
- **5xx 比例**从 Render 的 HTTP 请求日志（Pro）经日志流算，W4 选定告警工具时确定接法；Render 能否直接对 HTTP 指标告警需核实。
- **Render 自带**的 CPU、内存指标用于扩容判断（§3.1）。

### 6.4 可用性与危机兜底

- **两个接口**：
  - **存活接口**（Render 的 `healthCheckPath`，现为 `/api/platform/health`）：只查进程在、数据库能连上。绝不加入 worker 心跳。Render 在健康检查连续失败 15 秒后停止给 Web Service 路由、60 秒后重启实例（附录 A-8），如果把 worker 心跳放进来，worker 一停，网页和 API 就会被下线并反复重启，S3 的「晨报延迟」放大成全站 S1，L2 模板也发不出去；发布时 worker 重启期间 API 的新实例也过不了健康检查，发布会被取消（infra/platform/production/README.md 也写明不能用它代替 worker 存活告警）。
  - **深度检查接口**（不对外公开参数，只给外部探测和告警用）：outbox 最老一条的年龄、最近一次 worker 心跳时间，以及「L2 模板 dry-run」——只渲染、不写库，确认 `platform_safety_resources` 不为空、`PLATFORM_DATA_KEY` 能加解密一条测试密文。
- **worker 死人开关**：worker 每分钟向外部监控 ping 一次，超时由外部服务直接推送，不经过我们自己的应用。
- **外部探测**：UptimeRobot 付费档（Solo，60 秒间隔，附录 A-27）探测存活接口和深度检查接口。
- **生产危机路径自检**：每次发布后和每天一次，用标记为内部测试的账号跑一条 L2 用例，确认 2 秒内收到模板和资源卡；结果不进复核队列、不进统计；成功后向外部监控 ping 一次，失败或没有 ping 按 S1（§6.7）。
- **客户端危机资源卡**：网页只有 1 个实例，数据库不开高可用，L2 模板又由 API 同步写进 Postgres，所以 L2 依赖 Render 和数据库；发消息请求如果先被 429 或 5xx 拒绝，消息根本没有落库。因此在 PWA 预缓存的公共外壳里（10 §2.4）放一份静态危机资源卡（988 / 911 / 741741，加「查找本校心理咨询中心」）：发消息遇到网络错误、5xx、429、503 或离线时，在客户端直接显示，不依赖服务端（交给 Codex，B0 前）。
- **状态页**：用探测工具的状态页，只显示「正常 / 部分不可用 / 不可用」，说明文字固定带危机资源（「需要紧急帮助时不要等我们：拨打或发短信 988，紧急情况拨 911，或发短信 HOME 到 741741」）；地址写在登录页和邮件页脚。

### 6.5 费用

- **应用内**：CostGuard 的按用户周上限（首批软上限 $8 只通知运营，硬上限 $15 才限制，06 §12.3）和全站预算（09 第 8 步）。
  - **全站日预算**用动态值：剩余月预算 ÷ 当月剩余天数 × 1.5（月初约 $75）；CostGuard 做不到时固定 $50。固定 $100 × 30 天超过月预算，起不到控制花费速度的作用。日预算到 80%、100% 都只告警，不拦截。
  - **全站月预算**到 50%、80% 告警；到 100% 只放行必要调用。必要调用的范围与 06 §12.3 一致：首批到硬上限时保留的主理人简短对话、查看与确认已有内容、记忆管理和危机流程，加上「永不降级或拦截」的已生成内容的确认与发出、记忆的查看、修改、删除和导出。
- **供应商侧**：OpenAI 项目设硬性花费上限 $2,000（假设），作为最后一道。到达后返回 429，code 是 `project_spend_limit_exceeded` 或 `organization_spend_limit_exceeded`；拦截不是即时的，可能少量超额（附录 A-37）。应用把这两个 code 当作供应商不可用，如实提示、不重试（交给 Codex，§3.3）。
- **托管侧**：每月看 Render（含 bandwidth）、Cloudflare、Resend 账单，和 §9 对照；差距超过 30% 时复盘。

### 8.3 事故处理流程

1. **发现**：告警、用户反馈或员工发现，先在团队私有频道开一条事故记录（只写内部 id，不写邮箱和内容）。
2. **定级**：工程值班按上表定级，S1 立即叫产品负责人。
3. **止血**：优先用下表的开关，其次回退版本，最后才在生产上改数据。
4. **告知**：按上表告知用户；对用户的说明不写供应商名和模型名（07 §3.16），不说没有核实的话（例如「数据没有丢」只在核实后才写）。
5. **修复**：修复走 PR 和预发；紧急修复也要在预发跑冒烟检查。
6. **复盘**：S1、S2 在 5 个工作日内写无责复盘：时间线、影响了谁、根因、后续动作和负责人；S1 的复盘给法务一份。

**改开关的动作**都是：在共享环境组改值 → API 和 worker 各手动部署一次（同一 digest，不重新构建）→ 新实例过了健康检查后确认生效，在事故记录里写时间。只改值不部署，开关不会生效（§2.4）。这套动作在预发演练时计时（W3）。**回退后**马上逐项核对开关值，不一致就重设并再部署（§2.3）。

| 情况 | 开关或动作 | 影响 | 谁能操作 |
|---|---|---|---|
| 模型费用异常或供应商事故 | `PLATFORM_ALLOW_PROVIDER_CALLS=0`，两个角色各部署一次 | 对话如实显示暂时不可用；危机分级退回关键词，L2 模板照常 | 工程值班，事后告知产品负责人 |
| 某个功能出错 | 关掉对应的 `PLATFORM_FEATURE_*`，两个角色各部署一次 | 该功能隐藏 | 工程值班 |
| Discord 出问题 | 暂停 Discord 进程 | 主动消息退回网页（10 §3.12） | 工程值班 |
| 插件出问题或平台要求停止 | 签名策略包按域名远程关停（11 §5.1） | 该域名不再自动操作 | 工程值班，产品负责人知情 |
| 坏版本 | 回退（§2.3），之后核对开关 | — | 工程值班 |
| 隐私事故 | 停发邀请码；必要时开维护模式 | 维护页带危机资源 | 产品负责人 |

### 8.4 对用户的故障说明

- **S3**：沿用产品内已有的如实提示（「暂时不可用，已经退回文字」之类），由系统通知说，不由主理人说（06 §12.3 的提示原则）。
- **S1、S2**：状态页加邮件。模板：「{开始时间} 起，{功能} 暂时不可用，我们正在处理，{时间} 前会再更新。需要紧急帮助时不要等我们：拨打或发短信 988，紧急情况拨 911。」网页打不开时，PWA 外壳里的危机资源卡和状态页的固定说明是用户能看到的全部（§6.4）。
- **恢复后**：在下一封版本说明里写清发生了什么、影响了什么、我们改了什么（07 §8 第 4 条）。
