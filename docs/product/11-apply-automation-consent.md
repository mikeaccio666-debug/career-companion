# 插件自动投递：逐项授权方案

> 这份文档回答什么问题：浏览器插件要不要继续替用户自动做事、哪些事交给用户逐项授权、默认值是什么、哪些底线不碰，以及 Codex 需要改哪些代码。
>
> 2026-10-06 · 产品负责人已确认方向：插件保留并尽可能自动，授权改为逐项由用户决定。授权清单的默认值仍待确认（见第 1 节末尾）。
>
> 依据：自动投递产品调研、插件代码梳理、法律风险分析三份材料，以及对它们的核实结论（有出入的地方以核实结论为准）。文中的法律内容不是法律意见，上线前须请美国执业律师审核，需要问的问题列在第 7 节。

## 1. 结论

**同意你的判断：插件保留，继续尽量替用户做事。** 在弄清楚能不能像 Muse 一样投递之前，插件是我们手里唯一现成的提效工具。所以不建议按 `01-vision-and-users.md` §8.2 早期的写法把代签、代注册登录、自动翻页「删除或永久关闭」。要改的是授权方式：把 2026-09-28 那一句话同意、一次放开 20 类的做法，换成**首次使用时完整问一遍，每一类由用户自己选「自动 / 每次问我 / 永不」**。

这样改，效率损失很小，原因有两点：

- 选了「自动」的类别，照旧一键完成，和现在一样。
- 「每次问我」不需要用户自己去网页上找、去勾。插件填到那一项会停下，在浮层里显示原文和白话说明，用户点「同意」或「不同意」，插件替他点。推荐「每次问」的几类（仲裁、背景调查、AI 面试等）在申请表里出现得不多，背景调查多数在拿到 offer 之后才出现。

评估结果如下。

| 处理 | 能力 | 理由（一句话） |
|---|---|---|
| **保留，逐项授权，推荐「自动」** | 申请条款与隐私（含 Jobvite 的数据同意页）、属实声明与签名栏、at-will 确认、核实学历经历与 E-Verify 告知、日后联系与人才库、自动翻页（advance-steps） | 几乎每份申请都有，风险低。只要内容来自用户确认过的资料、最终提交由本人按，代勾的行为能清楚地归属到用户本人。 |
| **保留，逐项授权，推荐「每次问我」** | 仲裁协议、集体诉讼与陪审团弃权、背景调查与各类筛查（信用、药检、犯罪记录、驾驶记录、社交媒体）、AI 面试录音与 AI 评估、申请相关的短信与电话通知 | 放弃诉讼权利、被查信用、被录音评分，都是用户应当知情的事。FCRA 等法律的本意就是让本人授权。这几类出现频率低，问一下几乎不耽误效率。 |
| **保留，照用户资料作答** | EEO 自愿问卷、标准的工作授权与担保（sponsorship）题、能否联系现雇主或推荐人 | 已经是「用户答一次、插件照抄」的形态，和新方向一致。 |
| **保留但要改造** | ① 代注册登录：从条款同意里拆出来，单独一问；共用密码改为**每家网站一个独立的随机密码**，用户也可以改选自己设的统一密码 | 一个密码走遍所有招聘网站，任何一家泄露就全部失守。保险箱本来就按网站存密码，改动小。 |
| | ② 工作授权的「别国默认答」：资料里没有某个国家的记录时，现在默认答「有权工作、不需担保」。改为用户明确选择，推荐「每次问我」 | 对 F-1/OPT 学生，申请加拿大、英国等岗位时，这可能是在正式申请里作出的不实陈述，后果可能是被撤 offer。 |
| | ③ 营销信息：去掉「自动」选项，只留「每次问我 / 永不」 | 对用户没有好处。营销短信按 TCPA 需要本人签署的书面同意，插件代勾很难满足。 |
| | ④ 一句话里捆了好几项的同意（COMBINED_CONSENT）：按里面每一项各自的选择合成 | 现在代码只知道「这是混合」，不知道混了哪几项。逐项授权后必须拆开判断。 |
| | ⑤ Workday 注册页的条款勾选框：插件现在只读到「I agree」几个字，要改为读到旁边的条款正文再决定 | 正文里如果藏着营销或其他授权，现在会被一起勾上。 |
| | ⑥ 已同意 09-28 版的老用户：不自动转成「全部自动」，下次使用时补答问卷，补答前各项按「每次问我」 | 旧的一揽子同意不能当作逐项授权；但插件照常填写，不会打断投递。 |
| **永远由本人操作（底线）** | 最终提交；LinkedIn 站内的任何自动操作，以及 Indeed Apply 的自动化；验证码、人机验证、单点登录；「是否美国公民或绿卡持有人」答「是」；政府职位的属实声明；生物特征、出售资料、免责与赔偿、竞业与保密、医疗健康类授权；在服务器或云端后台代投 | 依次对应：执行边界，而且本人那一下点击是代勾归属于他的最强证据；平台条款明文禁止，有封号风险；绕过验证有法律风险；虚称美国公民可能导致永久不可入境；美国联邦虚假陈述罪；法律要求本人签署，或对用户明显不利；违反 AGENTS.md 现有的执行边界，要做须由你明确改方向。 |

需要你拍板的五件事：

1. 你说的「Muse」是不是 Meta 在 9 月 8 日发布的 Meta Muse（见第 2 节）。
2. 第 3 节的推荐默认值是否同意，尤其是两处取舍：「属实声明与签名」推荐自动，「申请通知短信电话」推荐每次问。
3. 是否考虑云端或后台代投。要做的话，需要改 AGENTS.md「不后台提交申请」这条边界。本方案不依赖这一条。
4. 授权记录存在哪里。现在的同意记录存在旧 argoland 后端，而 AGENTS.md 要求新产品不依赖旧 Argoland 的架构，所以建议放进 `services/platform-api`。
5. 批量预填（第 5 节的效率补偿）每天的上限。产品文档里写的是每天新增待确认的投递不超过 10 条，当时标的是假设。

还要说明一个法律上的区别。美国电子签名法（ESIGN）只规定：用了电子代理不影响效力，前提是代理的行为能归属到本人。它并不要求逐类授权。逐类授权是我们为了让归属清楚、减少争议而做的产品选择。它同时也符合加州隐私法（CPRA）对「同意」的要求：不能捆绑，不能预先勾好。CPRA 是否适用于我们要看公司规模门槛，但按它的标准设计更稳妥。

## 2. Muse 是什么、怎么投递

### 2.1 最可能是 Meta Muse，但请确认

| 候选 | 是什么 | 可能性 |

| **Meta Muse** | Meta 于 2026-09-08 发布的个人 AI 代理。先在美国上线（iOS、Android、muse.ai，也能在 WhatsApp 里用），9 月 18 日前后扩展到加拿大（墨西哥只见于部分媒体报道，未经官方证实），之后又发布了 Muse for Mac。上线一周登上美国 App Store 免费榜第一。 | 最高。时间和话题都对得上；仓库里的 `docs/automation-options-research.md`（10-05）也是按它理解的。 |
| Manus | Meta 于 2025 年 12 月收购的 AI 代理公司。有一个 Browser Operator 插件，在用户自己的浏览器里执行任务。 | 中。如果你看到的是「装个插件、在自己浏览器里跑」的演示，可能是它。 |
| The Muse（themuse.com） | 纽约的职业内容和招聘网站。 | 低。没有任何自动投递功能。 |

想跟你确认三个问题：

1. 你说的是哪一个？在哪里看到「Muse 投递」的（Reddit 帖子、朋友演示，还是媒体报道）？
2. 你最想要它的哪一点：关了电脑也能投、不用装插件，还是连提交都不用自己点？
3. 你看到的效果有没有数据，比如投了多少份、拿到多少面试？

### 2.2 Meta Muse 怎么投递

- **云端独立电脑。** 每个用户有一台云端虚拟机（Muse Secure VM），里面有自己的浏览器，能打开网页、填表、发邮件、结账。用户关掉 App 后，它会继续干活。
- **独立审批员。** 同一台机器上有一个和 Muse 隔离开的 Sentinel 进程。Muse 所有发往网络的动作都要它判定：允许、拒绝，或者问用户。判为「问用户」时，生成一个待批准项，暂停执行。发邮件和购买之前一定先问。结账页每次都要人工批准，前提是网站上已经存了支付信息、浏览器也识别出这是结账页。
- **凭据隔离。** 账号密码存在单独的凭据服务里，Muse 只能拿到一个替代令牌，真正发请求时才由 Sentinel 换成真密码。
- **没有专门的求职功能。** Meta 的官方公告里没有求职投递流程。「Muse 自动投递」来自一位 Reddit 用户的个人说法，Tom's Guide 在 2026-09-30 转引过：他从 9 月 14 日起让 Muse 每个工作日找岗位、按岗位改简历、填表并提交。看起来这是用户用通用的浏览和填表能力自己搭的流程，没有经过验证，也没有成功率数据。中文支持情况不明。
- **已知问题。** Meta 自己承认，提示词注入攻击（网页里藏的文字诱导代理做别的事）仍未解决。有媒体报道，内部测试中出现过绕过护栏、反复被登出、运行 15 分钟后停止刷新页面等问题。

|---|---|---|---|---|---|

两条外部约束：

- **平台条款。** LinkedIn 禁止任何第三方插件在它的网站上自动操作，违者可能被限制或封号。Indeed 在 2026-09-29 的条款里禁止在官方渠道之外自动化 Indeed Apply。
- **招聘系统在识别自动投递。** Greenhouse 用隐形 reCAPTCHA 分析鼠标和打字节奏，有时会要求邮箱验证码。Ashby 看设备、IP、邮箱、电话。Workable 会给自动化工具投来的申请打上「AI 辅助」标签，雇主可以一键筛掉。目前多是打标签、转人工复核，而不是直接拒绝。云端代投（机房 IP、没有真人操作轨迹、频率高）比本地插件更容易被识别。

### 2.4 我们能做到多接近

| Muse 的能力 | 我们现在 | 本方案之后 | 再往前一步需要什么 |
|---|---|---|---|
| 关掉 App 也继续干活 | 不能。需要用户电脑开着、浏览器开着 | 不变 | 服务端排队、等用户电脑在线时由插件执行（Manus 的做法）；或者用云端浏览器（要改执行边界） |
| 自己点提交 | 用户在浮层点一下（5 家招聘系统），其他家要到网站上自己点 | 同上，并扩大能在浮层里提交的网站 | 你决定修改 AGENTS.md「不后台提交申请」 |
| 独立审批，分三档（允许 / 拒绝 / 问用户） | 一句话全开 | **逐项三档：自动 / 每次问我 / 永不** | — |
| 凭据隔离 | 本机加密保险箱，所有网站共用一个密码 | 每家独立密码，仍然只存在本机 | 接入 1Password 等密码管理器（可选） |
| 审计记录 | 浮层当场写「已替你…」，不留存 | 每份申请一张回执，可以查看、导出 | — |
| 以谁的身份上网 | 用户自己的浏览器、IP 和已有登录。这是优势：不容易被识别 | 同上 | 云端方案会失去这个优势 |
| 求职专业能力 | H1B 担保过滤、各招聘系统的填写规则、主理人陪伴、蔓藤资源 | 同上 | Muse 是通用工具，没有这些 |

结论：除了「关电脑也能投」和「连提交都不用点」，Muse 的其他做法我们这次都能做到。逐项授权本身就是 Muse 那套「允许 / 拒绝 / 问用户」的求职版。剩下两点都要改执行边界，还会带来被识别和替用户托管密码的风险，建议等你确认 Muse 指的是什么、最想要哪一点之后再单独评估。

## 3. 授权清单

### 3.1 三个选项的含义

- **自动**：插件直接替你勾选、选择或填写，投递后在回执里告诉你做了什么。
- **每次问我**：插件填到这一项停下，在浮层里显示原文和白话说明。你点「同意」或「不同意」，插件替你点。同一份申请里，同一段文字只问一次。
- **永不**：插件不替你同意。能拒绝的（比如可选的营销订阅），替你保持不勾，或选「No」；必须同意才能继续的（比如仲裁是申请的前提），交给你自己在网页上决定。

所有问题初始都不预选。表里的「推荐」只在问卷里显示成一个标签。**没回答的一律按「每次问我」处理**；读不到授权记录、版本对不上，也同样按「每次问我」。这样既不会在用户没看过的情况下替他同意，也不会因为他跳过问卷就让插件停下来不干活。

### 3.2 代签与同意类（sign-on-behalf）

| # | 用户看到的问题 | 对应的类别 ID | 可选项 | 推荐 | 风险说明 | 法律依据要点（需律师审核） |
|---|---|---|---|---|---|---|
| Q1 | **申请条款与隐私**：申请表要你同意这家公司的申请条款、隐私政策，或者同意他们和他们的招聘系统服务商为这次申请处理你的资料时，我可以替你勾选吗？（进入申请表之前，要先选居住地对应隐私条款的页面，也算在内） | `TERMS_CONSENT`、`PRIVACY_NOTICE_TITLE`、`RECRUITING_DATA_SHARING`；Jobvite 数据同意页（`consentGate`） | 自动 / 每次问我 / 永不 | 自动 | 风险低，几乎是申请的前提。句子里一旦混进出售资料、为营销分享、仲裁、营销订阅，就改按对应那一问的选择处理，或者交还本人。只有标题、读不到正文的隐私声明，也会一并确认。 | 雇主按 CCPA 本来就要向求职者提供收集告知；CPRA 规定，捆绑在宽泛条款里或通过暗黑模式取得的同意无效（Cal. Civ. Code 1798.140(h)）；代勾行为能归属本人时有效（ESIGN 7001(h)、UETA §14）。 |
| Q2 | **属实声明与签名**：申请表最后要你声明「以上信息真实完整」，并在签名栏输入姓名和日期时，我可以替你填吗？（只在表上的内容都来自你确认过的资料时才会自动填；签名栏只填你的法定全名） | `TRUTH_ATTESTATION`、`SIGNATURE_NAME`、`SIGNATURE_DATE` | 自动 / 每次问我 / 永不 | 自动（有条件） | 替你签名，在法律上等同于你本人签字；内容不实可能导致被撤 offer 或解雇。表上有你没看过的 AI 生成回答时，这一份申请自动改为「每次问我」。政府职位一律交还本人。 | ESIGN 7006 要求电子签名有「签署意图」，你没见过具体文书时是否成立有争议；政府职位适用 18 U.S.C. 1001（联邦虚假陈述罪）。 |

## 4. 授权体验设计

### 4.1 什么时候问

- **主路径：第一次使用前完整问一遍。** 用户第一次点「自动填写」之前（或者在网页的资料页里），弹出「投递授权」问卷。大约 15 个问题，分三组，预计 3 分钟左右。这就是你说的「完整问一遍」。
- **可以先跳过。** 用户点「稍后再答」也能马上开始投递：没答的项都按「每次问我」处理，插件照常填写其他字段，遇到这类项时在浮层里就地问。就地问的卡片上有一个「以后都这样」的勾选项，勾上就把这次的回答存为这一类的设置。
- **新增问题或问题改版时**，只就那一问在第一次遇到时就地问，不重做整份问卷。
- **问卷可以在网页上答，也可以在插件里答。** 但「每次问我」的那一下同意，必须在插件浮层里、在那一页上点，因为插件需要一次真实点击作为凭证（AGENTS.md：手机上审阅不等于插件收到了可信点击）。所以手机和 Discord 上只能改设置，不能替某一份申请点「同意」。

### 4.2 怎么分组，让用户不嫌烦

| 组 | 组名 | 包含 | 交互 |
|---|---|---|---|
| 一 | **放心交给我** | Q1–Q5、自动翻页、EEO 照填、标准工作授权题 | 每题一行，显示「推荐：自动」标签。组上方有一个「这一组都选自动」按钮，点了会把每一项都填成「自动」，并逐项显示出来，每项都还能单独改。这个按钮是否算暗黑模式，需要律师确认（第 7 节）。 |
| 二 | **每次问我** | Q7、Q9–Q13、代注册登录、其他国家的工作授权 | 没有整组按钮，必须逐题选。每题下面有一行白话后果说明，例如「同意就等于放弃上法院的权利」。 |
| 三 | **只能你自己来** | 第 5 节的底线 | 只读说明，告诉用户插件永远不会做哪些事、为什么。不需要做选择。 |

每一题的展示方式：

- 一句中文问题，加一行白话后果。
- 「看看英文原文长什么样」可以折叠展开，给出一两句典型的英文原句。
- 固定一句提示：「插件替你勾选，在法律上等同于你本人勾选。」
- Q12、Q13 选「自动」时，弹出单独一屏做二次确认。

Q6（能否联系现雇主）和 Q8（营销信息）放在第一组的末尾，不受「这一组都选自动」按钮影响：Q6 需要用户给出答案，而不是选托管程度；Q8 没有「自动」选项。

### 4.3 随时修改

- 网页资料页和插件资料编辑器里都有「投递授权」一节，每一问一个三段开关（做法参照现在 EEO 的分段控件）。改了立即生效。
- 浮层里每张「已替你…」或「每次问我」的卡片上，都有一个「改设置」入口，直接跳到对应那一问。
- 用户在小组里跟主理人或投递官说「以后仲裁都先问我」，投递官回一张确认卡片，用户点了才生效。聊天本身不改设置。
- 撤回只对以后的申请有效，已经提交的申请改不了。这一点要在设置页写明。

### 4.4 版本化

- **每一问单独有版本号**（`wordingVersion`）。某一问的文案或范围变了，只重问那一问，其他答案照旧有效。这比现在「整份同意书升版本、全部作废」更细。
- **放宽了才需要重问。** 「范围」包括内核的匹配规则：如果某一类的判据放宽了（能认出更多种句子），那一问也要升版本。收窄（插件少做事）不需要重问。
- 插件读到不认识的版本、比自己更新的版本，或者读取失败，都当作「每次问我」，不当作「自动」。
- 每次回答都作为一条事件保存：谁、什么时候、哪一版文案、选了什么、在哪里选的（网页还是插件）。保存方式是追加记录，不覆盖旧记录，以便事后查证。

### 4.5 每次投递后的「替你做了什么」回执

- **提交之前**：提交卡片上先列出这份申请里插件替你做的事。点「提交」就表示你确认了这些。
- **提交之后**：每份申请一张回执，分五块：替你同意了什么、替你拒绝了什么、问过你的、留给你自己的、替你注册或登录了哪个网站。每一条都可以展开看原文快照、网址、时间，以及当时依据的是哪一问、哪一版设置。
- **存储**：原文快照属于用户自己的数据，默认只存在本机的插件里；后端只存原文摘要（hash）、类别、决定和时间。快照不进日志、不进诊断（AGENTS.md 规定原始页面不得进日志）。是否同步完整快照，由你和律师决定。
- 回执在设置里可以查看、导出。

### 4.6 投递官在小组里怎么汇报

投递官每天一条，只说结果和待办，不贴原文。原文和细节放在插件或网页的回执里。例如：

> **投递官**：今天准备的 5 份都已经填到检查页。Acme 和 Globex 两份你已经提交了，我替你同意了这两家的申请条款和隐私政策，也替你签了属实声明（内容都来自你的资料）。Initech 那份有一份仲裁协议在等你决定，原文和白话解释我放在插件里了。Umbrella 要先注册 Workday 账号，你点一下我就去注册。

- 有「每次问我」的项在等待时，投递官在小组里提醒一次，不重复刷屏。
- 遇到插件替不了的情况（验证码、网站报错、LinkedIn 的岗位），说清楚要用户做什么。
- Discord 上的镜像消息与此相同，不带密码、原文和其他个人资料。

## 5. 底线与效率补偿

### 5.1 无论用户怎么选，插件都不做的事

| 底线 | 理由 |
|---|---|
| 不经用户点击就按下最终提交 | AGENTS.md 的执行边界。用户本人点的那一下，也是整张表、包括所有代勾归属于他的最强证据。 |
| 在服务器或云端后台代投 | 违反 AGENTS.md「不后台提交申请」；机房 IP 更容易被识别；还需要托管用户密码。要做，须你明确改方向。 |
| LinkedIn 站内的任何自动操作，以及 Indeed Apply 的自动化 | 平台条款明文禁止，用户有被限制或封号的风险。运行时策略的 `deniedHostSuffixes` 默认包含它们，插件本地也要写死，不能由远程开关打开。 |
| 绕过验证码、人机验证、邮箱验证、单点登录，或者处理账号被锁 | 绕过访问控制有法律风险（CFAA、合同）。现有代码已经交还本人，保持不变。 |
| 「是否美国公民或绿卡持有人」答「是」 | 虚称美国公民可能导致永久不可入境。 |
| 政府职位（USAJOBS、州和市政府招聘站点）上的属实声明和签名 | 适用联邦虚假陈述罪（18 U.S.C. 1001）。 |
| 生物特征（人脸、声纹）同意；出售资料或为营销分享；免责、不追责、赔偿；竞业、不招揽、保密；医疗健康与残障信息；调查式消费者报告 | 有的法律要求本人签署，有的对用户明显不利。现有的 `KEPT_REFUSALS` 已经拒绝，保持不变。 |
| 用 AI 编造或推断经历、学历、日期，再替用户签属实声明 | 这对 F-1 学生是实质性的不实陈述；JobCopilot 的差评主要就集中在这里。 |
| 批量建号，或用用户本人以外的邮箱注册 | 违反 ATS 条款；也是招聘系统识别的重点。 |
| 密码离开用户这台电脑 | 现有设计如此，保持：不进 API、日志、诊断。 |
| 收到平台的停止通知后继续访问该平台 | 按 Power Ventures 案，平台发出停止通知后，即使有用户许可，继续访问也可能违反 CFAA。必须能按域名远程关停。 |

### 5.2 效率上的补偿

1. **「每次问我」做成浮层里一键。** 不需要用户自己去网页上找勾选框；同一家公司同一段原文（按摘要识别），可以选择「这家以后都这样」。
2. **批量预填队列。** 投递官选出当天的岗位后，插件依次打开、填好、翻到检查页，停在提交前。用户逐份看一眼、点提交即可。需要设每天上限和操作间隔，遇到验证码或拦截就退回给用户（借鉴 Jobright）。这是 L3 的一个不含提交的版本，需要你同意。
3. **扩大能在浮层里提交的网站。** 目前只有 5 家声明了提交按钮（`finalSubmitControl`），Ashby、Lever、Workday 等都没有，用户只能到网页上找按钮。给这些网站补上声明后，提交仍然是用户点，但少一步。
4. **自动翻页默认推荐开启。** Workday 这类多页申请表，用户点一次就能连续填到检查页。
5. **代注册之后自动登录。** 每家只在第一次注册时问一次，以后登录不再打扰用户。
6. **在 Greenhouse 托管页上，提示已经在用 MyGreenhouse 的用户直接使用它。** 那是平台自己的自动填写，不涉及第三方条款问题。

## 7. 需要律师审核的问题

1. 用户事先逐类授权、插件替他勾选，能否让这些勾选在法律上归属于用户（UETA §9、代理法）？用户没看过具体文书时，是否满足 ESIGN 对电子签名「签署意图」的要求？
2. 求职申请算不算 ESIGN 和 UETA 意义上的「交易」（transaction）？
3. 属实声明与签名栏推荐「自动」，前提是表上内容全部来自用户确认过的资料、最终提交由本人点击。这些条件够不够？政府职位的识别范围应该划到哪里？
4. FCRA：用户事先授权、插件代勾背景调查授权，是否满足「书面授权」？如果允许用户选「自动」，我们还需要额外告知什么？加州 ICRAA 的报告副本勾选框按用户偏好填写是否可以？
5. 仲裁与陪审团弃权：允许用户选「自动」（加二次确认）是否可行？加州等州对争议前放弃陪审团有什么特别规定？代勾以后，我们会不会被卷入争议，成为证人或被告？
6. TCPA：申请相关的自动拨号和预录电话，「事先同意」由插件代勾是否有效？营销类去掉「自动」是否足够？各州的 mini-TCPA（如佛罗里达）有什么额外要求？
7. AI 面试：在伊利诺伊、马里兰、加州等州的法律下，求职者事先授权第三方插件代表他同意录音或 AI 评估，是否有效？
8. 工作授权：「我在这些国家也有工作权利、不需要担保」由用户选定后自动作答，是否足以把陈述责任落在用户身上？「公民身份题永不答是」之外，还有哪些题必须每次问？
9. 平台条款：除了 LinkedIn 和 Indeed，雇主自己的 Workday 招聘站、Greenhouse 托管页、Lever、Ashby 的候选人条款是否禁止插件自动化？我们作为工具提供方，是否可能面临「干扰合同」等主张？收到停止通知后的处理流程应该怎么定？
10. 代注册账号：以用户名义接受招聘网站条款，效力和风险如何？MyGreenhouse 禁止自动化手段的条款，是否也适用于 Greenhouse 托管的申请页？
11. CCPA/CPRA：我们是否达到适用门槛？问卷的设计（无预选、第一组有「这一组都选自动」按钮）是否构成有效同意，会不会被认定为暗黑模式？保存原文快照、EEO 答案、身份信息时，需要怎样告知、怎样存储？
12. 授权界面、浮层提示、回执的文案审核；撤回的效力和范围。
13. 用户协议里应如何约定插件代勾行为的责任分担。
14. 如果将来做云端代投（Muse 那种），CFAA 风险和合同风险会怎样变化？Amazon v. Perplexity（第九巡回，2026-08-04）的结论依赖「经由用户电脑访问」这一事实。
