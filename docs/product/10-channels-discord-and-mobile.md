> 状态：修订 v2（2026-10-06），依据简报 v3 与跨文档裁决；产品事实来源，Codex 按此实现，分期以 07 为准。平台政策核实于 2026-10-06（见文末），查不到原文的写「需核实」。不是法律意见。

## 这份文档回答什么问题

1. 每个渠道负责什么、哪一期上线；回国或旅行时怎么办。
2. 手机网页与 PWA：安装、离线、Web Push。
3. Discord 私信机器人（P1-2）：绑定、呈现、关键时刻、命令、绝不发的内容、频率、失败、解绑。
4. Discord 第二阶段（P2）与私有 thread 的隐私问题。
5. Web 与 Discord 是否同一条对话；其他渠道与 App 路线。

**结论**

- 网页就是完整产品（P0），手机用手机优先网页加可安装 PWA。P0 唯一的主动触达是晨报邮件提醒（只有链接）；Web Push 在 P1b（P1-14）。
- Discord 私信机器人在 P1a（P1-2），是陪伴与提醒渠道：与网页同一条小组对话、同一份记忆、同一个主动额度；看全文或对外发出的一律回网页。
- Discord 里只出现 `normal` 级内容（03 §8.5），每条消息过模板白名单或出口检查，主动消息不用 `sensitive` 记忆；危机流程与网页一致，掉线、限流、预算都拦不住。
- 多身份群聊与社区服务器在 P2：默认 D（社区只放公共内容），可选 C（用户自己的私人小组服务器），不推荐蔓藤服务器私有 thread。
- 不做原生 App；Capacitor、短信、微信评估在 P2；iMessage、Telegram、WhatsApp 不做。

技术实现见 09。示例里的「墨」是周一然给主理人起的名字（02 §14.1）。队员示例按 07 分期：P0、P1a 只有主理人、前、投、面；规、教 P1b 起；脉 P2 起。

## 1. 渠道策略

### 1.1 渠道分工与分期

| 渠道 | 能做 | 不能做 | 分期（07） |
|---|---|---|---|
| 网页（桌面与手机，可装成 PWA） | 全部，包括在手机上确认待确认 | — | P0（P0-4）；Web Push P1b（P1-14） |
| 晨报邮件提醒 | 「晨报写好了」加链接，可关 | 正文、按钮 | P0（P0-6，07 §1.3 第 4 条） |
| Discord 私信机器人 | 聊天、晨报和三件事、低风险按钮、待确认摘要 | 确认对外发出、看简历和身份信息、替插件点同意、语音 | P1a（P1-2） |
| Discord 社区服务器；私人小组服务器 | 同期伙伴、蔓藤导师答疑；队员各自发言 | 承载个人小组对话；私信以外的内容 | P2 |
| 短信、微信；Capacitor 包壳 | 低频提醒、微信单独评估（第 6 节）；原生推送和麦克风（第 7 节） | 对话 | P2 |

### 1.2 三条跨渠道不变的规则

- **一个小组。** 同一个主理人、同一条小组对话、同一份记忆、同一组待确认对象（第 5 节）。
- **一个额度。** 主动消息额度跨渠道合计，一条主动消息只投递到用户选的一个渠道（02 §9.1）。
- **对外动作回网页。** 要发给别人的消息和材料，都先进待确认，只在网页上看完整版、点「确认这一版」；表单里哪些项可以替你做，由你逐项设定（见 11）；最终提交永远由你本人点。插件「每次问我」的同意只能在插件浮层里点（11 §4.1）。

### 1.3 回国或旅行

Discord 在中国大陆无法直接访问，Android 上 Web Push 依赖的推送服务通常也连不上（需实测）；发往 Discord 的消息照样「投递成功」，系统察觉不到。寒假又正是练面试的时间。所以：

- **时区变化**：网页每次打开时比较浏览器时区和设置里的时区，不一致就在「今天」页问一次：「你换时区了吗？晨报按新时区发？」[按新时区] [不用，很快回去]。同一组时区只问一次。
- **「回国期间」开关**（我 → 渠道与提醒）：用户设起止日期；期间 `proactive_channel` 临时为 `web`（可同时开邮件提醒），到期自动改回，并在改回后的第一封晨报里说「你回来了，晨报回到 Discord」。
- **提示**：Discord 连续 7 天没有任何互动（无 `brief_engaged`、无消息）而网页上有活动时，「今天」页提示一次这个开关。
- **实测**：网页和邮件提醒（含常用邮箱）在大陆的可用性列入 07 §9 上线前清单。

## 2. 手机优先的网页与 PWA

PWA 现状以 docs/platform/mobile-web.md 为准：`/sw.js` 由 `vite-plugin-pwa` 的 Workbox `generateSW` 构建生成（`apps/web/vite.config.ts`、`apps/web/pwa-build.ts`），原手写 `apps/web/public/sw.js` 已删除；192/512 PNG、maskable、180 Apple 图标已有；真机安装和 HTTPS 麦克风待设备测试。

### 2.1 手机网页的要求

手机布局见 08，逐屏流程见 05。渠道相关的三条：

- 待确认的完整内容（含简历差异）在手机上必须能看完、能确认。
- 每个界面和待确认对象都要有稳定 URL（现在 `apps/web/src/App.tsx` 用 `useState` 切页面，没有路由）。路由只在 05 §0.3 定名；本文用到的深链：`/today`、`/group`、`/pending`、`/pending/:id`、`/journey`、`/me/memory`、`/me/channels`、`/me/apply-consent`、`/interview/new`、`/interview/:sessionId`，可带 `?from=discord|push|email` 统计。`services/platform-api/src/static-web.ts` 对无扩展名的导航已回 `index.html`。
- 深链**不带任何登录凭证**（会被转发、截图、生成预览）。会话过期先登录，再回原链接；窗口账号与登录账号不一致时先显示「确认账号」（`x-companion-account` 规则，09 第 4 步）。

### 2.2 安装引导

不在首次访问时提示。第二天再次打开或接受了第一份三件事后，「今天」页顶部出现一次可关闭的提示条；点「不用了」后 30 天内不再提示（假设）。已以独立窗口打开（`display-mode: standalone` 或 iOS 的 `navigator.standalone`）的不提示。

| 平台 | 提示条 | 引导 |
|---|---|---|
| Android Chrome | 「把小组放到桌面，像 App 一样打开。」[安装] [不用了] | 调起 `beforeinstallprompt` |
| iPhone | 「把小组添加到主屏幕，打开更快。」[怎么添加] [不用了]（P1-14 后才加「还能收到晨报通知」） | 图示「分享」→「添加到主屏幕」→ 保持「作为 Web App 打开」（iOS 26 起默认）；其他浏览器没有这一项时提示改用 Safari（需实测） |
| 微信等应用内浏览器 | 「这里装不了，也收不到通知。请在浏览器中打开。」[复制网址] [关闭] | 关闭后本次会话不再出现 |
| 桌面 | 不主动提示，「我 → 渠道与提醒」里有说明 | — |

### 2.3 Manifest 与图标

- `apps/web/public/manifest.webmanifest`：`name`「Openfield — AI workspace」和英文 `description` 改为正式产品名（待确认问题 2）；`theme_color` `#174d43`、`background_color` `#f7f8f2`（鼠尾草绿与奶油底）改为 08 的 ink、paper；加 `lang: "zh-CN"` 和 `shortcuts`（今天、待确认、对话）。PNG 图标已齐，品牌定了以后同名同尺寸重画。
- `apps/web/index.html` 的 `<title>`、description、`theme-color` 同步改。`apps/web/src/main.tsx` 的 `pwaRuntime` 注册（`registerType: 'prompt'`，不自动跳过等待）和更新提示保留。

### 2.4 离线外壳

以 mobile-web.md 为准：CacheStorage 只预缓存公开构建资源，没有 runtime cache、后台写入队列和请求重放；API、认证、聊天、上传、语音、媒体都不缓存；导航 fallback 只匹配不带 query 的 `/` 和 `/index.html`。在此之上：

- **离线新开页面**：只显示公共外壳和「没网了。连上之后点 [重试连接]。」**不缓存、不显示晨报和三件事**。快捷入口和五个界面路由离线时是否也回外壳，由 09 在 P0-4 调整 `navigateFallbackAllowlist`。
- **已打开的页面断网**：可以继续打字，发送键变成「连网后发送」；草稿只在页面内存里，连网后由用户自己点发送，不自动补发。
- **退出登录、会话过期、换账号**：清空页面私人状态，回到公共连接入口。
- **缓存改名**：现为 `openfield-precache-v2-<scope>`（`pwa-build.ts` 的 `cacheId`）。改名后按 `apps/web/public/pwa-legacy-cleanup.js` 的做法，只在没有同源窗口时删确切旧名（`openfield-shell-v1`、`openfield-precache-v2-<scope>`）；`cleanupOutdatedCaches` 保持关闭。

### 2.5 Web Push 之前的触达

P0 没绑定 Discord 的用户：晨报留在「今天」页；晨报邮件提醒只发「墨的晨报写好了」和链接（`/today?from=email`），不带正文，用户可关（默认开关见待确认问题 3）。邮件提醒与 Discord 二选一，占同一个主动额度。现有邮件 outbox（`services/platform-api/src/account-mail.ts`）只发系统邮件，要扩展到提醒（09 第 6 步）。

### 2.6 Web Push（P1b，P1-14）

- **前提**：HTTPS 部署、推送订阅表、通知 outbox、service worker 的 `push` 与 `notificationclick` 处理。`generateSW` 产物没有这两个处理，要改用 `injectManifest`，或像 `pwa-legacy-cleanup.js` 那样用 `importScripts` 加载，由 09 在 P1-14 定。
- **平台**：iOS 与 iPadOS 16.4 起只有添加到主屏幕的网页应用能收推送，`display` 须为 `standalone`（现状即是）或 `fullscreen`，权限请求须由用户点击直接触发，不需要 Apple 开发者计划；iOS 18.4 起的 Declarative Web Push 在 service worker 失效时也能显示，优先评估。Android Chrome 与桌面是标准 Web Push。更低版本和应用内浏览器只给邮件或 Discord。
- **请求权限**：只在用户选「晨报发到这台手机」、点那一下时请求；被拒后不再请求，设置页说明怎么在系统设置里重开。
- **通知内容**：标题是主理人名字，正文只说是什么事：「晨报到了」「明天 10:00 有一场面试」「有 2 条待你确认」；`notification_preview = minimal` 时不出现公司名（待确认问题 5）；身份日期只写「有一个你设置的日期提醒」；点开到对应深链。
- **渠道选择**：在 02 的 `proactive_channel`（`web` / `discord`）之外加 `web_alert`（`none` / `email` / `push`），只在 `proactive_channel = web` 时生效；多个订阅时只发给最近活跃的那一个（假设）。

## 3. Discord 私信机器人（P1a，P1-2）

### 3.1 形态与身份

- **一个机器人账号，对所有用户相同。** 用户名和头像暂用产品名和标识（待确认问题 2），显示名末尾带「AI」，保证任何私信截图都能看到 AI 标识（02 §11.1）。「关于我」：「AI 求职小组。私信里的主理人和队员都是 AI，不是真人。隐私说明：（链接）」。
- **主理人就是机器人本身**：普通消息，不带 embed。
- **专家用 embed**：`author.name` 是「前 · 前辈」这样的「印章字 · 角色名」，`author.icon_url` 是印章头像，`color` 是队员的深色墨色，footer 一律带「AI」（08 §11）。
- **信件用 embed**：author 是主理人名字加印章，色条用主理人墨色；正文超过 300 字截断并给「到网页读完整的信」。晨报另有 200 字上限（第 3.5 节）。
- **印章头像**：服务端渲染 128×128 PNG（08 §11）。专家各一张固定图；主理人在诞生、改名、重新刻章时生成。URL 用随机路径、不含用户 ID，换图就换 URL。
- **色条**：08 深色队员色：前 #B597E2、面 #E2AE5B、投 #A0AABB；规 #89A5E8、教 #6BC39A（P1b 起）；脉 #5CBBCB（P2 起）。

### 3.2 绑定流程

**平台限制**：机器人只能私信和它至少共有一个服务器的用户，用户也可以在该服务器关掉「允许服务器成员私信」；User Install 能否替代共同服务器，官方没写明，**需实测**。所以 P1-2 需要产品自有的「小组大厅」服务器，只为让私信可达（待确认问题 1）。

**大厅防冒充**：用户在大厅打开私信，其他成员也能私信他，成员名单还会暴露谁在用这个产品；对常被冒充机构诈骗的人群，这就是冒充入口。所以：只经 OAuth `guilds.join` 或一人一次、10 分钟过期的邀请（`max_uses=1`）加人，不发公开邀请；没有聊天频道，只有一个只读欢迎频道（能否不留可见频道以隐藏名单，需实测）；欢迎频道、绑定卡片和欢迎消息都写防冒充提示（见下方卡片）；机器人每小时检查，未绑定或已解绑超过 24 小时的成员移出。

**入口**：「我 → 渠道与提醒 → Discord」；P1-2 上线后晨报末尾出现一次「想在手机上收晨报吗？可以连上 Discord。」（不占额度）。

**主路径：OAuth2**

1. 网页卡片：

   > **把墨请到 Discord 私信里**
   > 连上之后，晨报和今天三件事会发到你的 Discord 私信。你可以在私信里和墨聊天，点按钮完成小事。
   > 要发给别人的内容、你的简历、身份和签证相关的信息，只在网页上出现。
   > 连接时会把你加入我们的「小组大厅」服务器（Discord 要求有共同服务器才能发私信）。那里没有聊天频道，别人看不到你的小组内容。
   > 墨只在你和机器人的私信里出现，不会让你付钱、登录或加好友；其他自称墨或蔓藤导师的账号都不是我们。
   > [连接 Discord]　[先不用]

2. 授权范围 `identify`（用户 ID 和用户名，不读邮箱）、`guilds.join`；`state` 绑定当前网页会话，防 CSRF。
3. 回调：校验 `state`，换 token 读出用户 ID，加入大厅；**token 用完即弃，不保存**。
4. Discord 账号与产品账号一对一。已被绑定时：「这个 Discord 账号已经连在另一个账号上了。先在那个账号里断开，再来连接。」
5. 机器人发欢迎消息（第 3.3 节），网页显示：「已连接：{Discord 用户名}。以后晨报发到哪里？(•) Discord 私信 ( ) 留在网页 [完成]」。
6. 发送失败（50007）：「墨发不出私信。请在 Discord 里打开「小组大厅」服务器 → 隐私设置 → 打开「私信」，然后点 [再试一次]。」

**备用路径：一次性验证码**（手机上授权页可能要求重新登录 Discord，需实测）：网页显示 6 位码（如 `K7M4QX`，去掉易混字符），10 分钟有效、只能用一次，并给一人一次的大厅邀请；用户在私信里发 `/link K7M4QX` 或直接发码；机器人校验哈希、有效期、是否已用，每个码最多试 5 次，每个 Discord 账号每小时最多 10 次（假设）；通过后网页弹出「确认连接 {Discord 用户名}？」[确认] [不是我]，确认后才绑定，「不是我」作废这个码。

**未绑定用户私信机器人**：不处理内容、不保存消息，只回：「你好，我是 {产品名} 的机器人，还不知道你是谁。请先在网页「我 → 渠道与提醒」里连接 Discord，或者把网页上显示的 6 位验证码发给我。（网址）」

### 3.3 首条欢迎消息

一条 embed，author 是主理人名字加印章，色条用主理人墨色：

> 一然，我是墨。以后我们在这里也能说话了。
>
> 在这里，不带名字的消息都是我；队友发言会带上自己的名字和印章，比如「面」是面试官。
>
> 这里适合收晨报、聊几句、点按钮做小事。要发给别人的内容、你的简历、身份和签证相关的日期，只在网页上出现；需要你确认时，我会给你一个「到网页确认」的按钮。
>
> 我只在这个私信里找你，不会让你付钱、登录或加好友。锁屏可能显示消息预览，可以在 Discord 的通知设置里关掉。
>
> 晨报每天 {晨报时间}（你的时区）发到这里，{免打扰时段} 我不打扰你。想改，发 /settings。

时间取用户设置（默认见 02 §9）。footer「AI · 你的主理人和队员都是 AI」。按钮 [今天做什么] [设置]（`/me/channels`）[晨报别发这里]；点最后一个则 `proactive_channel` 改回 `web`，消息更新为「好，晨报留在网页上。想聊天随时找我。」

### 3.4 私信里的呈现与关键时刻

**对话呈现**：专家入场只在其第一条 embed 的 footer 写「刚加入对话 · AI」，离场不发（网页照常有系统事件行）。用户以「@前」「@前辈」「前：」「前辈，」开头或用 /ask 召唤专家，显式 @ 时专家总是入场，@ 了没上线的队员按 05 §2.3 的文案回应（03 §4.4）。一条消息不超过 3 段，一轮最多 3 条（主理人加至多两位专家），超出给网页链接。

> **一然**：Acme 那个岗位，我简历要不要改？
> **（机器人普通消息）**：这个让前辈看更准，我请前进来。
> **（embed · 前 · 前辈 · footer「刚加入对话 · AI」）**：JD 里反复提到 Spark，你简历里数据管道那段没写。我改了一版放进待确认，改动都标出来了，到网页看完再定。
> [到网页确认]（`/pending/{id}`）

**关键时刻的形态**（唯一出处，05 §4、08 §11 引用本表）。「消息正文」是 embed 之外那行字，会出现在通知和锁屏预览里；`notification_preview = minimal` 时只放中性句，公司名和日程只进 embed（锁屏怎么显示 embed 需实测）。未标分期的随 P1-2 上线。

| 时刻 | 消息正文 | embed | 按钮 | 通知 | 额度（02 §9.2） |
|---|---|---|---|---|---|
| 晨报 | 「墨的晨报」 | 第 3.5 节 | 第 3.5 节 | 是 | 占 |

### 3.5 晨报与今天三件事

内容、生成和三件事状态机见 05 §2.2，额度与免打扰见 02 §9。Discord 里是一条 embed，author 是主理人：

- 消息正文「墨的晨报」；title「晨报 · 10 月 7 日 周二」；description 是晨报正文，**≤ 200 字，所有渠道相同**，只讲一件最重要的事（02 §9.4）。
- field「今天三件事」：每件一行，序号、事情、负责队员的印章字、预计时长，例「1. 把推荐系统那个故事讲顺 · 前 · 40 分钟」。
- field「今天的日程」「待你确认」（有才出现）：面试的公司、轮次和时间；待确认条数和截止最近的一条，例「2 条 · 最近截止：材料包 10/09 23:59 PT」。
- footer：「今天不想做也可以，回我一句就行。」

按钮：第一行 [就这三件]（Primary）[换一件] [今天不想]；第二行 [到网页确认（2）]（有才出现）[看完整晨报]（`/today?from=discord`）。行为与网页晨报卡相同（05 §2.2）。Discord 特有：[换一件] 弹出只有本人可见的选择菜单（换哪件、换成哪件，备选 ≤ 3 个，外加 [不换了]），选完更新那一行；做完的按钮变灰，改为「1 做完了」。

连续 3 天没有 `brief_engaged`（第 9 节）时，按 02 §9.3 在第 4 天晨报末尾问一次「要不要我隔天来一次？」。

### 3.7 Discord 内可完成的低风险操作

标准：只改变用户自己在产品内的状态，不对外发出，只涉及 `normal` 级内容（03 §8.5），做错能撤销。

| 操作 | 条件 | 回执 |
|---|---|---|
| 三件事的接受、换一件、做完、挪到明天；今天不想、先歇几天；面试提醒的知道了；改晨报时间、免打扰、晨报发到哪里；付费推荐的不需要（按 06 §7.5 记录）；回复关心回访（02 §10） | — | 更新原消息或一句话 |
| 「记一条」：记住 / 不用 | 只限 `normal`，且不是推测的观察（02 §7.3）；「改一下再记」是到网页的链接 | 「记住了。[撤销]」 |
| 删除一条记忆 | 「忘掉这个」指代不清时先问「是这条吗：{摘要}」[是] [不是] | `normal` 写明删了哪条，`sensitive` 只说「删掉了一条记忆」；附 [撤销]，10 分钟内有效（与网页 10 秒的区别和软删除规则见 02 §7.3；原消息按 03 §8.8） |
| 待确认：稍后再看 | 设 `snoozed_until` 到下一封晨报（03 §9.2），不改状态、不延截止 | 「好，明早晨报里再提醒你。」 |
| 改看板阶段 | 只限用户自己点按钮；改为「已结束」同样按 05 §2.7 分级 | 更新原消息 |
| 请专家先离开 | — | 「好，前辈先退出了。」 |
| 插件投递授权：**收紧**（P1-1 起） | 只能改成「每次问我」或「永不」。聊天不直接改设置，只出 `apply_setting_change` 确认卡（11 §4.3）；确认后授权事件 `source = discord`、决定 `channel = discord`（03 §9.4、§10.2） | 「改好了：仲裁协议以后都先问你。正在填的那一份不变，下一份起生效。」插件下次领取材料包时读新设置 |

**不能在 Discord 里做的**（按钮一律链接到网页对应位置）：

- 确认任何待确认对象（材料包、邮件、外联消息、简历版本、周报）。要发给别人的消息和材料，都先进待确认，只在网页上确认；表单里哪些项可以替你做，由你逐项设定（见 11）；最终提交永远由你本人点。
- 查看或修改身份日期；修改记忆内容；确认 `sensitive`、`restricted` 的记忆提议或推测的观察。
- 付费、预约、退款。
- 放宽插件授权（改成「自动」）：要看完整的白话后果，部分题要二次确认（11 §4.2），只在网页设置页或插件资料编辑器里做。
- 替某一份申请点「同意」：插件需要浮层里的真实点击（11 §4.1；AGENTS.md「手机审阅不等同于插件收到可信点击」）。

对象与状态机见 03 §9，确认页见 05 §2.4。Discord 只出现由模板从白名单字段生成的摘要，不经模型改写：

> 投 · 材料包 · Backend Engineer, New Grad · Acme · 截止 10/09 23:59 PT
> 投 · 外联消息 · 1 位联系人 · 无截止

允许的字段：起草的队员、对象类型、岗位名、公司名、截止时间、条数；不出现内容、联系人、简历版本号以外的简历信息、任何身份信息。按钮：[到网页确认（2）]（`/pending`；只有 1 条时 `/pending/{id}`）[稍后再看]。出现在晨报、/pending 和截止提醒里；新增待确认**不单独推送**。

### 3.9 绝不发到 Discord 的内容

级别以 03 §8.5 的统一敏感度表为准（Discord 只出现 `normal`；`sensitive` 只给摘要；`restricted` 只说「有一个你设置的日期提醒」）。本节是它的展开：

| 内容 | 级别 | Discord 里出现什么 |
|---|---|---|
| 对外发出内容全文（邮件、外联消息、cover letter、申请表答案）；简历全文与差异 | `sensitive` | 摘要和「到网页确认」；「简历后端-v4 已备好」 |
| 联系人姓名与联系方式；薪资、offer 条款；学籍精确日期 | `sensitive` | 「1 位联系人」；「Acme 的 offer 详情在网页」；不出现 |
| 家庭与财务、情绪规律类记忆 | `sensitive` | 主动消息一律不用；用户发起的对话里，只有用户本轮自己提到时才回应，不复述原文 |
| 身份与签证日期、待业天数、OPT 与 H-1B 状态、I-20 或 EAD 信息 | `restricted` | 只说「有一个你设置的日期提醒」加链接，不出现天数 |
| 心理与健康、危机记录 | `restricted` | 不出现（危机当下按 02 §10） |
| 周报正文；蔓藤面经全文、交接包 | 用户内容；第三方内容 | 「周报草稿写好了」加链接；摘要和链接（04 §4.9） |
| 插件回执原文、密码、「每次问我」的同意动作 | — | 不出现 |

**出口检查**（每条发往 Discord 的消息发出前）：

1. 主动消息、待确认摘要、提醒由模板生成，只用白名单字段。
2. 模型生成的对话回复命中任一规则即拦截：与用户任何待确认对象、已确认的对外内容或简历版本连续重合 ≥ 40 字符；身份词与日期或天数同时出现（词表：OPT、STEM OPT、H-1B、CPT、I-20、I-983、EAD、SEVIS、cap-gap、grace period、待业、宽限期、工卡、身份、抽签；忽略大小写、空格和连字符，H1B、h-1b 都算）；A-number、SEVIS ID、护照号格式；邮箱、电话格式，或用户联系人表里的姓名；金额（$、美元、k、万）与薪资词（base、TC、package、年薪、签字费、offer）同时出现；本轮上下文用到 `restricted` 数据，或主动消息用到 `sensitive` 记忆（由上下文组装标记）。
3. **每次发送或编辑前**对本轮累计文本整体重跑，跨段的重合也算；命中时已发出的段落立即编辑替换。
4. 命中段落替换为「这部分涉及（简历 / 身份信息 / 要发出的内容 / 联系人 / 薪资），到网页看：[打开]」。只记命中的规则，不记内容。

**用户自己发了敏感信息**（如贴了 OPT 日期）：正常回答但不复述；由此产生的记忆提议只在网页出现。每 30 天最多提醒一次：「这类信息放在网页上更安全，Discord 的消息会存在 Discord 的服务器上。我看到了，不会在这里重复。」

**附件**：文件、图片不下载、不读、不存，回「附件请在网页上传，这里的附件我不会保存，也不会读。」语音消息回「这里听不了语音消息。可以打字告诉我，或者到网页上用语音跟我说。[打开网页]」

**危机**：流程和文案与网页完全一致，资源卡用 embed；危机对话永远不转到任何服务器频道或 thread（02 §10.4）。

### 3.10 频率与免打扰

额度、例外、免打扰和主动消息类型以 02 §9（类型表 §9.2）为准。Discord 特有的：

- 一条主动消息 = 1 条 Discord 消息（1 个 embed，≤ 2 行按钮），不追问。
- **投递窗口**：`deliver_before = max(scheduled_for, 免打扰结束时间) + 2 小时`；过了就不发 Discord，outbox 记 `expired_to_web`，只留在「今天」页。
- 用户发起的对话不占额度；一轮最多 3 条，**只有第一条触发通知**，其余加 `SUPPRESS_NOTIFICATIONS`；编辑不触发通知。用户在免打扰时段主动来聊，照常回复和通知。
- 「记一条」卡片上限按 02 §7.3，Discord 只出现 `normal`。
- 暂停期间（/pause、「先歇几天」）默认保留面试和截止提醒，其他停发；点 [都关掉] 后这两类也停（02 §9.3）。
- 付费建议不主动推送（06 §7.2）；投递官汇报不镜像。

### 3.11 流式输出：按段编辑

`DiscordTurnSink` 映射 03 §7.2 的 `TurnEvent`（事件名见 03 §6.6），不照 `packages/platform-contracts/src/index.ts` 的 `ChatStreamEvent`（它只有 delta、tool、usage、approval；start、done、error 是 `services/platform-api/src/app.ts` 路由发的 SSE 事件）。`turn_start`、`typing`、`tool` → 「正在输入」，约每 8 秒续一次直到第一条消息发出；`participant` → 入场写进 footer，离场不发；`start` → 每位发言者新起一条；`delta` → 服务端缓冲；`card` → 待确认转摘要、记一条只发 `normal`、其他给链接；`done`、`turn_done` → 最后一次编辑，去掉「……」；`error` → 第 3.12 节。

1. **首条消息**：第一段完整（遇到空行）；或缓冲超过 200 字且到句末；或已过 3 秒且至少有一个完整句子。
2. **后续编辑**：只在句子边界追加；同一条两次编辑至少隔 1.5 秒（假设，以 `X-RateLimit-*` 为准）；流式中末尾显示「……」。不逐 token 编辑。
3. **每次发送或编辑前**跑第 3.9 节的出口检查。
4. **换条**：超过 1,800 字或已有 3 段就新起一条；一轮最多 3 条，超出给网页链接。
5. **被限流**：跳过中间编辑，只做最后一次。
6. 只编辑本轮消息；超过 1 小时的旧消息除更新按钮外不再编辑（有次数上限，错误码 30046）。

### 3.12 失败与限流时的表现

| 情况 | 用户看到 | 系统行为 |
|---|---|---|
| 模型服务失败或未配置 | 已发出的部分保留，末尾改为「（我这边断了，没说完。）」[重试] [到网页继续] | 如实呈现，不用固定回复冒充（AGENTS.md） |
| 到了费用硬上限 | 系统通知（无 author，footer「系统提示」，不用主理人口吻）：「深度准备的额度用完了，{恢复时间}恢复。聊天、查看和确认已有内容、管理记忆照常。」 | 降级与恢复时间以 06 §12.3 为准；主理人简短对话和危机流程照常；48 小时内有面试时作战简报与练习可用到硬上限 |
| 按钮超过 3 秒 / 网页已处理 / 失败 | 加载后更新 / 只给本人看「这件事已经在网页上处理过了。」/「没成功，再点一次，或者到网页处理。[打开]」 | 先延迟应答；操作幂等，原消息更新到当前状态 |
| 429；Discord 整体故障 | 稍晚收到，「正在输入」持续；网页不受影响 | 按 `retry_after` 排队；主动消息过窗口就只留在网页，不改发其他渠道 |
| 私信发不出（50007） | 「今天」页顶部：「Discord 私信发不出去了，可能是你关了私信或离开了服务器。晨报先留在网页。[重新连接]」 | 24 小时内连续 2 次失败改为 `unreachable`，`proactive_channel` 改回 `web`，停止重试 |
| 网页上有一轮在进行时在 Discord 发消息 | 按插话处理，回复发在 Discord | 全渠道同一规则（03 §7.3）：当前段说完，后续段作废，开新一轮；L1、L2 立即中断 |
| 短时间连发很多条 | 无感：最后一条后约 3 秒没有新消息才开始一轮，合并回复 | 复用 03 §7.3 的 `queued` 合并。限流只防滥用：每用户 10 分钟 60 条（假设），触发时回「我在看，你慢慢说，我一起回你。」，L1 及以上不出现；需扩展 `services/platform-api/migrations/011_request_limits.sql` 写死的 `scope` 与 `subject_type` |

**掉线恢复**（危机流程以 02 §10.2–10.3 为准）：按 `dm_channel_id` 拉取每位绑定用户 `last_seen_message_id` 之后的全部消息，然后：

1. 对全部未答消息（不限时长）逐条先分级；合并回复之前每条单独分级。
2. 任一条为 L1 或 L2：不受 30 分钟、限流和预算限制，按 02 §10.3 补发模板和资源卡 embed，开头说「刚才我掉线了，现在才看到。」
3. 全部为 L0：掉线 ≤ 30 分钟的合并补答，开头「刚才我掉线了，现在回你：」；超过 30 分钟只发一句「我刚才掉线了一阵，漏看的话到网页上找我。」

### 3.13 解绑与数据删除

入口：网页「我 → 渠道与提醒 → 断开 Discord」，或私信 /unlink。

> **断开 Discord？**
> 断开后，墨不会再在 Discord 里找你，晨报改回网页。你会离开「小组大厅」服务器。
> 你在 Discord 里和小组说过的话，会继续留在网页的小组记录里；想删，可以在网页上删。
> [ ] 同时删除机器人在私信里发过的消息（需要几分钟；你自己发的消息要在 Discord 里自己删）
> [断开]　[取消]

**立即**：绑定改为 `revoked`；待发消息改为 `cancelled`，`proactive_channel = web`；移出大厅（P2 社区成员身份不受影响）；勾选了就逐条删除机器人的私信消息。**数据**：清空外部身份字段，24 小时内删行，只留审计记录（外部 ID 哈希、绑定与解绑时间）90 天（假设，需法务确认并与隐私政策一致），由 09 第 6 步的 `retention` 任务执行；来自 Discord 的小组消息清空 `external_message_ref`，内容按网页删除规则处理；注销账号时全部删除，私信里的机器人消息尽力删除。用户在 Discord 那边撤销时我们不一定收到通知，按「私信发不出」处理；换账号先断开再连接。

## 4. Discord 第二阶段（P2）：社区服务器与多身份群聊

### 4.1 要解决什么

- **群聊感**：队员各用自己的名字和印章头像发言。webhook 能逐条覆盖用户名和头像、往指定 thread 发，应用创建的 webhook 还能带按钮；私信里不能用 webhook，多身份只能在服务器里做。
- **真人连接**：同期伙伴频道；蔓藤导师答疑（04 §3.7）。

### 4.2 隐私问题：服务器里谁能看到什么

私有 thread 只对被拉进去的人可见，但**有 Manage Threads 权限的人能看到所有私有 thread**，Administrator 和所有者能看到一切，技术上无法隐藏；私有频道同理，且每个服务器最多 500 个频道，同时活跃的 thread 约 1000 个（需核实）。服务器频道里读消息需要 Message Content 特权意图（私信不需要），2026-06-10 起用户数不到 1 万的应用可直接开启，超过要申请并每年复审。所以把小组放进蔓藤服务器的私有 thread，等于让蔓藤管理员和版主能读到所有人的小组对话；对「怕被机构割韭菜」的人群，这是信任问题，不只是合规问题。

### 4.3 方案对比与推荐

| 方案 | 隐私 | 群聊感 | 代价 | 结论 |
|---|---|---|---|---|
| A. 蔓藤服务器里每人一个私有 thread | 差：管理员、版主可见 | 强 | 活跃 thread 上限；严格的权限管理 | 不推荐；一定要做须满足下方 5 条 |
| B. 每人一个私有频道 | 差 | 强 | 500 个频道上限 | 不可行 |
| C. 用户自己的「私人小组服务器」 | 好：只有用户和机器人 | 最强 | 用户多做两步；机器人进入大量服务器（分片见 09）；需 Message Content 特权意图 | **推荐，可选** |
| D. 社区服务器只放公共内容，个人小组留在私信和网页 | 好 | 无多身份 | 最低 | **推荐，默认**（最终见待确认问题 1） |

**私人小组服务器（C）**：

1. 网页「我 → 渠道与提醒 → 私人小组服务器」：「在 Discord 里开一个只属于你的小组服务器，墨和队员会各用自己的名字和印章说话。服务器归你所有，除了你和我们的机器人，没有其他人。」[创建]
2. 用户点服务器模板链接建服务器（只有 #小组；模板可用性需核实，不可用时引导手动建），再点机器人安装链接，授予查看频道、发送消息、读取消息历史、管理 webhook。
3. 机器人在 #小组 建一个 webhook，主理人和队员都经它发言，每条覆盖名字和印章头像；webhook 名不能含「discord」「clyde」。
4. 内容边界同私信（第 3.9 节）；私信和私人服务器二选一（`discord_surface`）。
5. **只处理绑定用户本人的消息**：其他人的消息不读内容、不入库、不发给模型。有别人加入时提示一次：「这里有其他人了。墨会把这里当成公开场合：不提你的求职细节，也不用记忆，直到只剩你一个人。」期间只回应用户本人、不用记忆、暂停主动消息。

**如果仍选 A，上线前必须满足**：①所有者是产品公司的专用账号，不是蔓藤销售或导师的个人账号；②有 Administrator 或 Manage Threads 权限的真人 ≤ 2 人，签保密协议，角色写进隐私说明，版主不给 Manage Threads；③thread 只由机器人创建，`sensitive` 连摘要也不给；④真人导师只经用户在网页确认的交接进入，会话结束就移出；⑤用户开启前勾选：「这个私有 thread 在蔓藤的 Discord 服务器里。按 Discord 的规则，服务器的管理员能看到所有私有 thread。我们的管理员只有 2 人，不会主动查看；但如果你不能接受，请继续用私信，体验不受影响。」

### 4.4 蔓藤社区服务器的结构与规则

频道：#欢迎与规则（只读：行为准则、隐私说明、AI 与真人怎么区分）；#公告（只读，**不用 @everyone 或 @here**，01 §8.4）；#同期-{方向}-{届}-{组}（每组 6–8 人，假设；用户在网页上选择加入，组员和版主可见，**版主可见写进隐私说明**）；#导师答疑（每周固定时段，每场一个 thread，04 §3.7）。

- **AI 不在社区频道聊天**：机器人只发公告、回应只对本人可见的斜杠命令，不读、不回同伴对话；社区里的危机信号由版主按版主手册处理（依据 02 §10 改写）。
- 真人导师带「真人 · 蔓藤导师」身份组（08 §7.5）；版主和蔓藤导师不得私信用户推销付费服务（01 §8.9）。
- 小组内容不会自动出现在社区。想在 #导师答疑 提问，可在网页上请队伍帮着写好，**由用户自己复制发出**。

### 4.5 进入 P2 的条件

P1-2 的私信用户达到 07 的阈值且 H4 没被推翻（口径 `brief_engaged`）；蔓藤确认社区运营和版主人力（04 M2-3）；隐私说明（尤其 A 方案告知文案、#同期 的版主可见）经法务审阅；版主手册（行为准则、举报、危机）写好并演练一次。

## 5. Web 与 Discord 的一致性

### 5.1 同一条小组对话，Discord 不镜像网页

**采用**：Discord 的消息写进用户唯一的小组会话（`channel = discord`），网页能看到全部；私信里只出现 Discord 里发生的对话和投到 Discord 的主动消息。**不采用**两条对话共享记忆（主理人接不上「你刚在网页上说的」，像两个墨），也不采用全量双向镜像（重复通知，把敏感内容带进 Discord）。理由：一个关系、一支队伍（01 §7.1）。

对策：为 Discord 组装上下文时由 `services/platform-api/src/context-assembly.ts` 的渠道层按 03 §8.5 过滤，再由出口检查兜底；两个渠道同时说话按 03 的轮次与插话规则串行（现有 `services/platform-api/migrations/001_platform.sql` 的 `platform_one_stream_per_conversation` 也只允许每会话一条流式消息）。机器人进程在进程内直接调用服务层（09 第 9 步），不经 HTTP，不涉及 `x-companion-account`。网页上来自 Discord 的消息标小字「来自 Discord」。

### 5.2 渠道层的一致性要求

主理人层面的对照见 02 §13。渠道层只补三条：

- **状态以服务端为准**：网页上接受了三件事，Discord 晨报的按钮在下次被点时更新为当前状态，不主动编辑旧消息。
- **一个提醒只在一处出现**：主动消息投到哪个渠道就只在那里通知；「今天」页照常显示内容，但不再弹提醒。
- **同一个对象只有一个链接**：所有「到网页」按钮都用第 2.1 节的深链，不另做 Discord 专用页面。
