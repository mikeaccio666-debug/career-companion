# 你之前的审阅队列方案：评估

检查日期：2026-10-05。已在浏览器完整阅读[Claude artifact：审阅队列设计](https://claude.ai/artifact/6TVP8iJj2bnT9ReQLHjRa3)。这是设计材料，不是已上线能力。它引用后端 013d5128 与插件 7ebed714；本次插件迁移使用更新的 d1a496bf。

## 方案真正做了什么

夜间服务器挑选岗位并准备材料；用户在手机逐项审阅；电脑 Chrome 插件在本地已登录的页面里顺序填写。方案的第二阶段再设计一次性提交票据，把每个岗位、答案和附件版本绑定到明确批准的内容。

这是一种有价值的混合架构：准备工作和审阅不用一直开着电脑，本地执行能使用用户浏览器会话。但“手机批准”不会使关闭的电脑开始执行，也不会把手机变成 Chrome 插件环境。

## 哪些结论需要修正

- **“必须用插件”不是技术定律。**云浏览器、官方 API、本地桌面程序都能自动化。草案采用插件，部分原因来自原项目对账号和材料的处理边界。新产品可以重新选择执行环境，承担相应的会话隔离、授权和恢复工程。
- 云端失败比例、竞品做法、固定等待时间降低风控风险等叙述，缺少可验证的依据；本次不将其当作成功率或反封锁保证。已有调研只采用实际打开的官方来源。
- 83 人日是旧范围下的草案估算；尚未验证接口漂移、当前源码和验收条件，不适合直接作为我们的工期承诺。

## 源码核查后的真实差距

1. **已有提交路径，但不是无人值守提交。**现有 submit controller 要求插件自己界面中的可信用户手势，核验规则与远程策略后执行。手机批准不能作为那个点击的替身；草案里的批量票据和 `submit-approved` 是需要新增的协议与产品行为。
2. **服务 worker 恢复仍有缺口。**队列 entries、pending submissions、manifests 等仍存在内存 Map；部分 frame/tab 登记使用 session storage，submission outbox 使用 local storage，但它们不足以恢复整个队列。Chrome 会终止闲置 worker，因此要为中断、过期、结果不确定设计恢复流程。[Chrome 生命周期](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)
3. **签发和租约不能省掉。**旧后端的 ES256 意图、安装实例及用户绑定、资料与审批版本、单次 claim、短租约和回执事务互相依赖。迁移出的只读服务没有假装提供这些能力。
4. **后端与插件契约确有漂移。**后端存在 application-form/V3 的扩展，插件当前稳定签发链使用 V1/V2；另外还有资料投影差异。不能把两个目录合并后就宣称端到端兼容。
5. **先前的自动化边界不能靠一个批准按钮实现。**登录、验证码、动态问题、敏感字段、附件变化、网站改版、用户撤回和重复提交，均需要具体状态和验证方式。

## 对我们的建议

保留“手机准备与审阅，电脑插件填表”作为一种模式。先验证单个用户已打开的申请页面：从已确认档案填入、核对缺口、用户完成最后一步。随后评估任务持久化、断线恢复和逐站点云执行。

如果后续选择“批量批准后自动提交”，必须把它作为独立功能讨论：用户到底批准了什么、内容变化怎样重新确认、如何取消、何时判定成功、结果未知时怎样避免重复。当前迁移没有开启这个功能。
