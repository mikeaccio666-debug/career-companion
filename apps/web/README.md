# 求职伙伴网页

A responsive React/Vite client for the independent platform API. The working identity is centralized in `src/brand.ts` and follows `../../docs/product/09-implementation-roadmap.md` §2. Models execute on the server or through an explicitly started Realtime session; the client never stores provider credentials.

The current entry implements O0 registration and current-version legal consent. All Web accounts, including legacy accounts, stop at `/welcome` after the existing mailbox requirement and explicit consent. The page states that the remaining first meeting is unavailable. It mounts no student navigation, chat composer, private-data polling or internal workbench. O1 onward and first-letter completion are not implemented; legacy account existence and deployment flags do not establish their completion or a staff identity. The underlying conversation, knowledge, settings and workbench components remain in source for later authorized entry.

Registration reads the server's invitation requirement and the complete current legal documents, starts with an unchecked checkbox, and sends the exact displayed version and digest. `/terms` and `/privacy` are public pages and do not run the private account bootstrap. Missing or mismatched documents disable registration and confirmation; login and password recovery remain available. Existing accounts must separately confirm the current documents. Rechecking reloads current auth options and documents rather than treating an old checkbox or another account's late response as consent.

P0 companion interaction is planned as text. The retained conversation components can show private, read-only saved voice excerpts when a future authorized entry mounts them; O0 does not open that history. Interviewer practice requires the later stage-7 implementation; companion voices require the phase in `docs/product/12-voice.md`. Neither is represented as available by mounting a generic voice tool. The retained internal Voice Studio supports recording, file import, speech, ordinary reviewed chat and Realtime with server-selected routes and real capability booleans. Existing local voice preferences do not select services, models, voices, personalities or turn-taking in new requests.

Chat audio attachments use a separate receipt-backed review flow. The public `chatAttachments` support declares direct text/image/PDF inputs and audio limits without runtime identifiers; missing declarations do not imply availability. “转写并审阅” explicitly calls the account-bound upload transcription endpoint once with a retained client UUID. The immutable original ASR text and editable sending text are distinct; editing clears explicit review. Sending requires a valid source-matched receipt and the user's checkbox, retains the private source in `attachmentIds`, and sends only `{receiptId, reviewedText}` references. The server excludes raw audio from chat input. Video parsing remains visibly unsupported. Review verifies no identity, career experience or ability.

Canceled or lost transcription responses retain their request UUID and show an uncertain result. Recovery is an explicit GET to `/uploads/:sourceId/transcriptions/:clientRequestId`; 404 does not prove the prior request stopped and never triggers another POST. Account generations, navigation, component unmount and source removal abort reception and discard late results. Completed receipts remain reviewable when ASR is disabled. Message history labels original versus edited reviewed text and its untrusted provenance; edited history can explicitly fetch the original through the owned read-only `/audio-transcriptions/:receiptId` endpoint without running ASR. Transient review drafts/request IDs are memory-only until leaving the authenticated session or refreshing. Focused tests exercise uncertainty, source binding, review changes, limits and account races without real recordings or model calls.

## Run

From the repository root: `pnpm --filter @companion/web dev`. Vite listens on `127.0.0.1:4321` and proxies `/api` to `http://127.0.0.1:4320`. Configure `VITE_PLATFORM_PROXY` to change the local proxy target. `pnpm --filter @companion/web check` checks TypeScript; `build` builds static assets.

## API expectations

Domain types are imported from `@companion/platform-contracts`. Frontend optimistic messages add display state without defining a separate server contract.

O0 does not start private workspace polling or provider-detail requests. Account changes invalidate pending consent and account operations. Bootstrap anonymously reads `/features`, boolean `/capabilities` and `/auth/options`; these flags do not open a private workspace. The retained workspace components still use bound account clients and their existing generation and polling checks when a future authorized entry mounts them.

The client sends cookies only to its deployment-configured API. `VITE_PLATFORM_API_ORIGIN` is empty by default, retaining same-origin `/api/platform`; an explicit value must be an exact HTTPS origin or HTTP localhost/127.0.0.1/[::1] origin. It is public build configuration, never a secret. Production split hosting uses same-site HTTPS app/API subdomains and an exact server `PLATFORM_ALLOWED_ORIGINS` entry. Unrelated provider default domains are not a third-party-cookie guarantee.

`platform-endpoints.ts` owns API and private media URL resolution. Server media DTOs and private Markdown paths accept only `/api/platform/uploads|artifacts/<UUID>` and are mapped to the configured API; arbitrary external URLs cannot select a credential destination. Native media uses `crossOrigin="use-credentials"`; downloads use the authenticated `?download=1` server attachment response. JSON, multipart and SSE use the same client and reject redirects. Bodyless reads do not add a JSON Content-Type that would trigger unnecessary preflights; JSON writes keep the header and multipart keeps its browser boundary. Collections can be arrays or named envelopes (`conversations`, `messages`, `jobs`, `memories`, `approvals`). Errors should have `message` and optionally `code`, or `{error:{message,code}}`.

- `GET /health` and `GET /ready`: actual service/readiness evidence.
- `GET /features`: `{version:1,workbench:boolean,providerDetails:boolean}`. Missing, malformed or contradictory features close internal UI; they do not invent a provider or require clearing the user draft. Only exact GET/HEAD `/features` is a public client exemption.
- `GET /capabilities`: `{capabilities:Record<Capability,boolean>,chatAttachments?:PublicChatAttachmentSupport}`. All known capability flags are required booleans; absent support stays absent. This endpoint never supplies a provider catalogue. Real `transcription`/`realtime` availability describes the existing transport, not a released interviewer product; student speech remains disabled.
- Secured development `GET /capabilities/details`: `{providers:ProviderStatus[]}` only when the server allows detail exposure. Internal chat provider/model controls are read-only catalog information; the server chooses the actual route.
- Auth `POST /auth/register`, `/auth/login` return `{user}`; `GET /auth/me` returns `{user}` or 401; `POST /auth/logout` clears the cookie. Registration additionally requires `{consent:{accepted:true,version,digest}}` and an email-bound `inviteCode` when invitations are required. Public `GET /auth/options` reports invitation/legal availability; `GET /auth/legal-documents` returns the complete current documents or an unavailable state. Account-bound `GET/POST /auth/consent` returns `{consent}` tied to the current owner and policy.
- Student conversation: `{id,title,createdAt,updatedAt}`; create accepts only `{title}`. Public message keeps id/conversationId/role/content/status/createdAt/private attachments and reviewed audio source evidence. Student message input is only `{content,attachmentIds?,audioTranscripts?}`. Legacy role=tool rows are hidden in student history; existing user/JD/project text is preserved verbatim, including technical names. Internal chat may also send `mode`/legacy `persona`, but neither mode can override `provider` or `model`.
- Streaming uses `start`, `delta`, `tool`, `done`, `error`; student approval/usage events are not rendered, and public tool progress contains only messageId/name/status. Completion uses the actual saved message receipt.
- Upload accepts multipart `file`; returns `{attachment}`. Uploading alone never submits a file to a model. Public ASR receipts retain source IDs/MIME/SHA/text/provenance without requiring provider/model metadata. Internally returned runtime metadata is excluded from rendering/routing before the same strict source parser.
- Memory `{id,content,createdAt?}` is explicitly saved. Student `/usage` shows real aggregate counts, reporting gaps, null tokens and outcomes; it does not render provider/model breakdown or a fabricated cost bill.
- Internal voice `/voice/transcribe` accepts multipart **file only**, `/voice/speech` accepts **text only**, and `/voice/session` accepts **optional conversationId only**. Realtime returns its actual `clientSecret`, `endpoint`, `sessionId` and optional expiry/input-transcription/context fields. These protocol fields are necessary for direct WebRTC and do not conceal vendor network traffic. Microphone activation starts with a click and waits for context acknowledgements. Leaving, stopping or failures release the actual session, microphone and peer; a ten-minute limit still disconnects.
- Internal tasks keep their genuine provider-bearing task contracts, approvals and leases; student HTTP admission denies creation. Task details, workflow/browser/CLI/MCP panels and their polling remain internal infrastructure rather than the student product.

## Local and mobile behavior

Registration, persisted conversations, uploads and explicit memories work without model credentials. Actual unavailable chat is disabled with an honest service message; refresh reads the latest public capabilities. A manifest describes the mobile browser shell. Offline mode can show cached shell assets but cannot read private data or execute chat. Service workers do not cache API responses (including features/capabilities), tokens, user uploads or private media.

The internal recording/import flow caps audio at 20 MiB, preserves earlier text on silence and keeps explicit history saving separate. Browser dictation is offered only when the browser provides it. Voice capability refresh cannot prevent stopping an existing local resource. Production services are configured on the server; environment-variable/provider metadata appears only in the secured internal detail UI.

The following workflow, browser and voice infrastructure descriptions apply to the internal workbench, not the student navigation.

Workflows have an independent editor for one to eight text/image/video/speech steps. Media task retries distinguish resuming a persisted provider handle from a new generation request; terminal task regeneration requests a fresh approval and may incur another provider charge. Uncertain execution requires review before retry; unconfirmed CLI cleanup stays blocked.

## Reusable workflows

`WorkflowPanel` composes the UI, `workflow-editor.ts` handles draft serialization and dependency integrity, and `workflow-api.ts` owns private template requests. The editor supports per-step providers, models, prompts and reviewed JSON options. `{{input}}` means the current run goal; `{{previous}}` means the latest text output, initially empty. Image/video steps can select up to four image outputs from earlier image steps. References use step indices in the contract and stable editor identities during reordering; reordering into the future, deleting a referenced source or changing its image capability is blocked until the reference is removed. Media bytes are transferred by the backend; the frontend neither publishes private image URLs nor downloads data for another provider.

Private templates use `GET/POST /workflow-templates` and `PUT/DELETE /workflow-templates/:id`. Updates send the saved revision. A 409 retains the draft and offers an explicit server reload or a new copy. Template saves are possible before models are configured and do not execute anything. The current run goal is separate from the saved template. A full review freezes a task snapshot; creation is disabled while any chosen service or the workflow executor is unavailable. Creation requests an approval, and later template edits cannot change that submitted task.

Workflow task cards render server-derived per-step states and available artifacts, including completed outputs retained after a later failure. The API's `workflowResumeAvailable` flag decides whether unknown step results can resume; absent or false recovery permission keeps uncertain workflows blocked. An explicit true flag offers “审阅后继续”, preserving completed steps and querying existing provider tasks where available. Unfinished steps may create new requests and incur fees. The browser does not infer recovery permission from raw provider handles or manufacture completion or provider outputs.

The editor uses a one-column step layout on phone widths, unique accessible labels and 16px mobile text fields. `pnpm --filter @companion/web test` includes draft bounds, snapshot independence, API revision requests, placeholder insertion and image dependency ordering using fictional fixtures and mock HTTP only.

## Reviewed browser plans

`BrowserPanel` is independent of media/CLI composition. `browser-plan.ts` validates and serializes plans; `BrowserPlanDetails` and `ApprovalDetails` render the same complete, readable visit/action context next to approval controls. No JSON editor is needed for the ordinary browser flow. A URL and goal without actions produce a read-only text/screenshot task with options `{url}`. Users may design up to twelve ordered click/fill/select/scroll actions. Role targets pair links/buttons with clicks, textboxes with fill, and comboboxes with selection; label targets are also supported. Names/option labels are bounded to 200 characters, fill values to 2,000 with whitespace preserved, and scroll distances to 1–1,200 integer pixels. Unknown action/target/options fields are rejected. The frontend's URL entry limit is 2,000 characters; execution still validates DNS, redirects and network requests on the server.

Plans remain in page state without automatic persistence or execution. Review produces an independent snapshot and disables the editor until the user returns to edit. Creating a task still requires a separate approval. `browserActionsEnabled` must be explicitly true for action plans; missing/false flags retain read-only operation and allow designing drafts. Public HTTPS URLs are accepted; the only local exceptions are exact loopback fixture origins explicitly advertised by the server. The frontend does not guess whether public DNS names resolve privately; the server enforces that boundary.

Approval cards show the site, goal, action order and complete fill/selection content. Unsupported or malformed browser approval plans cannot be approved. Login, CAPTCHA, sensitive fields, payment and final submission remain outside this plan; full computer operation is still being integrated. Browser task cards display completed/total actions and stored partial artifacts. `reviewRequired`, started actions and malformed execution summaries prevent ordinary retry. Action plans without a checkpoint fail closed; known read-only tasks with a valid URL, absent/empty actions and no action execution record keep their normal reviewed retry. Existing action records cannot be bypassed by removing actions from displayed task metadata. Other task kinds keep their own retry rules.

“带回 Agent 草稿” places only an owned job reference and instructions to use `get_browser_observation` in the chat composer. It never sends automatically or copies raw page instructions into trusted chat context. A normal/companion conversation starts a new Agent draft while preserving the existing unsent text and selected uploads; an existing Agent conversation can continue. Conversation history is not silently copied. The button requires a stored `browser-observation.json` artifact with `application/json` MIME. Historical text/screenshots remain viewable but are not fabricated into observation records. Browser helper tests use fictional plans and verify strict shapes, bounds, role/action compatibility, exact local fixture origins, capability flags, review snapshots, safe handoff and partial-result retry rules without paid model calls or live applications.

Text/code results in CLI, workflow and creative task cards can also be brought to an Agent draft. Shared contracts restrict supported MIME types and source size to 1 MiB; source IDs must resolve to the current job list. The action appends only metadata and a `read_artifact_text` request, preserves prior text/attachments, avoids duplicate references and reports drafts exceeding 20,000 characters without silently truncating them. Account and navigation generations guard delayed selection and focus; clicking does not fetch the body or send a message. Actual reads occur after the user sends. The tool timeline merges events by call ID and distinguishes returned results, safe errors, unconfirmed results and historical approval requests; a returned tool result does not mean an execution task finished.

## Internal voice continuity

Internal Voice Studio supports reviewed turns: import or record audio, review its text, then explicitly send one ordinary message using the server route. Read-only catalog controls never change the transmitted route. The existing authenticated message stream saves the question and reply. Only a verified complete message receipt enables reply narration; speech failure leaves the reply and permits speech-only retry. Agent conversations cannot use this path to authorize tools. Configured local routes and direct WebRTC are separate paths and never start microphone access automatically. Viewing the saved conversation preserves the existing chat composer draft.

Account settings reads the owner-only `/usage` summary for the current UTC month. Known zero, absent/invalid reports and pending calls have separate displays; only provider-reported counts from the new call ledger are added. Legacy reports remain separate. This view covers conversation chat/companion/Agent calls, not all execution types, prices or a spend limit. Request cancellation and account generations prevent old results from being displayed after switching users.

`GET /conversations/:id/voice-records` returns `{records}`. Explicit saves use `POST` with the shared `VoiceRecordInput` contract and return `{record,created}`. Client UUIDs are retained for retrying the same excerpt; partially successful bulk saves resume without duplicating records. The API validates the current account, conversation ownership, audio attachments and actual server-issued Realtime session. Provider/model attribution is server-derived; the browser never submits tokens, raw events or ordinary assistant messages through this endpoint.

Recording or browser dictation can be reviewed, edited and saved as `transcription_excerpt`. Speech synthesis saves the actual input-text snapshot with its returned audio as `speech_excerpt`, independently of later editor changes. Realtime accepts only final user/assistant transcript events, orders items using their predecessor IDs, deduplicates repeated events and preserves all received complete turns until leaving the page. Text is split at Unicode boundaries to meet per-record limits. Revisions are labelled; saving a revised final event creates new excerpts. No transcript or turn is saved automatically.

All saved voice records have `client_submitted` provenance and remain visibly separate from normal model messages. “带回对话草稿” fills the selected conversation's composer with an explicitly labelled quote, without sending it or calling a model. A first explicit save creates a “语音笔记” conversation only when no conversation is selected. Realtime input transcription is optional and controlled by the server's `inputTranscriptionEnabled` flag; missing user transcripts are never fabricated. Released session excerpts can be saved within the server's 24-hour window. Leaving Voice Studio releases Realtime/microphone resources; bounded text drafts remain scoped to the current authenticated account and conversation until refresh or authentication change.

`pnpm --filter @companion/web test` checks final-event filtering, deduplication, item ordering, Unicode chunks, source attribution, revisions and buffer limits without microphone access or model calls.

## Public identity and install assets

`src/brand.ts` supplies the React label and AI identifier, the escaped HTML tokens in `vite.config.ts`, and the production manifest generated by VitePWA in `pwa-build.ts`. There is no separately named static manifest. Development keeps PWA registration disabled; installation assets are emitted by the production build.

The neutral conversation placeholder in `public/mark.svg` is the source for the complete PNG install-icon set. The maskable export has an opaque background. The generated worker uses a neutral cache namespace; legacy cleanup removes only the exact old shell cache and old precache for its own registration scope, after all same-origin windows close. Private API responses and user media stay outside the precache.

The working identity and account-entry/request boundaries are wired. The generic workbench remains retained internal infrastructure. Companion personalities, experts, interviewer sessions and the later group-chat interface still require their roadmap stages; O0 does not claim those roles exist or open their navigation.

The retained student knowledge handoff, for a future authorized workspace entry, quotes only the selected passage already returned by the owner-bound search, with its source/version and an unverified snapshot label. It preserves the existing conversation, draft and uploads, does not enable Agent or fetch a whole private source, and never sends automatically. Oversized drafts remain intact with an explicit limit notice. Internal handoff retains the original tool-reference flow; O0 mounts neither handoff.
