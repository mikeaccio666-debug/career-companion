# Platform API

Independent Fastify service for the web product. PostgreSQL owns identity, messages, saved memories, approvals, jobs, attempts and artifact metadata. Redis/BullMQ distributes jobs; it is not the source of task truth. The migrated application service and Argoland runtime are not started by this service.

## Initial meeting intake (unreleased)

`OnboardingDrafts` persists O1–O4 through the dedicated student `/onboarding` transport. The Web welcome view reads the real server cursor and saves fixed-question answers, explicit skips and configured text submissions. It does not supply ordinary chat, companion birth or first-letter delivery. Separate `/companion/drafts` routes below consume completed intake for O5–O6. An intake read returns `null` before the first explicit start; it never creates progress. Each accepted question, explicit skip or text submission saves one server revision. The core reducer computes the cursor, fast track and `intake_ready` boundary; that boundary grants no companion, room, memory, tool permission or delivery status.

Every read, save and duplicate operation checks a captured actual session, student account, configured email verification and exact current legal consent under PostgreSQL locks. Commands carry an expected server revision and a UUID operation ID. Two devices cannot silently overwrite the same revision. An identical retry returns the latest saved draft and the original operation's applied revision; reuse with different input conflicts. Commands and account context are copied before asynchronous work. Admission occurs at the final database-time session check before COMMIT; confirmation is returned only after successful COMMIT. Cancellation or natural session expiry after acceptance does not undo that write. A caller that loses confirmation must recover with the same operation under a valid session, rather than treating cancellation as proof of no save.

Migration 026 stores the whole draft and canonical operation input as ciphertext. `PLATFORM_DATA_KEY` is a separate 32-byte key encoded as exactly 64 hex characters, shared privately by API and worker. Production requires it. Development may omit it, in which case this service refuses reads and writes; explicitly empty or malformed configuration fails startup. Version 1 uses AES-256-GCM with a random nonce and authenticates table, column, actual row ID, owner and revision. It accepts at most 64 KiB of strict UTF-8 per plaintext. Invalid ciphertext, unknown schema or inconsistent decrypted state returns a bounded storage error; it never resets a draft. There is no plaintext fallback, email-key reuse or key-rotation implementation.

Typed answers are saved as encrypted operations and leave a public text reference in `safety_pending`; they cannot advance via ordinary answer/skip commands. The dedicated retry transport runs one server-owned detector claim through the existing classification runner and authenticated result-persistence port. New text requires an activated detector profile, reviewed response bundle, explicit configured classification route and positive model-call limit; availability does not grant admission. Missing or invalid current assets disable new text while previously captured authenticated resource cards remain readable. Classification is not dispatched by an automatic queue in this slice.

Under 05 §2.1, a full L0 result that cannot map text to an option advances with a separate `unmatched_text` skip and text reference; it does not invent a fact, a user skip or a saved memory. An old classification cannot release newer text, and older pending text remains eligible for L1/L2 intervention. The reducer rejects `keyword_only/L0`; 02 §10.2 and 09 §4 differ in wording about nonmatching fallback, so that policy still needs product clarification before release. Fictional `full/L0` fixtures prove protocol behavior, not classifier accuracy. Basic facts remain user-entered; program choice is an optional explicit draft value and is not mapped to a career profile or inferred from graduation dates while the product-document conflict remains unresolved.

Focused PostgreSQL tests use fictional actors in unique loopback schemas. They cover durable recovery, current admission, concurrency, encrypted pending text, replay, damaged/transplanted data, actual lock-wait expiry, deferred COMMIT rejection and recovery after acceptance. They do not establish mobile behavior, safety quality, persona prose quality or production readiness.

### Internal companion personality foundations

`CompanionIntakePreparation.prepare()` derives dimensions from the actual encrypted, completed intake under the fixed session, current student/email/legal policy and account lock. It authenticates every historical operation, detector result and explicit safety followup, including superseded text; pending or unhandled high-risk history prevents preparation. Handled high-risk text remains excluded from facts and personality preferences. Explicit O4 preferences are read only from the exact full-L0 operation/result pair. Its immutable projection contains source revisions and dimensions, without raw text. It is a snapshot, not a generation claim: a future writer must revalidate the source and current admission before committing work. Recovery may repair reference-only inbox records; preparation creates no companion, main room, memory, lease or first letter.

`career-core` supplies closed name rules, seeded three-character seal suggestions and a clearly tagged `generatedBy='fallback'` rule preview (summary, three samples, bounded style card, quirks and one of seven ink tokens). Fixed family/partner and team names remain reserved. Unicode Latin letters are allowed; same-name and vocabulary comparisons use explicit normalized whole-name matching. English seal associations require an external alias. Seeded metadata does not enforce message frequency, shared reroll limits or historic identity snapshots; those require the real persisted entity.

`PLATFORM_COMPANION_IDENTITY_BUNDLE_FILE` optionally names a server-only JSON asset with `schemaVersion:1`, positive `revision`, exact `contentDigest`, `sourceRefs:{names,seals,aliases}` and the six closed policy arrays. The bounded UTF-8 reader captures copied, immutable content. No external vocabulary, alias, normative 3,500-character table or approval is seeded. Hash and syntax validation cannot prove vocabulary completeness, tier-one membership or external review; those must be established before activation and student release.

These foundations do not generate O5 prose, record failed model attempts, activate an identity, create a room or expose student endpoints. Per 02 §2.6 and 05 §2.1, disabled model service remains unavailable. Rule metadata can be compiled during preparation, but fallback prose may be delivered only under the specified real failure policy.

### Internal name, seal-candidate and selection persistence

`CompanionIdentityDrafts` privately saves a user-typed name and exactly three server-generated seal candidates after an actual completed preview. It calls `BackgroundGeneration.readInTransaction()` in the same bounded transaction, preserving the current account/session/legal checks, complete protected intake/safety history and actual preview call/cost provenance. It uses the real database account name for `same_as_user`; neither dimensions nor an authorization claim comes from the naming command. Names preserve trimmed NFC spelling and case, with unsafe input rejected before trimming. Name rejection retains its category; missing English alias mapping remains `SEAL_CANDIDATES_UNAVAILABLE`.

New writes require both the server vocabulary bundle and `PLATFORM_COMPANION_IDENTITY_REVIEW_FILE`. The closed review manifest binds `bundleRevision`, `bundleDigest`, `coverage:'complete_eligible_level_one'`, `reviewerUserId`, canonical UTC `reviewedAt`, `reviewEvidenceRef`, `tierOneSourceRef` and its exact `reviewDigest`. Coverage is a human attestation that the loaded eligible character domain includes every qualified name initial after exclusions; a tiny subset cannot meet that product requirement. Parsing, reference strings and hashes cannot certify this assertion, vocabulary review or English reading/meaning associations. Those must be supplied and reviewed outside the application; no real assets or approval are provided here.

Migration 037 creates an empty identity policy table. Every new save checks its exact bundle/review binding, database activation time, active organization, actual staff reviewer with an active `content_reviewer` role and actual staff activator with an active `ops` or `org_admin` role in that organization. The policy and authority rows remain locked until the caller transaction completes. Missing, mismatched, future or revoked authority is unavailable. There is no activation endpoint, startup seed or automatically approved test resource.

Migration 038 retains exact non-user server asset snapshots and stores the name, three candidates, source/preview binding and account name at save in AES-GCM ciphertext. Canonical operation input is separately encrypted with actual operation/owner/revision AAD. New operations use the expected naming revision; repeated identical operations return the current saved draft and the original applied revision. Different displayed spelling under the same operation conflicts even when the comparison key matches. Concurrent saves cannot overwrite one revision. Responses are returned only after confirmed COMMIT; lost confirmation is recovered with the same operation under a valid session.

Private reads and identical retries authenticate and recompute the saved candidate snapshot against its recorded assets and actual preview, so changing/removing current server configuration does not redraw historical choices. Corrupt database snapshots or private ciphertext fail closed. `fromConfiguration()` reads the bounded optional server files; invalid current files disable new writes while saved snapshots remain readable. Historical recovery does not approve that resource for a new save or future birth. Handling policy changes at birth remains part of the future birth implementation.

Migration 042 adds a separate encrypted seal selection and exact-operation history. `readSelection()` returns the current identity revision, the monotonically increasing selection revision and the selected character, or `selectedSeal:null` when no selection is eligible. A new selection requires both the expected name revision and expected selection revision, an actual current candidate, and the same currently activated vocabulary/review as the saved candidate snapshot. A client-supplied character does not supply asset review or birth permission. The selection and its request are encrypted with their actual owner, row and selection revision as AAD.

Changing the name invalidates a previous selection without resetting its revision. Changing the name back cannot revive that selection. Exact operation retries return current state together with the original applied revision; they cannot overwrite a later choice. Historical reads and retries authenticate the saved captures and preview evidence even when current resource configuration is absent, while new writes still require current authority. The student-shaped types in `packages/platform-contracts/src/companion-identity.ts` are a transport vocabulary, not an HTTP route or authorization assertion.

This service is internal and unexposed. It keeps `awaiting_name`, creates no room/event/letter and makes no new model call. Name edits are initial candidate preparation, not the unimplemented shared three-reroll allowance or post-birth rename/reseal flow. Inspiration names, arbitrary English-name mapping, actual reviewed character assets, main-room/turn foundations, birth, lettering and student UI remain subsequent work. Fictional PostgreSQL authority fixtures test these boundaries without establishing resource quality or student release.

**Public naming prerequisite:** 02 §10.2 and 05 §2.1 require all pre-birth free text, including a proposed name, to be persisted and safety-graded before it advances the ceremony. The internal naming validator is not that detector. Existing onboarding claims, usage, responses and followups are bound to actual intake text operations and their intake revision; wrapping a name as `extra` would change the source of its already completed preview. Public naming therefore requires a separate authenticated durable name source and safety adapter, not a synthetic intake claim or a client-supplied level. Only a verified full L0 source may supply a new identity draft. L1/L2 sources need captured fixed resources, presentation, acknowledgment and explicit continuation; handling them never converts them to L0 or reuses them as a name. Keyword no-hit remains unavailable under the current detector protocol. Selection and birth must check the combined intake and name barriers when that source exists. Neither this migration nor the shared types open a student naming endpoint, seed a reviewed detector, or advance the intake cursor.

### Independent companion-name safety foundation

`CompanionNameSafety` owns a concrete source separate from onboarding. Migration 043 gives each actual completed preview an independent entry revision and immutable encrypted submissions. `submit()` retains the exact bounded UTF-8 string, including empty, multiline or semantically invalid names, before classification or name rules. A closed operation replay returns the saved source and current entry state; different raw text under the same operation conflicts. It neither rewrites the original intake nor issues an identity, model or birth grant.

`claim()` binds the current real session to a fresh encrypted generation capture. `process()` fences the real execution token, lease, account authorization, complete source capture and active detector at each accepted request and result. Full classification also requires the matching actual admitted, completed model-call record; an injected guessed L0 cannot satisfy that check. The server runner creates its usage adapter after the concrete process creates the token. Reviewed L2 keywords require no provider or model quota; a keyword no-hit with unavailable, refused, incomplete or failed model output remains pending/unavailable. Reads do not start a model. Re-login can claim pending work with a new actual session; it cannot substitute that session into an in-flight old generation.

Migration 044 extends the existing counts-only safety ledger with a closed `onboarding`/`companion_name` shape and two concrete source foreign keys. Both sources share one account lock, UTC daily call count and all historical unresolved usage. A new name, generation or day cannot erase uncertainty. Actual completed classification can remain valid when token counts are missing or invalid, while that uncertainty blocks subsequent paid safety calls. Late measured usage is saved under its accepted call binding even after execution authority expires; completion accounting grants no new request.

`apply()` is a separate transaction after classification COMMIT. Only the latest full-L0 intent can reach current reviewed vocabulary and actual account-name validation; other pending or risky name sources remain barriers. Semantic rejection is durable, preserves the classification and does not trigger another model call. Newly applied identities have real source provenance; old internal drafts receive no fabricated safety backfill. Historical captures must match the actual immutable save receipt and recorded assets, rather than merely agree with another copy.

This is an internal foundation, not public O7/O8. Captured fixed resources, publication, same-session presentation/acknowledgment/explicit continuation, cross-source public selection barriers and historical preview recovery still need integration. Current source validation requires the original completed preview and intake/current legal authority; it must not be weakened into permission to process a stale source. No public naming route, reviewed production resource, safety event delivery, room, birth or first letter is supplied by this foundation.

### Durable companion draft preparation

`CompanionDraftPreparation.prepare()` composes the full intake check with its writes in one bounded PostgreSQL transaction. It creates a real `drafting` companion, an encrypted answer/reference snapshot and one encrypted `pending` generation task. The task binds the actual intake ID/revision, account auth version, rule versions and server route snapshot. The companion UUID seeds rule metadata; fallback prose and its `generatedBy` tag are discarded. Replaying preparation verifies both protected snapshots after rechecking the whole safety history, current source and session. Concurrent retries return the same durable IDs. Missing model route configuration returns unavailable before any new drafting rows are committed.

Before a new preview, the ordinary fingerprint index checks the initial dimensions, quirks and ink against other companions. A collision redraws only the quirks once, using the actual companion UUID; dimensions, ink and fallback prose stay fixed. Migration 036 saves this zero-or-one draw on the task and authenticates draw one in the encrypted seed. Existing zero-draw seeds retain their exact encoding. Replays restore the saved draw without another collision check. This is best-effort variation, not globally unique personalities or a user reroll.

Migration 032 initially supports `drafting`/`pending` and revision zero; migration 033 adds the internal generation transitions below. Preparing a task still grants no runtime lease, cost reservation, provider request, generated preview, birth, room or memory. The student request composition below separately records its accepted intent. Configuration availability and a saved task are not execution authority. There is no placeholder success response or automatic rule preview.

The pure `parseCompanionModelPreview`/JSON codec accepts only a summary and exactly three samples, snapshots and freezes them, and rejects malformed/truncated output, duplicate decoded JSON keys and extra fields. Its 16 KiB UTF-8 ceiling is an internal transport bound. Structural parsing establishes neither provider completion nor factual, identity or paid-suggestion approval.

### Internal background preview generation

`BackgroundGeneration.generate()` consumes an actual prepared task under a fixed authenticated session. It verifies the full encrypted intake history, current legal/student/email policy, exact source revision, original auth version and sealed route. It claims one separate 60-second `background` runtime lease, with at most three sequential model requests. `PLATFORM_COMPANION_GENERATION_PROVIDER=openai` and `OPENAI_COMPANION_GENERATION_MODEL` must both be explicit and available. Neither defaults to ordinary chat. Changed routes, disabled providers, absent prices/policies, hard-budget blocks or an unavailable degraded route return unavailable; they do not produce a rule preview. An old pending task sealed against an ordinary chat model needs a real re-preparation flow before dispatch, which is not implemented by silently rewriting its seed.

Each attempt uses the actual `runtime.streamChat` background path, with tools, attachments, client persona and continuation disabled. Server style metadata supplies the context; raw intake text and user facts are absent from this preview prompt. The strict OpenAI adapter issues one request with `store:false`, a 1,536 output-token limit and a 15-second deadline. It buffers the complete validated result until accounting finishes. The original schema is checked locally; the wire projection omits unverified string-length keywords while retaining array cardinality. Loopback protocol tests do not establish paid API entitlement, production schema compatibility or model quality. See the [official Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs).

The service commits a prepared call and CostGuard reservation before real admission. Admission rechecks the exact live task/runtime lease, account/source/legal history, sealed route and fresh money decision, then starts the actual provider request under those locks without awaiting HTTP headers under the transaction. Terminal receipts preserve actual usage or conservative estimates even after cancellation, auth reset or lease loss. Migration 034 adds a durable accounting-only dispatch-risk marker: a request may escape before an admission COMMIT fails or the process dies. Such reservations expire into an estimated `dispatch_uncertain` ledger entry, never a free release. This marker and the cost table's accounting timestamp are not proof of model admission; publishing a preview still requires the actual admitted and terminal call records. A positively observed zero-launch rejection can clear a still-reserved risk marker. CostGuard operations reconcile lazily; the worker also invokes accounting-only reconciliation at startup and every 15 seconds, including after session revocation. Production accounting and billing reconciliation remain rollout work.

`checkCompanionOutput` applies one scoped forbidden-expression configuration and preview checks for identified identity, outcome, paid, immigration, execution, numeric and entity claims. Preview facts and source references must be empty. Unmatched statement clauses require review. Only `passed_rules` can be persisted. Its assurance is explicitly `deterministic_rules_with_heuristic_fact_detection`: free natural wording is preserved, and rule passing is not a semantic proof. The separate exact-span grounding helper establishes neither source authority nor complete fact detection. Human bilingual product evaluation and source-authorized ordinary conversation checking remain release work.

An actually admitted timeout, or three actually completed outputs rejected by the local preview/content checks, permits the specified `generatedBy='fallback'` template. The template passes the same output checker. The background adapter records a failed `invalid_format` outcome only after a valid completed assistant response and normal stream EOF, when local JSON/schema validation fails. It emits no rejected text. Migration 035 preserves this bounded evidence separately from successful completion, alongside actual admitted/terminal call and cost records; legacy failed rows gain no inferred proof. Each retry rechecks prior validation and accounting at request preparation and dispatch admission. Arbitrary interruption, cancellation, refusal, provider error, malformed protocol envelopes, absent admission/accounting or disabled calls do not meet the fallback condition. Migration 033 stores only fixed rule identifiers for rejected output, not its text. Passing model or eligible fallback prose is encrypted in one owner/source/task-bound revision, and only then transitions to `awaiting_name`. Reads authenticate and revalidate the protected source/provenance; already-completed previews are reused without another call or budget check.

Migration 040 adds authenticated encrypted checkpoints only for model output that passed the actual preview checker. Validation and checkpoint persistence commit together, binding the original source, actual call IDs, policy, and settled accounting receipts. A later expired-lease takeover uses the same generation and a fresh lease token: it rechecks and publishes the original checkpoint without another model call. No-call interruptions can safely continue; terminal invalid outputs resume only the missing eligible attempt. Prepared/admitted calls without confirmed terminal receipts, or paid completions whose output was never saved, become `uncertain`. Neither an expired lease nor a cost ledger proves a usable result. Both task and runtime leases renew together; old tokens cannot revive themselves.

### Student preview requests and background recovery

`POST /companion/drafts` accepts only `{operationId, expectedRevision}` under the real student session, current legal/email policy and full protected intake history. `CompanionEntry.accept()` atomically writes the drafting entity, encrypted original accepted request and reference-only outbox in one bounded transaction, then returns HTTP 202 and actual state. The request retains the original session hash only inside owner/source-bound ciphertext. Identical retries return the same task and operation; another intent must read the existing task. Changing sessions does not rewrite accepted authority. Migration 041 seeds no account, approval, price, budget, policy or model result.

`GET /companion/drafts/current` is a read-only account projection: intake required, not prepared, actual generation state with any durable hold, or the stored summary, three samples, ink and model/fallback tag. It creates no task and calls no model. Original authorization loss is visible as a hold, and is not automatically requeued. Configuration holds may be rechecked; damaged or unknown records require review. The page first reads, then submits once after actual intake completion, polls only observable pending/running work, and aborts observation on account changes or unmount. A lost POST confirmation is followed by a read, never treated as proof that nothing was accepted.

The API and worker use a separate `${PLATFORM_QUEUE_NAME}-companion` BullMQ outbox. Notifications contain only `requestId` and `taskId`; their job ID/name and closed payload are checked. The worker decrypts the real accepted database snapshot, locks the user before source/request rows, and rechecks the original session and current source at each model/publication boundary. A notification cannot choose a new identity or generation. Redis loss is repaired from PostgreSQL, an invalid notification is isolated rather than blocking other users, and browser disconnects do not cancel accepted work. Known PostgreSQL rollback errors for lock contention, deadlock or serialization failure leave the original outbox eligible for another reference-only notification, which rechecks the original session, source and durable core state. Connection loss and operation deadlines do not qualify. Worker startup and its periodic recovery reconcile conservative expired costs independently of model or session availability; this accounting path grants no execution permission.

Completed previews remain readable with the model disabled. Eligible rule fallback is clearly labeled; disabled calls and uncertain outcomes never become fixed success. User-authorized fresh execution retries, shared rerolls, naming/seal selection, birth, first letters, rooms and shared memory remain unfinished. These changes are unreleased; no production migration, deployment or paid model call was performed.

### Internal dollar cost reservations

`CostGuard` and migration 031 add empty server-managed price/policy tables, exact micro-dollar arithmetic, durable token-call reservations and a cost ledger. This initial scope supports ordinary chat/background input and output tokens. Prices, an active approved global policy and a per-owner budget policy must all exist; none is seeded or inferred from student status. Money policies and their audit actor are accounting configuration, not enrollment, legal consent, source ownership or execution approval. Audio, cached-input pricing, entitlement quotas, necessary-call exceptions and integration with the existing paid entry points remain subsequent work.

`reserve` returns an accounting decision; it cannot launch a model. Future callers must verify the actual source, identity, legal consent and current execution lease, obtain a fresh `reserveInTransaction` decision (including same-ID retries), apply any degradation and use `admitInTransaction` in that same bounded transaction at the actual launch boundary. Global month/day and owner hard budgets include pending cost estimates; owner soft/day degradation uses settled ordinary token cost. Settlement may record spend after an auth version or lease expires without allowing a new request. An unadmitted expired reservation is released; an admitted request is conservatively charged its saved estimate until actual usage is known. Pending reservations carry into a new UTC period; settled costs, including expired-call estimates and late corrections, are attributed to the actual admission period. Missing/invalid counts are never a zero report. Known actual zero counts are recorded as such. Late reports replace estimates idempotently using the saved price snapshot. Account deletion anonymizes financial rows; subsequent owner-bound settlement refuses that removed identity and retains the estimate. Coordination of deletion with in-flight requests remains a dispatcher integration requirement. Cost-only records contain IDs, routes and counts, without request text, keys or copied execution tokens. Crisis fixed responses continue outside this guard.

The current conversation-message route delegates its existing single-assistant pipeline to `ConversationTurns.submit`. HTTP authentication, account headers, request limits, body-object and route-ID parsing remain in `app.ts`; field validation stays at its original point in the service. The service preserves message preparation, owned history, audio provenance, tools, approvals, leases, accounting and final persistence. `SseTurnSink` owns HTTP frames and connection lifecycle, while `CollectingTurnSink` supports an in-process caller without HTTP. Callers must supply their captured account recheck; the service does not authenticate a caller or grant execution permission. This extraction retains busy responses and cancellation on disconnect. Student groups, speakers, queued interjections, background continuation and Discord remain later product steps.

Reviewed MCP connections use a server-only catalog, real discovery, per-user grants, immutable task approvals, durable started receipts and private result reads. The catalog is empty by default; this is not third-party OAuth or a live Gmail integration. See [MCP setup and boundaries](../../docs/platform/mcp.md).

Standalone transcription uses its server-owned route, the existing authenticated endpoint, owner checks and runtime lease/usage boundary. Its multipart request accepts only one audio `file`; a speech-only provider cannot authorize transcription. Import does not automatically persist raw audio or a transcript. Production queue recovery, deployment binding and storage readiness remain separate work; see [deployment plan](../../docs/platform/deployment-plan.md).

Audio files in ordinary chat have a separate reviewed path. `POST /uploads/:id/transcriptions` accepts only a UUID `clientRequestId`, uses the explicitly configured local `faster-whisper` / `whisper-tiny` adapter, and saves an immutable receipt tied to the owner's upload and exact SHA-256. It accepts at most 20 MiB and 120 seconds. A completed retry returns that receipt without repeating ASR. `GET /uploads/:id/transcriptions/:clientRequestId` and `GET /audio-transcriptions/:id` recover completed results; a 404 does not establish that an earlier request stopped. Account/session, cancellation, source bytes and the voice lease are rechecked before persistence. There is no alternate or paid ASR fallback.

To send audio in chat, retain its `attachmentIds` and explicitly select `audioTranscripts: [{receiptId, reviewedText}]`. A message accepts at most two reviewed transcripts, each at most 8,000 characters. The service verifies ownership and source bytes, saves the selected text independently of the original receipt, and supplies it as `untrusted_audio_transcript` source text. Raw audio is excluded from the chat provider's attachments. User review selects text; it does not establish speaker identity, real experience, skills or tool authorization. Completed receipts remain readable and usable when ASR is disabled. Provider `chatAttachments` metadata describes this route and supported direct file types; video extraction is not implemented.

Integration tests use synthetic runtimes or injected Responses fixtures and never contact commercial model services.

## Workbench admission

`PLATFORM_ENABLE_WORKBENCH` defaults to `0` and strictly accepts `0` or `1`. With it closed, shared task admission rejects new `browser`, `cli`, `workflow`, `image`, `video` and `mcp` jobs with `403 WORKBENCH_DISABLED` before input preparation or external work. This covers `POST /jobs`, `POST /mcp/tasks`, Agent preparation and creation, and new tasks bound to a confirmed goal plan. An owned retry and a pending approval's first transition to `approved` also require the switch. Request bodies, headers and model tool arguments cannot enable it.

Explicit `1` restores internal non-production task preparation; provider availability, ownership, user grants, approvals, leases and current consent still apply. It does not identify a staff user, open the Web workspace or permit paid calls. Until employee workbench authorization is wired, `NODE_ENV=production` rejects `PLATFORM_ENABLE_WORKBENCH=1` at startup. The separate staff metadata boundary below already uses real database roles. API and worker should use the same configuration; an already accepted job is governed by its saved execution policy and model admission.

Closing admission does not stop accepted queued/running jobs, outbox delivery, worker execution or interrupted-job recovery. Owned reads, cancellation, approval rejection, duplicate decisions on an already approved task, and reuse of an existing goal-plan binding retain their existing checks. Agent omits `create_job`, `prepare_browser_task`, `prepare_mcp_task`, `get_execution_capabilities` and `propose_goal_plan`, removes their planning instructions, and rejects direct callback attempts; owned saved-source readers remain available.

The HTTP student channel additionally closes all new `/jobs` kinds, including speech, and eligible retries and first approvals. New generic workflow/goal-plan definitions, edits and first draft confirmations require internal workbench mode. Owned historical reads, cancellation, rejection, already confirmed plans and existing bindings retain their checks. Shared worker execution still uses its saved policy; an HTTP feature switch does not rewrite accepted work.

## Student channel and server routing

`src/model-routing.ts` selects each of `chat`, `agent`, `realtime`, `transcription` and `speech` from an optional server-owned provider binding, parsed from `PLATFORM_<PURPOSE>_PROVIDER`. The resolver requires that exact provider to be enabled, support the requested capability and declare one configured model for it. A missing binding, unavailable provider or ambiguous model raises `503 MODEL_ROUTE_UNAVAILABLE` internally (student HTTP/SSE presents `CAPABILITY_UNAVAILABLE`); there is no first-enabled-provider, cross-purpose or paid fallback. Availability uses the same catalogue decision without contacting a provider. Speech and realtime defaults also require a valid server-declared voice.

`PLATFORM_EXPOSE_PROVIDER_DETAILS` strictly accepts `0` or `1`, defaults off, and is effective only with `NODE_ENV=development` and internal workbench mode enabled. It does not grant a staff role, client override or permission to call a model.

`GET /features` returns `{version:1,workbench,providerDetails}`. Anonymous `GET /capabilities` returns a boolean map and the selected chat route's actual attachment limits. `GET /capabilities/details` requires a real session, the matching account header, verified email when configured, and the effective development diagnostic flag; otherwise it is denied. Internal mode is a development setting, not staff authorization. No HTTP message request can override `provider` or `model`, including in internal mode.

Student conversations accept only `title`; ordinary messages accept `content`, optional `attachmentIds` and reviewed `audioTranscripts` references. Their mode is server-fixed chat and they do not inherit an old saved user-selected persona. Internal requests can retain legacy mode/persona. A standalone `goalPlanStep` uses the original confirmed analysis checkpoint, with its stored provider/model/hash rather than the current ordinary chat route. It cannot be mixed with new content or selection fields.

The shared `student-api.ts` contracts and `student-projection.ts` functions construct public conversation, message, transcription, voice, aggregate usage and historical task/plan data without model-selection metadata. They preserve user text, source hashes, provenance, accounting facts and stored internal records. Projection neither rewrites approval/definition hashes nor changes private worker policies. Arbitrary user material and external MCP schemas/results are source data and are not redacted by matching words such as “model”. Student SSE retains the existing single-assistant `start`/`delta`/`done` receipt protocol, emits tools as `{messageId,name,status}`, and omits tool inputs/results, approvals and usage events. The projecting sink leaves cancellation, heartbeat, settlement and persistence order intact.

Realtime sessions accept only optional `conversationId`, standalone transcription only `file`, and internal speech only `text`; their model, voice and supported patient turn taking are fixed by the server. All mutating routes, including public account actions, require an `Origin` included in `PLATFORM_ALLOWED_ORIGINS`.

`/live` only checks the responding process. `/ready` requires the database's migration ledger and required schema presence; its HTTP status depends on data readiness, allowing saved content and direct chat to remain usable when task execution is degraded. `/execution-ready` additionally requires a read-only Redis observation and a fresh matching worker process report. Public responses contain only fixed states and a check timestamp, never cross-user counts, queue names, instance IDs or connection details. See [runtime checks](../../docs/platform/operations-readiness.md).

Private requests additionally require `x-companion-account: <window-confirmed user UUID>`. The server authenticates the Cookie first, then compares this assertion with that request’s real session before domain reads/writes, request counters or provider work. It is not a credential or an identity selector: anonymous requests remain 401, missing assertions return 409 `ACCOUNT_CONTEXT_REQUIRED`, mismatches return 409 `ACCOUNT_CONTEXT_CHANGED`, malformed/duplicate/conflicting assertions return 400. `GET /auth/me` remains the authenticated bootstrap exception; logout and email verification require the assertion. Only native-byte `GET/HEAD /uploads/:id` and `/artifacts/:id` accept the equivalent `expectedAccount` query (including Range/download), and ownership still applies. See [cross-window verification](../../docs/platform/verification.md#跨窗口账号断言与旧资源清理).

## Account email and recovery

`GET /auth/options` returns the public `AuthOptions` shape `{emailActionsEnabled,requireVerifiedEmail}`. These booleans describe server configuration and access policy; they do not claim that an email was sent or delivered. Register/login/me identities include `emailVerified`. New and pre-migration accounts remain unverified until a real challenge is consumed; migration does not backfill mailbox ownership.

| Route | Authentication and exact input | Response |
| --- | --- | --- |
| `POST /auth/password-reset/request` | Public; `{email}` | `202 {accepted:true}` when account email is configured |
| `POST /auth/password-reset/complete` | Public; `{token,password}` with password 10–256 characters | `200 {ok:true}`; clears the current session cookie |
| `POST /auth/email-verification/request` | Current account session; `{}` | `202 {accepted:true}` when account email is configured |
| `POST /auth/email-verification/complete` | The same owner account's session; `{token}` | `200 {user}` with current verification state |

Unknown account-action fields are rejected; clients cannot select an owner, redirect, sender or provider. Reset requests for an unknown email or an exhausted target allowance return the same accepted response as an eligible account. Neither request response issues a token, URL, account identifier or session. `202` means the request was accepted: a challenge may not have been queued, the worker has not necessarily sent it, and the recipient has not necessarily received it. Delivery processing happens outside the request. Missing/disabled mail returns the same safe `503 ACCOUNT_EMAIL_UNAVAILABLE` for valid known and unknown emails; database failure returns `503 ACCOUNT_ACTION_UNAVAILABLE` without raw diagnostics.

Account email is separately opt-in with `PLATFORM_ALLOW_ACCOUNT_EMAIL=1`. It requires server-only `RESEND_API_KEY`, `PLATFORM_ACCOUNT_EMAIL_FROM`, `PLATFORM_ACCOUNT_WEB_ORIGIN` and `PLATFORM_ACCOUNT_EMAIL_ENCRYPTION_KEY`. The encryption key is a dedicated 32-byte secret encoded as 64 hex characters, shared by API and worker. The web origin must be an exact member of `PLATFORM_ALLOWED_ORIGINS`, without paths, credentials or query strings; non-loopback origins require HTTPS. These values never belong in `VITE_*`, source, browser responses or logs. The example leaves mail disabled and secrets empty. This switch is independent of the commercial-model switch.

Development defaults to `requireVerifiedEmail:false`. Explicit `PLATFORM_REQUIRE_VERIFIED_EMAIL=1` requires complete account-email configuration. `NODE_ENV=production` always requires verified accounts and configured email; a production `PLATFORM_REQUIRE_VERIFIED_EMAIL=0` is rejected. An unverified production session can read its own identity, request/complete verification and log out, while ordinary workspace reads and mutations return `403 EMAIL_VERIFICATION_REQUIRED` before provider or task execution.

Migration `012_account_actions.sql` adds mailbox-verification time, account/session `auth_version`, challenges and an independent encrypted mail outbox. A challenge uses 32 random bytes encoded as a 43-character base64url token; its authoritative row stores only SHA-256, owner, purpose, account version, timestamps and consumption state. Links expire after 15 minutes. Repeated requests retain prior valid links until expiry or successful consumption. Consumers lock the user first and conditionally lock the matching challenge, then complete the change in one transaction; independent API instances cannot consume the same challenge twice. Email verification also requires the current server-authenticated user ID to match the challenge owner, so a mailbox link alone cannot promote someone else's pre-registered session.

Password reset changes the password, increments `auth_version`, deletes all that user's sessions, and revokes their outstanding challenges and unsent encrypted messages atomically. Login binds a session to the version used during password verification, and subsequent authentication requires the account/session versions to match. An old-password login cannot acquire a valid session after a concurrent reset. Reset completion does not automatically log in or verify an email; the user signs in again. Verification consumes/revokes that owner's remaining verification challenges and messages without changing the password or auth version.

Mail links use the configured application origin and `/#account-action=<purpose>&token=<secret>`. The frontend keeps the received secret in memory after clearing the fragment and submits it only after explicit confirmation; GET/page loading does not consume a challenge or change a password. An expired, used, malformed, wrong-purpose or wrong-owner validly shaped challenge returns the same `400 ACCOUNT_ACTION_INVALID`; invalid new passwords return `400 INVALID_REQUEST`.

The outbox encrypts the fixed `from/to/subject/text` payload with AES-256-GCM; plaintext mail and tokens are not stored in the outbox or logged. The existing worker runs a separate account-email loop. PostgreSQL `SKIP LOCKED` and 30-second leases coordinate workers. Dispatch uses only `POST https://api.resend.com/emails`, server Bearer authorization, redirect rejection and the outbox UUID as `Idempotency-Key`. Each retry preserves the same key and payload and is allowed only during the challenge's 15-minute lifetime. Resend documents a 24-hour idempotency window; the platform does not extend its own deadline to match it. [Send Email](https://resend.com/docs/api-reference/emails/send-email), [Idempotency Keys](https://resend.com/docs/dashboard/emails/idempotency-keys).

Provider acceptance marks `sent`; it is not proof of recipient delivery. Sent, expired, revoked and invalid encrypted payloads erase their ciphertext. Retries store only a fixed error code, and no configured email worker makes no database or network calls. Real sender-domain/account configuration, email delivery and production capacity still require validation.

## Reusing private artwork

`GET /artifacts/:id/reference-attachment` resolves a persisted PNG, JPEG or WebP artifact to its existing private upload. The artifact, upload and source job must all belong to the current account. The response supplies the existing attachment ID, name, MIME, size and session-protected upload URL, together with the source artifact/job IDs. Reading this reference does not copy a blob, create an upload or job, call a model, change the source artwork or make its URL public. It remains usable when model calls are disabled, so a user can prepare a draft without starting generation. Completed private results from a partially completed parent task can also be selected explicitly.

Reference images must be non-empty, at most 20 MiB and consistent with their persisted MIME and byte-size metadata. The service checks PNG/JPEG/WebP file signatures after reading the original private bytes. This is a signature check, not full image decoding or a guarantee that a supplier accepts the image dimensions or account/model combination.

New image/video jobs continue to submit `attachmentIds` through the existing owner-checked reader. Before accepting a task, the API checks the selected provider's `referenceImages` capability for that task kind, distinct image count, supported MIME types, combined byte limit, file signatures and provider binding. At most four distinct references totaling 20 MiB are permitted, with lower provider limits enforced. Providers without reference support, including the current ComfyUI template path, reject attachments for image/video generation. Inputs without references retain their normal creation behavior. The runtime rechecks references before dispatch; provider capability metadata does not prove paid account entitlement or model quality.

For OpenAI image jobs, an attached private image selects the existing image-edit adapter rather than ordinary image generation. Ark video and fal use their declared private-reference bindings. Each edit creates a new job and new output artifacts; the source remains available. No client-facing provider URL or public transfer URL is required.

Agent mode provides `get_artifact_reference(artifactId)` using the same ownership and file checks as the GET endpoint. `list_jobs` supplies candidate artifact IDs; the reference tool returns an attachment ID that `create_job` can use. Tool schema allows up to ten distinct attachment IDs for the existing general task interface; server parsing enforces at most four for image/video references, and media creation applies the same provider/content checks. If a media request omits its model, creation freezes the declared default for that capability before model-specific preflight; server-driven ComfyUI templates retain their existing model-free configuration. Resolving a reference grants no new creation authorization. Image/video jobs keep their existing queued behavior after an authorized creation request; browser, CLI and workflow tasks still require explicit approval.

## Reading private text results

Agent `read_artifact_text` and `GET /artifacts/:id/text` share the same owner-bound reader. Text/plain, Markdown, CSV and JSON are supported; browser artifacts use the separate approved-observation reader. Artifact, upload and source job ownership are checked before storage. Stored MIME and size must agree. Every read validates the complete source (at most 1 MiB) as strict UTF-8 and rejects binary signatures and unsupported control characters; it does not execute or render the file as active content.

For the first Agent call provide only `artifactId`. Optional `maxBytes` controls the returned page: default 12 KiB, maximum 16 KiB, distinct from the source-size limit. Returned `nextOffset` is a UTF-8 byte boundary; any nonzero offset requires the exact strong `version` returned by a previous read. GET query fields are `offset`, `version` and `maxBytes`; unknown fields, duplicate numeric fields and invalid values are rejected. A changed blob returns 409 rather than mixing versions. Serialized results remain below the Agent result limit and identify `provenance: untrusted_artifact`; a truncated page is not the whole file.

The reader uses pinned `stat`/`openRead` rather than unbounded `get`, waits for storage cleanup and propagates cancellation. Safe validation and lookup errors return as tool data so the model can correct its request; cancelled reads stop the tool loop. Resolving text neither copies a file nor creates a task or permission. Existing partial text results remain readable; a parent task need not have completed every step. Original large files remain available through authenticated downloads.

## Explicit voice history

The legacy/internal realtime page can explicitly opt into the current conversation's recent text. `POST /voice/session` accepts an optional owned `conversationId` and returns a bounded `serverContext`; client-authored history is rejected. The snapshot contains at most 20 completed text-only user/assistant messages, 8,000 Unicode code points per message and 24 KiB UTF-8 total. Whole messages carrying attachments/audio references are omitted, along with tools, unfinished messages, saved memories and voice excerpts; `truncated` discloses omissions. Context is not sent as issuer instructions. Fixed-session authorization and conversation existence are checked during issuance and before delivery. A newly bound voice session can only save excerpts to that conversation. This is not the student-group/interviewer context pipeline; see [handoff behavior and limits](../../docs/platform/voice-completion-status.md).

Voice excerpts are saved only by an explicit user action. They use a separate table and are never inserted as normal model messages, fed automatically into chat context, or presented as server-verified transcripts. Recording/transcription and speech synthesis do not themselves create voice-history records.

`POST /conversations/:id/voice-records` accepts the following fields; all other fields, including provider/model claims, credentials and raw vendor-event envelopes, are rejected:

```json
{
  "clientRecordId": "a-new-stable-uuid-per-excerpt",
  "source": "realtime_transcript",
  "role": "assistant",
  "text": "The final text selected by the user",
  "sessionId": "the-server-issued-voice-session-uuid",
  "attachmentIds": []
}
```

`source` is `realtime_transcript`, `transcription_excerpt` or `speech_excerpt`; the reported `role` is `user`, `assistant` or `unknown`. `sessionId` is required for realtime excerpts and disallowed for other sources. Optional attachments must be private audio uploads owned by the current user. A speech excerpt can associate the returned synthesis attachment with the exact text sent for synthesis. The server still labels its text as client submitted rather than asserting that its content was independently verified.

The response is `{record,created}` with HTTP 201 on creation or 200 for an identical retry. Each record has fixed `provenance: client_submitted`, source, reported speaker, text, authorized attachment metadata and server timestamps. Realtime records additionally retain provider/model privately from the server-issued session marker; student responses omit those fields. A stable `clientRecordId` is unique per user; reuse with a different conversation or excerpt returns 409. Reads return `{records}` in saved order. Reading, saving and retrying require the conversation owner's session.

Realtime issuance stores only session ID, owner, provider/model, timing metadata and an optional bound conversation ID. It never stores the short-lived credential, SDP, context text, or vendor-event payloads in its session marker. Associated session ownership and any remaining runtime lease are checked before creating a record. Explicit saving remains available for 24 hours after issuance, including after the user ends the connection; this does not extend the provider session or lease. An identical saved retry can still be retrieved after that window. Session metadata stays private; the platform does not expose a session-listing endpoint.

Limits are 8,000 characters/32 KiB of text per record, two audio attachments totaling at most 20 MB, 500 records/1 MiB of text per conversation, and 10,000 records/20 MiB of text per user. A feature-specific PostgreSQL advisory lock serializes cumulative limits across conversations without reversing chat's lease lock order. Deleting a conversation deletes its saved excerpts. Public-launch retention rules, account deletion and user-selectable retention remain deployment work.

## Task execution

CLI, browser and workflow jobs always start in `needs_approval`. Creating a task through an agent tool does not grant permission to execute it. Approval atomically changes the job to `queued` and inserts a PostgreSQL outbox record. The API dispatches outbox entries to BullMQ with generation-specific identifiers; workers claim each task under a database lock and hold a renewable lease. Results are saved only if the lease remains current and the task has not been cancelled. Each attempt is recorded separately.

Cancellation prevents publishing a successful result; it cannot undo an external effect that already happened. Runtime cancellation is cooperative and a database heartbeat aborts work whose lease was revoked. Known asynchronous video task IDs and fal/ComfyUI image task IDs are saved before polling and reused after interruption. An interrupted attempt without a safely resumable task ID becomes `uncertain` and requires user review before retry. Other provider failures stay `failed`, with safe error messages. No automatic retries issue additional paid requests.

An in-flight cancellation retains its execution lease until the worker confirms shutdown. Its API response carries `CANCELLATION_PENDING`; retry is blocked while cleanup remains pending. A `CLI_CLEANUP_UNCONFIRMED` result changes even a cancelled job to `uncertain` and blocks ordinary retry with `OPERATOR_REVIEW_REQUIRED`. CLI work interrupted by a worker crash receives the same operator-review requirement. The local operator must verify the specific container stopped before changing this incident; the service exposes no endpoint that pretends cleanup succeeded.

## Saved workflows and durable steps

Workflow templates are private reusable internal designs; student mode preserves owned reads and deletion while blocking new definitions and edits. `GET /workflow-templates` returns `{templates}`; `POST` and `PUT` return `{template}`; deletion returns `{ok:true}` and hides a soft-deleted template. Creation accepts `{name,description?,steps}`. Updates also require the current positive `revision`; concurrent edits return `409 WORKFLOW_TEMPLATE_REVISION_CONFLICT` rather than overwriting the accepted revision. Owner checks and the same session/Origin requirements apply to every operation. Saving a template requires no configured provider and does not create or execute a job.

Templates support one to eight explicit `chat`, `image`, `video` or `speech` steps with `provider`, `prompt`, optional `model` and bounded options. Limits are 100 active templates per user, 128 KiB per payload, 100 characters for names, 1,000 for descriptions and 20,000 per step prompt. A per-user database lock makes the capacity check atomic. Unknown fields, credentials and server connection settings are rejected, including inside nested provider input. The same parser validates plans supplied directly to job creation. Workflow options use the 128 KiB allowance; ordinary job options retain their smaller limit.

An image or video step may select up to four distinct earlier image results through `referenceImages: [{fromStep:0,imageIndex:0}]`. Indices start at zero and omitted `imageIndex` means zero. References cannot point forward, select a non-image step or duplicate an image. Provider binding is checked before saving and again before execution: Ark video uses `referenceMode` (`first_frame`, `first_last_frame`, `reference_image`), while fal uses `referenceField` (`image_url`, `image_urls`). These references read only this job's completed private receipts, never arbitrary uploads owned by the same user. The selected model must support the provider-specific binding.

Creating a workflow job freezes the reviewed goal, execution steps and capability-specific model choices independently of later template edits. Missing models are rejected except for ComfyUI, whose server template defines generation and is saved as a private execution snapshot with a public version binding. A configured ComfyUI template must declare `COMFYUI_OUTPUT_KIND=image|video`; the kind is hashed and new tasks must match it. New same-kind template files do not change saved tasks; changing the server or available output kind requires new review for unfinished tasks. Historical missing-kind snapshots remain readable but cannot authorize new execution; a genuinely completed workflow checkpoint may retain its old digest without replaying that step. Returned artifacts must match the declared MIME and actual image header or MP4/WebM video structure; video poster sidecars are excluded. Structural validation does not certify decoding or generation quality. Every attempt requires a fresh generation approval that includes the frozen definition hash.

Workers receive internal checkpoint callbacks, not a public endpoint for fabricating results. Before each new external call, the worker persists `started` under owner, generation, approval, definition-hash and live-lease checks. Each subsequent transition uses a compare-and-swap revision and keeps a metadata-only transition ledger. Completed text and artifacts are saved privately per step before later steps run; partial completed artifacts remain visible if the parent job fails. One step permits at most eight artifacts, 100 MiB per artifact and 200 MiB combined. Publishing references rechecks authorization after storage, removes proven unpublished blobs after rejection, and preserves committed blobs if the database acknowledgement is lost. Final parent success rechecks the live lease, current approval, frozen definition and completion of every step. Expired leases cannot be renewed by a stale worker.

Completed steps are reused without another model call, including when their provider is no longer enabled. A known asynchronous provider task is resumed by polling its saved handle after another approval; it never issues a replacement creation request. A confirmed terminal provider failure can start a new approved attempt while retaining its earlier ledger. A started or uncertain step without a known handle blocks ordinary retry with `WORKFLOW_REVIEW_REQUIRED`; the service exposes no force-replay endpoint for an unknown paid result. `Job.workflowSteps` reports step states and safe errors, and `workflowResumeAvailable` indicates whether a reviewed continuation is supported without exposing provider handles. Recovery preserves completed receipts and known handles and marks interrupted calls without handles uncertain.

## CLI model relay

An approved CLI task can use a server-configured OpenAI or installed Ollama model through a callback given only to its claimed worker. The API exposes no public model-proxy route. The disconnected Docker container receives no provider key or external model URL: its reviewed wrapper bridges the official Codex CLI's internal loopback requests over bounded stdin/stdout frames. Execution requires the isolated harness configuration and `PLATFORM_CLI_MODEL_RELAY=1`. The default OpenAI path additionally requires server credentials and `PLATFORM_ALLOW_PROVIDER_CALLS=1`; these commercial switches remain off by default.

For local inference, explicitly select `PLATFORM_CLI_MODEL_PROVIDER=ollama`, set `PLATFORM_CLI_MODEL` (or `OLLAMA_CHAT_MODEL`) and `PLATFORM_CLI_OLLAMA_BASE_URL` (or `OLLAMA_BASE_URL`). The endpoint accepts only literal HTTP `127.0.0.1` or `[::1]`, with an optional `/v1` path. Before every model request, the broker reads that server's bounded `/api/status` response and requires `cloud.disabled === true`. A missing, malformed or enabled-cloud status blocks inference. No commercial key is sent to Ollama, and the paid-provider switch can remain off.

Every request must match the task owner, CLI provider, current generation, live execution lease and current approved action. Creation fixes the model, model provider and normalized upstream-route fingerprint from server configuration, saves its execution policy, and includes the relay allowances in the approval. A conflicting client model is rejected. A later configuration change cannot substitute a different provider, model or route, or enlarge the approved allowances; current server limits can tighten them. Legacy approvals without a provider fingerprint remain bound to the original fixed OpenAI endpoint. Authorization is checked before dispatch, during the request and before returning its result.

Before a provider request, PostgreSQL atomically reserves `encoded request bytes + 1,024 + allowed output tokens` under a per-user advisory lock. This is a conservative usage allowance, not a tokenizer, dollar balance or billing guarantee. The defaults and server settings are:

| Scope | Default | Server setting |
| --- | ---: | --- |
| Requests across all attempts of one job | 16 | `PLATFORM_CLI_RELAY_MAX_REQUESTS` |
| Reserved usage across all attempts of one job | 131,072 | `PLATFORM_CLI_RELAY_MAX_TOKENS` |
| Reserved usage across a user's jobs per UTC day | 524,288 | `PLATFORM_CLI_RELAY_DAILY_TOKENS` |
| Output tokens per request | 4,096 | `PLATFORM_CLI_RELAY_MAX_OUTPUT_TOKENS` |

Requests are also limited to 256 KiB and responses to 8 MiB. An accepted request ID is unique per job generation and cannot be replayed automatically. Reservations are retained after failure or uncertainty; a new attempt does not reset the job allowance. The audit stores model, counts, reservation, status and safe error codes, without prompts, provider credentials or raw upstream errors. Official Codex's `client_metadata` and ordinary `metadata` are accepted for compatibility and stripped before forwarding.

The relay pins its upstream route, forces `store: false`, disables background execution and accepts only text context plus bounded local tools. OpenAI supports function and custom tools; the Ollama adapter accepts native function/namespace tools and rejects freeform custom tools, custom-tool replay and compaction items. Hosted tools and retained response/conversation references are rejected. Native Responses JSON or SSE bytes are buffered and validated for completion and bounded usage before being forwarded; this path does not deliver incremental upstream deltas to the CLI while generation is running. Upstream error bodies and response headers are not passed through.

The reviewed harness image includes FFmpeg and FFprobe for approved local media processing. Collected MP4/M4A, WebM and WAV outputs receive media MIME types only when their supported container headers match; this recognition does not prove full decoding, quality, duration or audio retention. Those claims require separate runtime checks. Output collection retains the existing size, file-count, ownership and link restrictions.

Cancellation, timeout and authorization loss abort upstream work, but do not prove that provider execution or charging was undone. Interrupted, malformed, oversized or otherwise unconfirmed results keep their reservation and use `uncertain`; provider 5xx responses are also ambiguous. Explicit provider rejection uses `failed`. Outstanding `reserved` or `uncertain` requests prevent a worker from publishing successful results, even if the harness returns normally. Worker errors preserve the same uncertain job state and require another review before retry. The stdio bridge retains structured safe broker error codes and waits for cancelled callbacks to settle rather than treating a closed client connection as successful settlement.

## Storage and scaling

Local private blobs and per-job workspaces default to `.local/platform/blobs` under the workspace root. Production uses the included S3-compatible adapter by setting `PLATFORM_S3_*`; bucket provisioning and access policies are explicit deployment work. The optional `object-storage` profile now uses SeaweedFS 4.48 pinned by its multi-architecture digest. MinIO's previous image could not be pulled, and its community repository is archived. Existing MinIO volumes are untouched. [SeaweedFS release](https://github.com/seaweedfs/seaweedfs/releases/tag/4.48), [MinIO project status](https://github.com/minio/minio).

From the workspace root, `pnpm infra:objects` starts this development-only store on `http://127.0.0.1:19000`. It uses its own named volume, precreates `companion-dev`, and initializes the fictional credentials `local-companion-s3-access` / `local-companion-s3-secret-only`. These public development values belong only to this loopback fixture. Telemetry, WebDAV, administration UI, embedded IAM and table services are disabled; the S3 endpoint requires signed credentials. No host data directories are mounted. The platform preview keeps its existing local storage; changing `PLATFORM_S3_*` does not migrate existing blobs.

HTTP delivery authenticates before touching storage and checks upload, artifact and source-job ownership. Full responses are streamed as 200; single closed/open/suffix ranges use 206 with exact Content-Range/Length, and valid unsatisfiable ranges return empty 416. Malformed, multiple or unknown-unit Range values are ignored and return full 200. HEAD ignores Range and opens no body. If-Range matches only a current strong ETag; mismatches, weak tags or dates cause full 200. The S3 adapter uses HeadObject plus GetObject Range/IfMatch, not upstream If-Range. Local reads pin a file descriptor and object reads pin a version. Cancelled clients tear down the read; short or oversized streams abort instead of completing with inconsistent bytes. Response headers remain private/no-store, with MIME, disposition and nosniff; downloads do not use buffered `storage.get`. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-14.2), [AWS GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html).

For the optional real-store regression, start `pnpm infra:objects`, then run `PLATFORM_TEST_OBJECT_STORAGE=1 pnpm --filter @companion/platform-api exec tsx --test test/object-storage.integration.test.ts`. It creates and cleans only its own random bucket and PostgreSQL schema, uses fictional credentials and refuses non-loopback endpoints. The default test run skips this opt-in store fixture. Real cloud access, production bucket policies, durability, upload streaming and concurrency sizing remain separate work.

API replicas share PostgreSQL sessions, request counters and outbox rows; worker replicas share the same Redis queue and database leases. A production deployment must explicitly configure database/Redis URLs, allowed origins and HTTPS cookies, use object storage, and route same-origin API traffic through its TLS ingress. Account verification/reset and shared limits now have tested implementations; real email delivery, usage billing/quotas, backups, retention and operational monitoring remain launch work. Request-counter load and the actual ingress identity boundary need independent production validation.

### Shared request limits

Migration `011_request_limits.sql` creates atomic PostgreSQL fixed windows; `013_account_action_limits.sql` adds anonymous recovery scopes. Protected routes authenticate the session, enforce verified email when required, then count the authenticated user ID. Session rotation and API restarts do not reset an account's allowance, and accounts behind the same network do not share protected-route counters.

| Scope | Default allowance | Routes |
| --- | --- | --- |
| Ordinary API | 120/minute | Other authenticated reads and mutations |
| Chat | 20/minute | Message generation |
| Speech | 20/minute | Text to speech |
| Transcription | 20/minute | Speech to text |
| Realtime | 4/hour | Voice-session creation |
| Control | 120/minute | Job cancellation, voice-session release, logout and authenticated email-verification actions |
| Anonymous | Public 120/minute; login 20/minute; registration 10/minute | Public features/capabilities, auth options and authentication |
| Anonymous email request | 10/hour | Password-reset request, keyed to the actual socket peer |
| Anonymous email consume | 20/minute | Password-reset completion, keyed to the actual socket peer |
| Email target/purpose | 3/hour | Reset or verification requests, with separate PostgreSQL windows per normalized-email digest and purpose |

The target allowance is shared across API instances and silently suppresses new mail after exhaustion; account-action requests still return the uniform `202`. It does not reset existing links or reveal whether an account exists. Anonymous HTTP limits return ordinary `429` and `Retry-After`. Authenticated verification retains the separate control limit as well as the email-target allowance.

Scopes are exclusive: generation does not also consume the ordinary API window. Controls have a separate bounded window, so exhausted ordinary/generation allowance does not block cancellation or release. Existing ownership checks, realtime usage checks and concurrent leases still apply. Invalid or expired sessions return 401 before protected quota writes. A denied request returns 429 with a positive `Retry-After`, exposed through CORS; unavailable counters return a sanitized 503 before providers or handlers run.

Anonymous subjects are canonicalized hashes of the actual socket peer, never cookies or arbitrary forwarding headers. Behind a reverse proxy the socket may represent the proxy itself; trusted ingress identity and edge abuse limits must be designed and tested before production. Health, static assets, preflight and unknown routes do not consume these counters.

Counter queries have a transaction-local PostgreSQL statement timeout (default 2000ms, trusted override 50–5000ms). The existing pool connection timeout is 5000ms; these are separate bounds, not an end-to-end HTTP deadline. Expired rows are cleaned in bounded batches with a separate timeout and `SKIP LOCKED`. Tests/configuration may supply trusted server policy overrides through `AppOptions.requestLimits`; request input cannot select policy. These limits count attempts, including authenticated requests that later fail validation; they are not billing or a global model-spend budget.
