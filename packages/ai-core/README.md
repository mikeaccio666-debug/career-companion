# AI provider and execution adapters

`@companion/ai-core` implements the shared platform provider contract. Model adapters use server configuration; browser and CLI adapters execute reviewed jobs supplied by the platform worker. The worker owns identity, attachment authorization, approvals, leases and durable result storage. These functions are execution primitives and do not replace those controls.

`local-transcription.ts` connects only to an explicitly configured literal-loopback Faster Whisper service with fixed `whisper-tiny`. It uploads bounded audio with a generated filename, validates bounded UTF-8 JSON, preserves empty silence results and supports transport cancellation; it never falls back to a paid provider. The independent service owns model loading, bounded decode and process reaping. Actual synthetic English/Chinese/silence inference and UI evidence are recorded in [verification](../../docs/platform/verification.md).

Verified against official documentation on **2026-10-05**. Tests include an actual Docker container and official Codex CLI using synthetic local Responses. They have not called a commercial model or submitted a real job application.

## ElevenLabs and a configured custom voice

`elevenlabs` provides speech generation through the same direct speech, reviewed job and durable workflow paths. It requires explicit server `ELEVENLABS_API_KEY`, `ELEVENLABS_TTS_MODEL` and `ELEVENLABS_TTS_VOICE_ID`, plus the existing commercial-call opt-in. The HTTP model set is `eleven_v4`, `eleven_v3`, `eleven_multilingual_v2` and `eleven_flash_v2_5`; unknown IDs and the realtime WebSocket variant are not inferred from their names. Single-speaker v4 is documented for Create speech. [Product guide](https://elevenlabs.io/docs/eleven-creative/playground/text-to-speech), [Create speech](https://elevenlabs.io/docs/api-reference/text-to-speech/convert).

The request uses the fixed ElevenLabs host, `xi-api-key`, MP3 output and the bound voice/model. Client input cannot replace these bindings, add a URL, change retention, supply synthesis settings or turn a professional clone into its instant-clone variant. Generic expression `instructions` are unsupported; the catalog states this so the webpage does not send them. Audio tags may be entered explicitly in text for supported models. The service's stored voice settings remain in effect.

Provider history is disabled in the request by default. ElevenLabs documents this zero-retention mode as Enterprise-only. A trusted server operator may explicitly set `ELEVENLABS_ALLOW_PROVIDER_HISTORY=1` after choosing to permit provider history; the adapter never switches this option after rejection, retries with another model or falls back to another provider. The global commercial gate remains off in the example. [Retention parameter](https://elevenlabs.io/docs/api-reference/text-to-speech/convert).

The voice is a server-reviewed shared product voice. A configured ID does not prove ownership, successful training, readiness or account access. Per-user private voice registration requires a separate authenticated ownership and permission model. This adapter neither uploads recordings nor creates/trains/clones a voice. v4 professional-clone support is rolling out by account; verify model and fine-tuning status before paid generation. [v4 capability](https://elevenlabs.io/docs/overview/capabilities/text-to-speech/eleven-v4), [Recording plan](../../docs/platform/personal-voice-recording.md).

Responses are bounded to 30 MiB and checked for MIME, declared/actual size and MP3 signature, with cancellation during headers and body reading. Synthetic transport and runtime fixtures prove dispatch and persistence contracts; they do not prove decoded audio, naturalness, real account permissions or realtime conversation. Commercial generation is a separate explicit evaluation.

## Local English speech

`kokoro` advertises `speech` only and declares `speechLanguages: ['en-US']`. Configure all three server variables: `KOKORO_BASE_URL=http://127.0.0.1:8880/v1`, `KOKORO_TTS_MODEL=kokoro-82m`, and `KOKORO_TTS_VOICE=af_heart`. Only literal loopback HTTP URLs and the fixed model/voice are accepted; clients cannot choose a server URL. It remains available with commercial calls disabled. Prepare and start the independent [local speech service](../../services/local-speech/README.md) explicitly; runtime requests never install packages or download weights.

The adapter posts a fixed four-field speech request, forwards cancellation and validates a bounded 24 kHz mono PCM16 WAV before returning bytes. Workflows use the same selected speech adapter, with platform-owned approval, leases and private artifact publication. This provider does not support transcription or realtime; explicit unsupported choices fail instead of falling back to OpenAI. Protocol tests use synthetic WAV bytes and actual loopback HTTP; the separate local model smoke validates genuine Kokoro inference on this machine.

## Render a page and execute reviewed browser actions

The browser adapter accepts a strict `options={url,actions?}` plan and creates a new headless Chromium process and nonpersistent context for each job. Readonly jobs return a bounded text snapshot, a form-masked viewport PNG and a structured `untrusted_page` observation. Reviewed plans may contain up to twelve click, fill, select or scroll actions; login, sensitive fields, agreements, uploads and final submission remain unavailable. Playwright documents nonpersistent context isolation and context-level HTTP/WebSocket routing in its [BrowserContext reference](https://playwright.dev/docs/api/class-browsercontext).

| Server variable | Behavior |
| --- | --- |
| `PLATFORM_ENABLE_BROWSER=1` | Enables browser reading; otherwise disabled. |
| `PLATFORM_ENABLE_BROWSER_ACTIONS=1` | Separately enables reviewed actions; both gates must be on. Default off. |
| `PLATFORM_BROWSER_EXECUTABLE` | Optional server-owned Chromium executable. Otherwise uses the installed Playwright Chromium. |
| `PLATFORM_BROWSER_TIMEOUT_MS` | Default 30,000 ms; accepted range 500–120,000 ms. |
| `PLATFORM_BROWSER_ALLOWED_ORIGINS` | Comma-separated **exact loopback HTTP(S) origins** for synthetic local fixtures, e.g. `http://127.0.0.1:4111`. Cannot allow metadata or another private network address. |

Normal destinations require HTTPS and publicly routable DNS results. Each GET/HEAD request and each redirect is checked, then Node connects to the checked IP while retaining the original TLS hostname. The reader blocks other HTTP methods, cookies, WebSockets, service workers, WebRTC and WebTransport. Chromium's own hostname resolution is disabled; HTTP resources are fulfilled through the checked reader. A temporary deny-all loopback proxy also rejects native preconnect/background HTTP traffic, with Chromium's implicit loopback proxy bypass removed. Its limits are 80 requests, five redirects per request, 2 MiB per decoded response, 8 MiB across responses, 64 KiB extracted text and a 4 MiB viewport PNG. Cancellation closes the browser and context and aborts pending reader requests.

Targets use an exact visible role/name or label. They must identify one visible native control: a link or explicit `type=button` for click, a text/search input or textarea for fill, or a native select for selection. Input limits are 200 characters per name/option label, 2,000 characters per fill value and 1–1,200 pixels per scroll request. No caller scripts, selectors, coordinates or keyboard input are accepted. Pinned element handles avoid a locator selecting a different node after inspection. See [Playwright locators](https://playwright.dev/docs/locators). A wheel is a requested input, and page code may consume it; it is not a guarantee of exact displacement. The executor waits for render frames before capture, and tests verify actual scroll effects on the fictional page. See [the Mouse wheel contract](https://playwright.dev/docs/api/class-mouse#mouse-wheel).

Actions require a fresh revision-zero journal, current authorization and a durable checkpoint callback. The runtime confirms `started` before dispatch; each resulting text/PNG/JSON observation is privately persisted and acknowledged before the next action. The platform binds checkpoints to the owner, reviewed plan hash, approval generation and live lease. Action executions return no duplicate final artifacts. A context cannot resume: any action that started followed by interruption or an unconfirmed receipt is held for review, and ordinary retry cannot replay that plan. Readonly retries retain their separate behavior. The platform can expose an approved private observation to the owning Agent without an external page fetch; page text and targets never provide instructions or permission.

Renderer isolation is static server-reviewed code with no interpolated user input. It disables cookie writes and native form submission, and blocks native submit/default controls at the click boundary. Initialization is checked before execution; an attempted form submission stops the action plan. This guard complements the network and semantic target checks rather than granting permission for automatic submissions.

Each task owns a public Playwright `BrowserServer` launched on a temporary loopback control endpoint; the endpoint is neither logged nor exposed. Cancellation of an active task aborts the reader and immediately calls that server's `kill()`, then waits for its physical process exit and control connection closure. Normal shutdown allows one second for `close()` before escalating only this owned server. Failure to confirm exit returns `BROWSER_CLEANUP_UNCONFIRMED`, and proxy cleanup still runs. Another task's browser is never selected or terminated. The public [BrowserServer API](https://playwright.dev/docs/api/class-browserserver) documents process ownership and termination.

Playwright's browser launch is not interrupted by an AbortSignal. Cancellation during cold startup waits for launch to finish or reach its maximum 15-second launch timeout, then reaps the newly owned process. Production supervisors still need a hard process lifetime limit and resource isolation.

Redirects are fetched by the reader before fulfillment. The snapshot records both the requested and final response URL, but Chromium's address bar and relative-resource base remain the original requested URL. This can reduce fidelity for redirected sites. Authenticated pages and sites requiring cookies or unsupported transports will not behave like a user's signed-in browser. GET-only access can still trigger a website's tracking or server-side behavior; this adapter promises restricted actions, not control over the site's semantics.

This is limited browser rendering and reviewed interaction, **not full computer use**. Public production workers also require OS/container memory limits and an enforced network egress policy. Application routing and Chromium flags are defense layers rather than a complete isolation boundary for hostile page scripts.

Chromium documents manual proxy routing and its implicit loopback bypass in the [official proxy design reference](https://chromium.googlesource.com/chromium/src/+/HEAD/net/docs/proxy.md). This worker uses a single global HTTP proxy without a direct fallback; the proxy never forwards requests or CONNECT/upgrade sockets.

## Execute a coding harness in a container

CLI execution is disabled until `PLATFORM_ENABLE_CLI=1` and an image are configured. For model-backed tasks the platform catalog additionally requires its provider-call gate, server key, explicit command and relay flag. The Docker image must already exist locally: the adapter inspects its immutable image ID and runs with `--pull=never`. See [Docker image inspect](https://docs.docker.com/reference/cli/docker/image/inspect/).

| Server variable | Behavior |
| --- | --- |
| `PLATFORM_ENABLE_CLI=1` | Enables the isolated runner. |
| `PLATFORM_CLI_IMAGE` | Trusted preinstalled image containing a reviewed Codex/OpenCode binary; no automatic image pull or install. |
| `PLATFORM_CLI_COMMAND` | Server-owned JSON argv array. Executable basename must be `codex` or `opencode`; user command/env options are rejected. Codex config/profile/model/feature override flags are rejected so argv cannot replace the reviewed wrapper policy. |
| `PLATFORM_CLI_USER` | Non-root numeric `uid:gid`. Defaults to the worker UID/GID, or `65532:65532` for a root worker. A non-root worker must use its own UID. |
| `PLATFORM_CLI_TIMEOUT_MS` | Default 120,000 ms; accepted range 500–600,000 ms. |
| `PLATFORM_CLI_NETWORK` | Must be `none`. Every other value is rejected. |
| `PLATFORM_CLI_MODEL_RELAY=1` | Uses the trusted Node stdio wrapper. Requires `JobExecutionContext.requestModel` and a Codex command. Without this flag the runner is only a disconnected command fixture; no model connection is supplied. |
| `PLATFORM_CLI_MODEL` | Server-selected model, falling back to `OPENAI_CHAT_MODEL`, then `gpt-6-astra`. Client job model overrides do not select the relay model. |
| `PLATFORM_CLI_EXTERNAL_SANDBOX=1` | Explicit server opt-in required for `danger-full-access`, `--yolo` or Codex's sandbox-bypass argv. Docker remains the execution boundary; the Codex inner filesystem sandbox is disabled. Never applies to a host CLI. |

Example server argv for an empty per-task workspace:

```json
["codex", "exec", "--json", "--skip-git-repo-check", "--sandbox", "workspace-write", "--ephemeral", "-"]
```

This is also the direct executor fallback. Codex ordinarily requires a Git repository and defaults to a read-only sandbox; its [official non-interactive guide](https://learn.chatgpt.com/docs/non-interactive-mode) documents these flags and stdin input. Nested sandbox support depends on the worker kernel/runtime. On the tested macOS/Colima runtime, the default Codex bubblewrap sandbox could not create a user namespace; the older Landlock option also rejected execution. Neither test produced a deliverable. With the explicit external-sandbox flag and server argv using `--sandbox danger-full-access`, the same outer Docker controls allowed official Codex to write a synthetic TypeScript file, which the executor collected and verified by contents. There is no automatic fallback that disables the inner sandbox. OpenAI documents externally isolated container execution in its [security guide](https://learn.chatgpt.com/docs/agent-approvals-security).

OpenCode supports noninteractive `run` and JSON events in its [CLI reference](https://opencode.ai/docs/cli/). Its model relay and installed-version stdin behavior are not implemented or verified here. Selecting `opencode` only enables the disconnected direct runner path.

The runner uses no shell to launch Docker and sends the prompt through stdin. Docker receives a narrow client environment containing its connection settings and PATH; no host model keys are forwarded into the container. The container has a read-only root and `/workspace`, a separately writable `/workspace/output`, a 64 MiB nonexecutable `/tmp`, non-root user, all capabilities dropped, `no-new-privileges`, 128-process limit, 512 MiB memory, one CPU and 8 MiB file-size ulimit. Healthchecks and Docker logging are disabled. Docker's [run reference](https://docs.docker.com/reference/cli/docker/container/run/) explains these container controls. The runner never mounts a Docker socket into the task.

If the worker needs a nondefault Docker Desktop/remote context, configure its client-side `DOCKER_CONTEXT` and `DOCKER_CONFIG` (or explicit `DOCKER_HOST` and TLS settings). These settings remain in the Docker client process; they are not task container environment variables. The image must contain no baked-in user credentials, platform keys, telemetry endpoints or unreviewed tools.

### Codex model requests through stdio

The trusted image includes [`relay-wrapper.mjs`](src/relay-wrapper.mjs). It writes an ephemeral user-level `CODEX_HOME/config.toml`, listens only on **127.0.0.1 inside the disconnected container**, and starts the server-configured Codex argv. The custom provider uses the Responses wire protocol without API authentication. Compression, WebSockets, HTTP/stream retries, hosted search, multi-agent mode, analytics, feedback and persistent CLI history are disabled. The official [advanced configuration guide](https://learn.chatgpt.com/docs/config-file/config-advanced) and [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference) document custom providers and these controls. The platform does not open an HTTP listener on the host for this connection.

Only POST `/responses` and `/v1/responses` reach the relay. Model requests become framed JSON lines on Docker stdout. The host executor invokes `requestModel({ requestId, body, signal })`, pins the server model and `store:false`, and sends the permitted response status, Content-Type and bytes through Docker stdin. No URL, provider headers, API key or host credential is delivered to Codex. The callback is the security boundary for real model access: the platform worker must recheck current user ownership, approval, lease, fixed route/model and task/daily budget, and persist usage or uncertainty before settling a request. The platform API implements that broker separately; these execution functions cannot authorize their own jobs. Long-lived keys stay in that server process. OpenAI's [automation guidance](https://learn.chatgpt.com/docs/non-interactive-mode#authenticate-in-automation) explains why model keys should not be exposed to repository-controlled code.

Protocol version 1 uses the prefix `@companion-relay-v1 ` followed by one JSON object and newline. Container messages are `ready`, `model.request`, `model.cancel`, `harness.output` and `harness.exit`. Host messages are `start`, `model.response.start`, `model.response.chunk` and `model.response.end`. Model chunks are canonical base64 and never become task stdout artifacts. Invalid frames, extra fields, unknown or duplicate request IDs and premature harness exits fail the execution. Limits are 1.5 MiB per frame, 1 MiB per request, two concurrent requests, 32 requests per task, 8 MiB per response, 32 MiB combined responses, 48 KiB chunks and 1 MiB combined harness stdout/stderr. Response headers other than permitted Content-Type are discarded.

Cancellation aborts each model callback and terminates the container. A cancelled request remains in-flight until its callback settles; an `exit 0` cannot conceal it. The executor waits up to five seconds for callbacks to settle after the Docker client closes. Missing confirmation becomes `MODEL_RELAY_UNCERTAIN`, which the worker must preserve as a review-required result even if its audit is still pending. The explicit public `MODEL_RELAY_*` broker codes survive cross-package errors; raw upstream exceptions and private messages do not cross the relay. The optional real-CLI test verifies only a synthetic Responses service, not commercial model behavior, cost accounting against OpenAI, or production capacity.

### Input and output files

The worker provides `readAttachment(id)` only for user-authorized upload IDs attached to the job. At most four distinct files are copied into `/workspace/input` as UUID filenames with a MIME-derived extension: 10 MiB per file and 20 MiB total. The original filename/path is never used as a host path or included in the generated input manifest. The stdin prompt lists the generated container paths. Input files and the workspace root are read-only inside the container.

Only `/workspace/output` is collected after a successful process exit. Limits are 20 regular files, 8 MiB per file, 32 MiB total, three levels of subdirectories and 100 total entries. Symbolic links, multiply linked files and special files are rejected; reads use `O_NOFOLLOW`, file identity checks and bounded buffers. UTF-8 code/text uses `text/plain`; supported image/PDF MIME types require matching signatures. HTML, SVG and unrecognized bytes use `application/octet-stream` for download. Filenames are sanitized without host paths. Artifacts are returned as `GeneratedArtifact` bytes for the worker to persist with its normal user ownership checks. Combined stdout/stderr is limited to 1 MiB and returned as private task artifacts, never application logs.

Each execution attempt gets a fresh private directory. A running-task scan enforces soft output count/size/depth/link limits; the file-size ulimit adds a per-file kernel bound. **These checks are not a hard aggregate disk quota.** Production requires a dedicated worker and filesystem/project quota for task bind mounts, plus image auditing, restricted network egress and workspace retention policy. Docker [bind mounts](https://docs.docker.com/engine/storage/bind-mounts/) expose paths on the daemon host; a remote daemon needs the same task path on that host. Mount subdirectories are excluded with `bind-recursive=disabled`.

Cancellation kills the Docker client, force-removes the named container and confirms absence when automatic removal already occurred. Temporary input/output files are removed only after confirmed container shutdown. An unconfirmed shutdown returns `CLI_CLEANUP_UNCONFIRMED`, retains the workspace for operator review and must be treated as an uncertain task by the worker. This is a coding-harness runner, not a desktop automation agent or job-application submitter.

## Private media references and durable workflows

OpenAI image edits, Ark video and fal image/video requests can read up to four distinct private image attachments through the worker's authorized `readAttachment` port. These bindings are declared in `ProviderStatus.referenceImages`, with a maximum of four images, 20 MiB combined, and PNG/JPEG/WebP MIME types. MIME types must match recognized file headers. The exported pure `validateMediaJobInput` and `validateMediaReferenceImages` helpers let the API check options and authorized bytes before queueing; the adapters check them again before submission. Header recognition is not full image decoding or a check of the selected model's dimension requirements. ComfyUI does not advertise or accept uploaded references.

OpenAI receives validated raw bytes in multipart `image[]` fields with generated reference filenames. Ark and fal receive Base64 data URIs in the inference request; those adapters do not publish a platform upload or call a public file-storage API. The platform API can create an authorized upload alias for an existing private generated image, allowing a later task to edit that result again or use it as a video reference. The API must verify ownership, completed source job, stored MIME/size and actual bytes before returning that alias; an artifact ID or result URL alone is not an attachment authorization. See the [official OpenAI image-edit guide](https://developers.openai.com/api/docs/guides/image-generation#edit-images).

OpenAI image options currently accept only `aspectRatio`. For configured `gpt-image-2.5-flare` and `gpt-image-2.5-sunburst`, exact mappings are `1:1` → `1024x1024`, `16:9` → `1536x864`, `9:16` → `864x1536`, and `4:3` → `1536x1152`. The [official size guide](https://developers.openai.com/api/docs/guides/image-generation#customize-image-output) permits custom dimensions for these models. Older or unrecognized models accept explicit `1:1`; other explicit ratios fail before inference rather than being substituted. Omitting a ratio retains the adapter's `1536x1024` default. Masks, arbitrary dimensions, quality settings and retained Responses image-edit context are not implemented by this adapter. Repeated edits use the previous private image bytes plus a new task prompt, rather than a retained model conversation.

For Ark, one reference defaults to `first_frame`, two to `first_last_frame`, and three or four to `reference_image`. An explicit `options.referenceMode` can choose these exclusive modes with the corresponding number of images. Supported options are `referenceMode`, `aspectRatio`, integer `duration`, integer `seed` and `resolution`. Known Seedance model IDs receive additional duration checks; for an explicit Seedance 2.5 first/last-frame task, a supplied ratio must be `adaptive`. The adapter does not guess the model behind an account-specific endpoint ID. Model access and other model-specific restrictions still require server configuration and official schema verification. See the [Ark task API](https://docs.volcengine.com/docs/ark/create-video-generation-task-api?lang=zh) and [Seedance 2.5 guide](https://docs.volcengine.com/docs/ark/seedance-2-5).

For fal, supported top-level options are `referenceField` and `input`. `referenceField` defaults to `image_url`; models accepting several images must use `image_urls`. The selected endpoint must support that field. When private images are supplied, either image URL field in `options.input` is rejected as a conflict. Without private references, existing explicit model inputs, including public file URLs, remain available under `options.input`; this does not grant access to private platform artifacts. Parameters remain bounded JSON (1 MiB, depth 12, 512 values) and are passed literally, with the task's prompt supplied separately. `sync_mode:true` is rejected before submission because this adapter persists queue handles and downloads HTTPS outputs rather than accepting inline output data URIs. These controls do not validate every fal model's custom schema or advertise video/audio editing. See [fal's official file-input and output schema](https://fal.ai/models/fal-ai/flux-pro/kontext/api).

Downloaded fal images are recognized from PNG/JPEG/WebP headers and stored with the matching MIME type and filename extension, even when the optional provider `content_type` is absent. A contradictory declared image type fails rather than publishing mislabeled bytes. This matters because endpoints such as Kontext default to JPEG, and the next reference step checks that MIME and bytes agree. Resuming a saved Ark or fal provider task only queries its existing handle; it does not read or submit the reference images again. ComfyUI accepts no client media options; its parameters remain in the reviewed server template.

Workflows require the platform's durable checkpoint ports. Definitions are frozen and canonically hashed; step inputs include the expanded prompt and referenced artifact identities. The runtime confirms `started` before a provider call, confirms asynchronous handles before polling, and confirms private result storage before the next step. Completed receipts are reused. A saved Ark/fal/ComfyUI handle resumes polling, while a started call without a known result is held for review. Saving templates alone does not configure or call providers. These rules do not promise exactly-once billing at an external provider when a response or database acknowledgement is lost.

Inside a workflow, references select only already completed image results from that same job. Cross-task editing uses the separately authorized private artifact alias described above. ComfyUI remains a server-reviewed workflow and currently rejects references passed into its target step. Real model entitlement, input compatibility, media quality and cost have not been tested.

ComfyUI API templates are captured once at runtime startup from `COMFYUI_WORKFLOW_TEMPLATE` (regular UTF-8 JSON, at most256KiB). A valid API graph needs nodes with `class_type` and `inputs`, plus a configured existing string prompt input at `COMFYUI_PROMPT_NODE` / `COMFYUI_PROMPT_FIELD` (default `text`). Editor workflow JSON is a different format. Invalid files disable the provider without returning their private path. Restart the API and worker after deliberately changing the template; the public catalog shows the captured version hash, with no graph, endpoint or path.

The API binds each new ComfyUI task or workflow step to `executionTemplate:{version:1,hash}`. Canonical hashing covers the original graph, prompt node/field and server base URL; it survives JSONB key ordering. The full private snapshot lives in the job execution policy. `captureComfyUITemplate()` returns a clone for the trusted API; `validateComfyUITemplateSnapshot()` checks saved material without consulting environment configuration, while runtime `validateComfyUITemplate()` additionally checks the current server endpoint. Callers must provide the saved snapshot through the worker context even when resuming a known queue handle. Missing, tampered or mismatched snapshots fail before external requests; there is no legacy fallback that rereads a mutable file.

Dispatch substitutes only the user prompt into a clone of the captured graph. Changing the source file or starting a new runtime version does not change the graph of an existing task. Changing the server endpoint rejects old dispatch and polling rather than contacting a different server with an old handle. Every unfinished workflow template is checked before any earlier text/media step runs. Public template identities enter definition and effective input hashes; completed step receipts retain their original version. Template pinning covers API graph inputs and routing, not server weights, custom-node versions, internal network effects, output quality or external billing. Those require a separately reviewed ComfyUI server and execution environment.

`{{input}}` uses the task's original goal; `{{previous}}` uses the latest completed text result. Substitution is performed once with literal replacement values. Media travels through explicit earlier image references, rather than prompt text or public URLs. Current plans are linear and do not include top-level user attachments, DAGs, browser/CLI substeps, or video/audio editing.

## Local verification

`ChatContext.onModelCall` is an optional trusted server hook for each actual chat request. The runtime awaits `started` before HTTP and always attempts `finished` in `finally`; hook failures propagate and prevent later tool/model actions. Finished events contain only a generated call ID, status and validated provider-reported input/output token counts, or explicit `missing`/`invalid` coverage. Whole-call reports are not deltas; identical repeats are deduplicated and conflicting reports are invalid. Ollama and Ark request final streaming usage with `include_usage`; OpenRouter uses its default final report. Workflow calls do not yet forward this hook to the platform ledger. No prices or reservations are represented as actual token usage.

```sh
pnpm --filter @companion/ai-core check
pnpm --filter @companion/ai-core test
```

Browser fixtures use a real locally installed Chromium with invented HTML and explicit loopback origins. Regular CLI tests replace the Docker executable with a protocol fixture to inspect argv, cancellation, secrets isolation and synthetic file input/output. The optional test below additionally runs the official Codex CLI in a real Docker container and returns only synthetic Responses through `requestModel`. It asserts a generated file's actual bytes. It does not enable the commercial provider gate or require an API key.

Build the reviewed image with the helper, which sends only the Dockerfile and wrapper as its build context:

```sh
node infra/platform/harness/build.mjs
PLATFORM_TEST_REAL_HARNESS=1 PLATFORM_TEST_CLI_EXTERNAL_SANDBOX=1 \
  pnpm --filter @companion/ai-core test
```

The external-sandbox test flag is explicit because the tested Colima runtime does not support the inner sandbox. On a runtime with working inner isolation, omit it to verify the default `workspace-write` path. `PLATFORM_TEST_CAPTURE_SCHEMA=1` emits only request field/tool/type names for compatibility inspection, never prompt contents. See the [harness build instructions](../../infra/platform/harness/README.md). A passing fixture does not prove a commercial provider, production worker isolation or deployment is configured.
